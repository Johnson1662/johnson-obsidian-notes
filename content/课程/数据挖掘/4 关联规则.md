# 4.2 Apriori 算法

## 4.2.1 基本概念

### 引例：一个超市的 10 笔交易

商品集 $I=\{$bread, beer, cake, cream, milk, tea$\}$（6-项集），|D| = 10。

| TID | 顾客购买商品 Items   | TID | 顾客购买商品 Items   |
| --- | -------------------- | --- | -------------------- |
| T1  | bread cream milk tea | T6  | bread tea            |
| T2  | bread cream milk     | T7  | beer milk tea        |
| T3  | cake milk            | T8  | bread tea            |
| T4  | milk tea             | T9  | bread cream milk tea |
| T5  | bread cake milk      | T10 | bread milk tea       |

### 9 个定义

| 定义 | 名称                    | 记法 / 公式                                                                                                                           | 要点与例子                                                                 |
| ---- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 4.1  | 项目与项集              | $I=\{i_1,i_2,\ldots,i_m\}$，项集 $X$ 的长度为 $k$ 则称 $k$-项集                                                                       | 每个商品是一个项目；$X=\{$milk, tea$\}$ 是 2-项集，$I$ 是 6-项集           |
| 4.2  | 交易                    | $T\subseteq I$（非空子集），每笔交易有唯一交易号 TID，全体构成交易数据库 $D$                                                          | $\lvert D\rvert=10$；习惯用 TID 指代一笔交易                               |
| 4.3  | 项集的支持度            | $\text{support}(X)=\dfrac{\text{count}(X\subseteq T)}{\lvert D\rvert}$                                                                | count 是**绝对**支持度（支持度计数），support 是**相对**支持度（出现概率） |
| 4.4  | 最小支持度与频繁集      | 满足 $\text{support}\ge \text{min\_sup}$ 的项集为**频繁项集**，$k$-项集称 $k$-频繁集，记 $L_k$                                        | 不满足的称非频繁集；只有满足 min_sup 的项集才能产生规则                    |
| 4.5  | 关联规则                | $R:\ X\Rightarrow Y$，其中 $X\subset I,\ Y\subset I,\ X\cap Y=\phi$                                                                   | 语义：$X$ 出现会导致 $Y$ 以某一概率同时出现                                |
| 4.6  | 规则的支持度            | $\text{support}(X\Rightarrow Y)=\dfrac{\text{count}(X\cup Y)}{\lvert D\rvert}$                                                        | 即**联合概率** $p(X,Y)$                                                    |
| 4.7  | 规则的置信度            | $\text{confidence}(X\Rightarrow Y)=\dfrac{\text{support}(X\cup Y)}{\text{support}(X)}=\dfrac{\text{count}(X\cup Y)}{\text{count}(X)}$ | 即**条件概率** $p(Y\mid X)$；反映"含 $X$ 则含 $Y$"的概率                   |
| 4.8  | 最小支持度 / 最小置信度 | $\text{min\_sup}$（最低重要性）、$\text{min\_conf}$（最低可靠性）                                                                     | 用户给定；两条门槛缺一不可                                                 |
| 4.9  | 强关联规则              | $\text{support}\ge\text{min\_sup}$ **且** $\text{confidence}\ge\text{min\_conf}$                                                      | 否则为弱关联规则；只有强规则才用于指导商家决策                             |

### 支持度与置信度的算例

课件用 $X=\{bread,milk\}$、$Y=\{tea\}$ 演示：

| 规则 / 项集                     | 计算                                          | 结果 |
| ------------------------------- | --------------------------------------------- | ---: |
| $X=\{bread,milk\},\ Y=\{tea\}$  | $\text{count}(X\cup Y)=3,\ \lvert D\rvert=10$ |  0.3 |
| $X=\{tea\},\ Y=\{bread,milk\}$  | 同上（$\cup$ 对称）                           |  0.3 |
| $X=\{bread\},\ Y=\{tea,cream\}$ | $\text{count}=2$                              |  0.2 |

| 项集                       | 支持度计数 | 支持度 |
| -------------------------- | ---------: | -----: |
| $X_1=\{$bread$\}$          |          7 |    0.7 |
| $X_2=\{$bread,milk$\}$     |          5 |    0.5 |
| $X_3=\{$bread,milk,tea$\}$ |          3 |    0.3 |

| 规则                               | 置信度    | 数值  |
| ---------------------------------- | --------- | ----- |
| $\{bread,milk\}\Rightarrow\{tea\}$ | $0.3/0.5$ | 0.6   |
| $\{tea\}\Rightarrow\{bread,milk\}$ | $0.3/0.7$ | ≈0.43 |

若 $\text{min\_sup}=0.3$：$\{bread,milk\}$ 支持度 0.5 → **2-频繁集**；$\{cake,milk\}$ 支持度 0.2 → **非频繁集**。

### 课件例：网球拍与网球（表 1）

数据库含 **6 个事务**，项集 $I=\{$网球拍, 网球, 运动鞋, 羽毛球$\}$，$\text{min\_sup}=0.5$、$\text{min\_conf}=0.5$。

| TID | 网球拍 | 网球 | 运动鞋 | 羽毛球 |
| --- | -----: | ---: | -----: | -----: |
| 1   |      1 |    1 |      1 |      0 |
| 2   |      1 |    1 |      0 |      0 |
| 3   |      1 |    0 |      0 |      0 |
| 4   |      1 |    0 |      1 |      0 |
| 5   |      0 |    0 |      1 |      1 |
| 6   |      1 |    1 |      0 |      0 |

考虑规则：网球拍 ⇒ 网球
$$\text{支持度}=\frac{3}{6}=0.5\ge 0.5,\qquad \text{置信度}=\frac{3}{5}=0.6\ge 0.5$$
两条门槛都过，所以**是强关联规则**（分子 3 = 同时买两样的交易数，分母 5 = 买网球拍的交易数）。

## 4.2.2 挖掘策略

### 两个子任务

| 子任务                                      | 目标                                                 | 产出                   |
| ------------------------------------------- | ---------------------------------------------------- | ---------------------- |
| 频繁项集产生（Frequent Itemset Generation） | 发现所有满足最小支持度阈值的项集                     | **频繁项集**           |
| 规则的产生（Rule Generation）               | 从上一步的频繁项集中提取所有高支持度、高置信度的规则 | **强规则** strong rule |

目标是找出支持度 $\ge\text{min\_sup}$ 且置信度 $\ge\text{min\_conf}$ 的所有规则。

### 为什么不能蛮干

**格结构（lattice structure）**：由事务数据集产生的频繁项集数量可能非常大——给定 $d$ 个项目，共有 $2^{d}-1$ 个可能的候选项集（$A,AB,ABC,\ldots$ 层层张开）。

**Brute-force（暴力）方法**：把格结构中每个项集都当候选项集，将每个候选项集与每个事务比较，确定支持度计数。

$$M=2^{d}-1,\qquad \text{时间复杂度}\sim O(NMW)$$

其中 $N$ 为事务数、$M$ 为候选项集数、$W$ 为事务最大宽度。开销可能非常大，从数据集提取规则的数量达**指数级**。

### 降低计算复杂度的两条路

| 思路               | 做法                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| 减少候选项集的数量 | 先验（apriori）原理：非频繁项集不参与生长                                               |
| 减少比较的次数     | 不再让每个候选项集与每个事务逐一匹配，改用更高级的数据结构，或存储候选项集 / 压缩数据集 |

## 4.2.3 Apriori 算法

Apriori 是最有影响的挖掘频繁项集的算法，名字就来自它使用了**频繁项集性质的先验知识**。

### 先验原理与反单调性

| 命题                                                   | 推论                                           |
| ------------------------------------------------------ | ---------------------------------------------- |
| 一个项集是**频繁**的，则它的所有**子集**一定也频繁     | 频繁项集的全部子集都是频繁集                   |
| 一个项集是**非频繁**的，则它的所有**超集**一定也非频繁 | 非频繁项集可以安全剪枝，其上生长的分支全部砍掉 |

这种基于支持度度量修剪指数搜索空间的策略称为**基于支持度的剪枝**（support-based pruning），它依赖支持度度量的关键性质：

$$\text{项集的支持度}\ \le\ \text{它任一子集的支持度}\qquad(\text{反单调性 anti-monotone})$$

### 基本思想：level-wise 逐层搜索

$$
L_1\ \to\ C_2\ \to\ L_2\ \to\ C_3\ \to\ \cdots\ \to\ L_k=\varnothing\ \text{时结束}
$$

- 先找频繁 1 项集 $L_1$，用 $L_1$ 找 $L_2$，用 $L_2$ 找 $L_3$，直到没有新的频繁 $k$-项集；**每个 $L_k$ 都要求对数据库作一次完全扫描**。
- 用 $L_{k-1}$ 找 $L_k$ 分两步：
  - **连接步**：$L_{k-1}$ 与自身连接，产生候选 $k$-项集的集合 $C_k$；
  - **剪枝步**：剪除不满足最小支持度的候选项集（含非频繁子集的候选一律剪掉）。

### 手工跑一遍（4 个事务，min_sup 计数 = 2）

| TID | Items      | TID | Items          |
| --- | ---------- | --- | -------------- |
| T1  | I1, I3, I4 | T3  | I1, I2, I3, I5 |
| T2  | I2, I3, I5 | T4  | I2, I5         |

| 轮次                     | 候选与计数                                                                    | 结果                             |
| ------------------------ | ----------------------------------------------------------------------------- | -------------------------------- |
| 扫描 D 计数 1 项集       | I1:2, I2:3, I3:3, **I4:1**, I5:3                                              | $L_1=\{I1,I2,I3,I5\}$（I4 被剪） |
| 连接 $L_1$ 得 2 项集候选 | I1I2, I1I3, I1I5, I2I3, I2I5, I3I5（6 个）                                    | —                                |
| 扫描 D 计数 2 项集候选   | I1I2:1, I1I3:2, I1I5:1, I2I3:2, I2I5:3, I3I5:2                                | $L_2=\{I1I3,I2I3,I2I5,I3I5\}$    |
| 连接 $L_2$ 得 3 项集候选 | I1I2I3, I1I2I5, I1I3I5, I2I3I5；前三者含非频繁子集 I1I2 / I1I5 → **剪枝剪掉** | 只剩 I2I3I5                      |
| 扫描 D 计数 3 项集候选   | **I2I3I5:2** $\ge 2$                                                          | $L_3=\{I2,I3,I5\}$               |
| 下一轮                   | 无法再由 $L_3$ 连接出候选                                                     | **算法终止**                     |

所有频繁项集共 9 个：$L_1$ 4 个 + $L_2$ 4 个 + $L_3$ 1 个。

### 伪代码

```text
输入：交易数据库 D，最小支持阈值 min_sup
输出：D 中的频繁项集 L = ∪ Lk

(1)  L1 = find_frequent_1_itemset(D);        // 发现 1-项集
(2)  for (k = 2; L(k-1) ≠ ∅; k++) {
(3)      Ck = apriori_gen(L(k-1), min_sup);  // 连接 + 剪枝，产生候选 k-项集
(4)      for each t ∈ D {                    // 扫描数据库，确定支持频度
(5)          Ct = subset(Ck, t);             // 取 t 所包含的候选项集
(6)          for each c ∈ Ct
(7)              c.count++;
(8)      }
(9)      Lk = {c ∈ Ck | c.count > min_sup};
(10) }
(11) return L = ∪ Lk;
```

### 第二个例：Bread / Milk / Beer / Diaper（最小支持度计数 = 3）

| TID | Items                     | TID | Items                     |
| --- | ------------------------- | --- | ------------------------- |
| 1   | Bread, Milk               | 4   | Bread, Milk, Diaper, Beer |
| 2   | Bread, Diaper, Beer, Eggs | 5   | Bread, Milk, Diaper, Coke |
| 3   | Milk, Diaper, Beer, Coke  |     |                           |

| 层级   | 计数                                                                                          | 频繁项集                                         |
| ------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1 项集 | Bread 4, Coke 2, Milk 4, Beer 3, Diaper 4, Eggs 1                                             | Bread、Milk、Beer、Diaper（Coke 2、Eggs 1 被剪） |
| 2 项集 | Bread,Milk 3；**Bread,Beer 2**；Bread,Diaper 3；**Milk,Beer 2**；Milk,Diaper 3；Beer,Diaper 3 | 4 个（黑体两个被剪）                             |
| 3 项集 | Bread,Milk,Diaper **2** $<3$                                                                  | 无频繁 3 项集                                    |

这个例子最能说明先验原理的价值：**枚举所有项集将产生 $C_6^1+C_6^2+C_6^3=41$ 个候选，使用先验原理只需 $6+6+1=13$ 个。**

### 两个重要特点

| 特点          | 说明                                                                             |
| ------------- | -------------------------------------------------------------------------------- |
| 逐层算法      | 从频繁 1-项集到最长的频繁项集，每次遍历项集格中的一层                            |
| 产生-测试策略 | 每次迭代由上一轮发现的频繁项集产生新候选，再对每个候选计数并与最小支持度阈值比较 |

迭代次数是 $k_{\max}$，即频繁项集的最大长度。

### 规则产生

忽略前件或后件为空的规则，每个频繁 $k$-项集能够产生多达 $2^{k}-2$ 条关联规则。

提取方式：把项集 $Y$ 划分成两个非空子集 $X$ 和 $Y-X$，使得 $X\Rightarrow Y-X$ 满足置信度阈值。

若 $\{A,B,C,D\}$ 是频繁项集，候选规则共 $2^4-2=14$ 条：

| 后件 1 项                  | 后件 2 项                                | 后件 3 项                  |
| -------------------------- | ---------------------------------------- | -------------------------- |
| ABC⇒D, ABD⇒C, ACD⇒B, BCD⇒A | AB⇒CD, AC⇒BD, AD⇒BC, BC⇒AD, BD⇒AC, CD⇒AB | A⇒BCD, B⇒ACD, C⇒ABD, D⇒ABC |

这些规则必然已经满足支持度阈值，因为它们都是由频繁项集产生的；**支持度只需算一次，规则产生阶段只需再查置信度**。

## 4.2.6 Apriori 算法复杂度分析

| 因素             | 影响                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------- |
| 支持度阈值 ↓     | 更多项集变成频繁的，计算复杂度增加；频繁项集最大长度增加，导致需要扫描数据集的次数也增多  |
| 项数 ↑           | 存储项的支持度计数需要更多空间；若频繁项集数目也随之增长，候选更多，计算量与 I/O 开销增加 |
| 事务数 ↑         | 算法反复扫描数据集，运行时间随之增加                                                      |
| 事务的平均宽度 ↑ | 频繁项集最大长度随之增加；事务包含更多项集，支持度计数时的遍历次数增加                    |

## 4.2.7 Apriori 算法优缺点

| 优点                     | 缺点                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 简单、易理解、数据要求低 | ① 每一步产生候选项集时循环产生的组合过多，没有排除不应参与组合的元素；② 每次计算项集支持度都对数据库 $D$ 的全部记录扫描比较，大型数据库的 I/O 开销随记录数呈几何级数增长 |

**瓶颈**：算法模式是"候选项集 — 生成 — 测试"。

| 主要开销           | 说明                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------- |
| 生成候选项集代价高 | 数据库含 100 个项目时，候选项集数量 $C_{100}^1+C_{100}^2+\cdots+C_{100}^{100}=2^{100}-1$ |
| 多次重复扫描数据库 | 每一层都要把数据库全扫一遍                                                               |

于是问题变成：**如何提高生成频繁项集的效率？** → 引出 FP-growth。

# 4.3 FP-growth 算法

## 4.3.1 动机与整体思想

| 角度     | 内容                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 针对瓶颈 | Apriori **需要产生大量候选项集**、**需要重复地扫描数据库**                                    |
| 提出     | 2000 年 Jiawei Han 等人提出基于 FP-树生成频繁项集的 FP-growth；属于"**不生成候选项集**"的方法 |
| 压缩方式 | FP-树是输入数据的压缩表示：逐个读入事务，把每个事务映射到 FP-树中的一条路径                   |
| 两阶段   | ① **建立 FP-树**：把数据库中的事务构造成一棵 FP-树；② **挖掘 FP-树**：挖掘频繁模式和关联规则  |
| 扫描次数 | 只进行 **2 次**数据库扫描，不使用候选集；研究表明比 Apriori **约快一个数量级**                |

两次扫描各做什么：

| 扫描    | 作用                                                   |
| ------- | ------------------------------------------------------ |
| 第 1 次 | 得到 1 维频繁项集（频繁项及其支持度），并排序成 F-list |
| 第 2 次 | 用 1 维频繁项集过滤数据库中的非频繁项，同时生成 FP-树  |

$$
\begin{array}{c}
\text{数据库}\ \xrightarrow{\text{扫描 1}}\ \text{频繁 1 项集}\ \xrightarrow{\text{按支持度降序}}\ \text{F-list}\\[4pt]
\text{F-list}\ \xrightarrow{\text{扫描 2}}\ \text{FP-树}\ \xrightarrow{\text{前缀路径}}\ \text{条件模式基}\ \to\ \text{频繁项集}
\end{array}
$$

## 4.3.2 五个定义

| 定义 | 名称           | 组成 / 要点                                                                                                                            |
| ---- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 4.10 | **FP-树**      | 树形结构：一个频繁项组成的**头表**、一个标记为 "null" 的**根节点**，根的子节点是**项前缀子树**的集合                                   |
| 4.11 | 频繁项头表     | Head Table 每个表项两个域：`item-name` 与 `node_link`；`node_link` 指向 FP-树中同名项的第一个节点，有时也含支持度计数                  |
| 4.12 | 项前缀子树     | 每个节点三个域：`item-name`、`count`（所在路径代表的交易中包含此节点项目的交易个数）、`node_link`（指向下一个同名节点，没有则为 null） |
| 4.13 | **条件模式基** | 一个"子数据库"，由 FP-树中与该后缀模式一起出现的**前缀路径集**组成                                                                     |
| 4.14 | 条件 FP-树     | 由**条件模式基**构造出来的 FP-子树                                                                                                     |

## 4.3.3 第一阶段：构造 FP-树

步骤：

1. 扫描数据库 $D$ 一遍，得到频繁项的集合 $F$ 和每个频繁项的支持度；把 $F$ 按支持度**递降**排序，结果记为 $L$；
2. 创建 FP-树的根节点 $T$，标记为 "null"；
3. 第二次扫描 $D$：每个事务中的项按 $L$ 中的次序排列，并对每个事务创建分枝；沿共同前缀上的每个结点计数加 1，为前缀之后的项创建结点和链接。

### 例一：A–E 五个商品，min_sup = 2

| TID | Items        | TID | Items        |
| --- | ------------ | --- | ------------ |
| 1   | {B, A}       | 6   | {D, B, A, C} |
| 2   | {B, D, C}    | 7   | {A}          |
| 3   | {E, C, D, A} | 8   | {B, A, C}    |
| 4   | {A, E, D}    | 9   | {B, A, D}    |
| 5   | {C, A, B}    | 10  | {B, E, C}    |

| 项目 | A   | B   | C   | D   | E   |
| ---- | --- | --- | --- | --- | --- |
| 频率 | 8   | 7   | 6   | 5   | 3   |

F-list $=$ A(8), B(7), C(6), D(5), E(3)；每个事务内的项重排后，逐个插入构建 FP-树。

构造过程（前几个事务）：

| 读入 | 事务         | 树的变化                                                                                      |
| ---- | ------------ | --------------------------------------------------------------------------------------------- |
| T1   | {A, B}       | 新建路径 null → A:1 → B:1                                                                     |
| T2   | {B, C, D}    | 与 T1 无共同前缀，新建路径 null → B:1 → C:1 → D:1                                             |
| T3   | {A, C, D, E} | 与 T1 **共享共同前缀项 A**，路径 null→A→C→D→E 与 null→A→B 部分重叠，结点 A 的频度计数增加为 2 |
| …    | …            | 继续该过程，直到每个事务都映射到 FP-树的一条路径                                              |

最终 FP-树（min_sup = 2）：

```text
null
├── A:8
│   ├── B:5 ─┬── C:3 ── D:1        (T5, T6, T8 的公共前缀；T6 继续长 D)
│   │        └── D:1               (T9)
│   ├── C:1 ── D:1 ── E:1          (T3)
│   └── D:1 ── E:1                 (T4)
└── B:2 ── C:2 ─┬── D:1            (T2)
                └── E:1            (T10)
```

### 例二：f, c, a, b, m, p（min_sup = 3）

| TID | Items bought             | (ordered) frequent items |
| --- | ------------------------ | ------------------------ |
| 100 | {f, a, c, d, g, i, m, p} | {f, c, a, m, p}          |
| 200 | {a, b, c, f, l, m, o}    | {f, c, a, b, m}          |
| 300 | {b, f, h, j, o, w}       | {f, b}                   |
| 400 | {b, c, k, s, p}          | {c, b, p}                |
| 500 | {a, f, c, e, l, p, m, n} | {f, c, a, m, p}          |

头表（Header Table）：f 4, c 4, a 3, b 3, m 3, p 3；F-list $=$ f-c-a-b-m-p。

```text
null
├── f:4 ── c:3 ── a:3 ─┬── m:2 ── p:2     (T100, T500)
│                      └── b:1 ── m:1     (T200)
├── f:4 ── b:1                             (T300)
└── c:1 ── b:1 ── p:1                      (T400)
```

### FP-树的大小与排序

| 结论               | 说明                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| 通常会比原数据小   | 因为关联规则的数据中事务常常共享一些共同项；若共同项较少，压缩效果不明显 |
| 大小依赖项如何排序 | 一般按**支持度计数递减序**排列，可以得到较小的 FP-树                     |
| 含结点链接指针列表 | 连接具有相同项的结点，便于快速访问树中的项                               |

## 4.3.4 第二阶段：挖掘 FP-树

- 输入：FP-树；输出：针对 FP-树挖掘频繁模式和关联规则。
- 因为每个事务都映射成一条路径，所以**只考察包含特定结点（例如 $i$）的路径，就能发现以 $i$ 结尾的频繁项集**；借助与结点 $i$ 关联的指针可快速访问这些路径。

五个步骤：

| 步骤  | 内容                                                                       |
| ----- | -------------------------------------------------------------------------- |
| Step1 | 读取数据库，构造频繁 1 项集及 FP-树                                        |
| Step2 | 遍历头表，对每个频繁项 $i$ 累积它的所有前缀路径，形成 $i$ 的**条件模式基** |
| Step3 | 对条件模式基上每条路径的节点更新计数为 $i$ 的计数，构造**条件 FP-树**      |
| Step4 | 从条件 FP-树中找到所有路径，对路径上的节点找出所有组合方式，合并计数       |
| Step5 | 把 Step4 的频繁项集与 $i$ 合并，得到包含 $i$ 的频繁项集                    |

Step2–5 循环，直到遍历头表中的所有项。

### 例一（续）：A–E 的条件模式基与频繁项集

| 项  | 条件模式基                   | 合并计数                        | 得到的频繁项集                                      |
| --- | ---------------------------- | ------------------------------- | --------------------------------------------------- |
| A   | 空前缀                       | —                               | {A}                                                 |
| B   | A:5                          | A:5                             | {B}, {A,B}                                          |
| C   | AB:3, A:1, B:2               | A:4, B:5, AB:3                  | {C}, {A,C}, {B,C}, {A,B,C}                          |
| D   | ABC:1, AB:1, AC:1, A:1, BC:1 | A:4, B:3, C:3；AB:2, AC:2, BC:2 | {D}, {A,D}, {B,D}, {C,D}, {A,B,D}, {A,C,D}, {B,C,D} |
| E   | ACD:1, AD:1, BC:1            | A:2, C:2, D:2；AD:2             | {E}, {A,E}, {C,E}, {D,E}, {A,D,E}                   |

注意合并计数的读法：$D$ 的五条前缀路径先把单项目计数相加（A 出现 4 次、B 3 次、C 3 次），再把 2 项组合出现次数相加（AB 2、AC 2、BC 2），只有 $\ge\text{min\_sup}=2$ 的组合才保留。

### 例二（续）：f, c, a, b, m, p 的条件模式基

| 项  | 条件模式基      |
| --- | --------------- |
| c   | f:3             |
| a   | fc:3            |
| b   | fca:1, f:1, c:1 |
| m   | fca:2, fcab:1   |
| p   | fcam:2, cb:1    |

从 $P$ 的条件数据库（fcam:2, cb:1）出发，把含 $P$ 的前缀组合与 $P$ 合并，就得到以 $P$ 结尾的频繁模式。

## 4.3.5 结构优点与对比

FP-树结构的优点：

| 性质   | 说明                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 完整性 | 保持了频繁项集挖掘的**完整信息**                                                                                               |
| 紧密性 | 减少不相关的信息，去掉了非频繁的项；项按支持度降序排列，越频繁出现越可能被共享；**不计结点链接和计数域时，不会比原数据库更大** |

FP-growth 与 Apriori 的比较（数据集 T25I20D10K）：在不同支持度阈值下，FP-growth 的运行时间都明显低于 Apriori——**约快一个数量级**，且不需要产生候选集。

# 4.4 推荐算法

## 为什么需要推荐

| 动机     | 说明                                                                             |
| -------- | -------------------------------------------------------------------------------- |
| 长尾挖掘 | 商品、服务、广告的销量是**高斯分布 vs 长尾分布**，难点是"如何找到匹配的长尾商品" |
| 流量利用 | 把宝贵的页面位置花在更可能被点击的内容上                                         |
| 用户体验 | 用户视角：找到自己想要的商品                                                     |
| 技术储备 | 平台视角：提升长尾商品价值                                                       |

推荐要解决的"页面困境"，四个特点：

| 特点     | 含义                                        |
| -------- | ------------------------------------------- |
| 宝贵的   | 页面位置有限：外部成本、内部成本            |
| 不确定的 | 用户意图不确定                              |
| 差异化的 | 整体用户群与到达具体页面/位置的用户是不同的 |
| 稀疏的   | 差异化的另一面：每一"种"用户的数量很少      |

技术发展脉络：**人工规则 → 关联规则 → 行为类算法 → 内容类算法 → 多算法融合 → 引入机器学习 → 引入深度学习**。

## 4.4.1 基于流行度的推荐算法

| 项   | 内容                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------- |
| 做法 | 比较简单粗暴，主要对热点商品或信息推荐：用分享率、点击量、得票数等数据按某种热度排序推荐给用户     |
| 优点 | 简单；适用于刚注册的新用户，能解决**对新用户进行推荐的冷启动问题**                                 |
| 缺点 | 分数是人为设计的，无法提供个性化推荐                                                               |
| 优化 | 加入用户分群的流行度排序，例如把热榜上的体育内容优先推荐给体育迷，把政要热文推给热爱谈论政治的用户 |

热度打分（衰减式）：

$$\text{score}=\frac{P-1}{(T+2)^G}$$

$P$ 为帖子得票数，$T$ 为帖子发布时间，$G$ 为超参数（控制衰减速度）。

## 4.4.2 基于关联规则的推荐算法

| 项       | 内容                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 首要目标 | 挖掘出关联规则：同时被很多用户购买的物品集合，集合内的物品可以**相互推荐**                                                           |
| 算法来源 | 目前关联规则挖掘算法主要从 **Apriori** 和 **FP-Growth** 两个算法发展演变而来                                                         |
| 优势     | 转化率较高——用户已经购买了频繁集合中的若干项目后，购买该频繁集合中其他项目的可能性更高                                               |
| 缺点     | ① 计算量较大（但可以离线计算，影响不大）；② 采用用户数据，不可避免存在**冷启动和稀疏性**问题；③ 存在**热门项目容易被过度推荐**的问题 |

## 4.4.3 基于协同过滤的推荐算法

协同过滤基于"**物以类聚，人以群分**"的假设：喜欢相同物品的用户更有可能具有相同的兴趣。它一般应用于**有用户评分**的系统，通过分数刻画用户对物品的喜好，被视为利用**集体智慧**的典范——不需要对项目进行特殊处理，而是通过用户建立物品与物品之间的联系。

两类：

| 类型                | 口诀       | 做法                                                                                   |
| ------------------- | ---------- | -------------------------------------------------------------------------------------- |
| 基于用户 User-based | "人以群分" | 找到与用户兴趣相同的用户（有过类似行为），把这些人浏览过/买过的物品推荐给用户          |
| 基于物品 Item-based | "物以类聚" | 若很多用户对某两个物品有相似偏好，则这两个物品"相似"，推荐与用户喜欢过的物品相似的东西 |

### 4.4.3.1 基于用户的推荐算法

思路：根据所有用户对物品的偏好（评分），发现与当前用户口味相似的"**邻居**"用户群（一般用计算 **K 近邻**的算法），再基于这 $K$ 个邻居的历史偏好为当前用户推荐。

| 优点                                                                                             | 缺点                                                                                                             |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 推荐物品之间内容上可能完全不相关，因此可以**发现用户的潜在兴趣**，并为每个用户生成个性化推荐结果 | Web 系统中用户增长速度远大于物品增长速度，计算量增长巨大，系统性能容易成为瓶颈；业界单纯用基于用户的协同过滤较少 |

实现三步与公式（用户向量每个维度表示一个**物品**，如 $u:[1,1,0,1,\ldots]$）：

$$
\text{sim}(u_i,u_j)=\cos\big(\theta_{\{u_i,u_j\}}\big)=\frac{u_i\cdot u_j}{\lvert u_i\rvert\lvert u_j\rvert}
$$

$$
\text{rel}(\text{user}_i,\text{item}_j)=\sum_k \text{sim}(\text{user}_i,\text{user}_k)\cdot\text{rate}(\text{user}_k,\text{item}_j)
$$

三个工程问题（课件 Q&A）：

| 问题                                     | 答案                                                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 是否需要计算每两个用户之间的相似度？     | 不需要——大量用户之间的相关性可以预判为 0（如 $[1,2,0]\cdot[0,0,3]$ 结果必然为 0），用**倒排表**高效筛选 |
| 是否需要用一个用户的全部相关用户来计算？ | 不需要——相关性影响衰减非常快，只需取 **TopK**；去除的位置是"用户相关性计算阶段"                         |
| 没有 rate 怎么办？                       | 用隐式反馈 implicit feedback：点击、浏览、购买……                                                        |

### 4.4.3.2 基于物品的推荐算法

思路：用所有用户对物品的偏好（评分）发现**物品与物品之间的相似度**，再根据用户的历史偏好把类似的物品推荐给用户。

| 结论             | 说明                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 与关联规则的关系 | 可以看作是关联规则推荐的一种**退化**；但协同过滤更多考虑用户实际评分，且只计算相似度而非寻找频繁集，因此准确率较高、覆盖率更高 |
| 与基于用户相比   | 应用更广泛，扩展性和算法性能更好（物品增长速度一般较为平缓，性能变化不大）；缺点是无法提供个性化的推荐结果                     |

实现三步与公式（物品向量每个维度表示一个**用户**，如 $\text{item}:[1,1,0,1,\ldots]$）：

$$
\text{sim}(\text{item}_i,\text{item}_j)=\cos\big(\theta_{\{\text{item}_i,\text{item}_j\}}\big)=\frac{\text{item}_i\cdot \text{item}_j}{\lvert \text{item}_i\rvert\lvert \text{item}_j\rvert}
$$

$$
\text{rel}(\text{user}_i,\text{item}_j)=\sum_k \text{sim}(\text{item}_k,\text{item}_j)\cdot\text{rate}(\text{user}_i,\text{item}_k)
$$

课件例：6 个用户 × 6 个物品的评分矩阵（空格 = 未评分）。

| 用户 \ 物品 | 1   | 2   | 3   | 4   | 5   | 6   |
| ----------- | --- | --- | --- | --- | --- | --- |
| A           | 4   | 3   |     |     | 5   |     |
| B           | 5   |     | 4   |     | 4   |     |
| C           | 4   |     | 5   | 3   | 4   |     |
| D           |     | 3   |     |     |     | 5   |
| E           |     | 4   |     |     |     | 4   |
| F           |     |     | 2   | 4   |     | 5   |

按用户维度算物品相似度，物品 1 与物品 2/3/4/5/6 的余弦相似度为：

| 与物品 1 相比 | 物品 2 | 物品 3 | 物品 4 | 物品 5 | 物品 6 |
| ------------- | ------ | ------ | ------ | ------ | ------ |
| 相似度        | 0.27   | 0.79   | 0.32   | 0.99   | 0      |

- 物品 1 的向量（按用户 A…F）= $(4,5,4,0,0,0)$，物品 2 = $(3,0,0,3,4,0)$：只有公共用户 A 有评分，$\dfrac{12}{\sqrt{57}\cdot\sqrt{34}}\approx 0.27$ → **相似**（绿色）；
- 物品 1 与物品 5 = $(5,4,4,0,0,0)$ 在 A、B、C 上高度重合 → 0.99；
- 物品 5 与物品 6 没有任何共同用户 → 相似度 0 → **不相似**（红色）。

### 基于用户 vs 基于物品

| 基于用户                                           | 基于物品                                       |
| -------------------------------------------------- | ---------------------------------------------- |
| 结果群体化、扩展化                                 | 结果个性化、精准化                             |
| 适用于用户量相对小于物品量的场景，例如新闻推荐系统 | 适用于物品量相对小于用户量的场景，例如电商平台 |
| 对用户新行为敏感度低                               | 对用户新行为敏感度高                           |
| 对物品新行为敏感度高                               | 对物品新行为敏感度低                           |
| 推荐理由说服力较弱                                 | 推荐理由说服力较强                             |

### 协同过滤的优缺点

| 优点                                                                                 |
| ------------------------------------------------------------------------------------ |
| 不需要对物品或用户进行严格建模，也不要求物品的描述是机器可以理解的，因此**领域无关** |
| 计算出来的推荐是开放的，可以共用他人的经验，很好地支持用户发现潜在的兴趣偏好         |

| 缺点                                                                                                       |
| ---------------------------------------------------------------------------------------------------------- |
| 核心是基于历史数据，对**新物品和新用户都有"冷启动"**问题                                                   |
| 推荐效果依赖于用户历史偏好数据的多少和准确性                                                               |
| 大部分实现中用户历史偏好用**稀疏矩阵**存储，稀疏矩阵上的计算有明显问题，少部分人的错误偏好会严重影响准确度 |
| 对于一些特殊品味的用户不能给予很好的推荐                                                                   |
| 以历史数据为基础，抓取和建模用户偏好后很难利用偏好演变，方法**不够灵活**                                   |

## 4.4.4 基于内容的推荐算法

多用于资讯类应用：针对文章（电影、音乐）本身抽取一些 **tag** 作为关键词，继而用这些 tag 评价两篇文章的相似度。

| 项   | 内容                                                                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 优点 | 易于实现；不需要用户数据，因此**不存在稀疏性和冷启动问题**；基于物品本身特征推荐，因此**不存在过度推荐热门的问题**                                    |
| 缺点 | ① 抽取的特征既要保证准确性又要具有实际意义，否则很难保证推荐结果的相关性（豆瓣采用人工维护 tag 的策略）；② 推荐的 Item 可能会重复，典型的就是新闻推荐 |

方法：把文本表示成一个向量，用 TF-IDF 加权，再用余弦相似度算相关性。

$$
\text{tf}(t,d)=\frac{n_{t,d}}{\sum_k n_{k,d}},\qquad
\text{idf}(t,D)=\log\frac{\lvert D\rvert}{\lvert\{d\in D:\ t\in d\}\rvert},\qquad
\text{tf-idf}=\text{tf}(t,d)\times\text{idf}(t,D)
$$

$$
\text{sim}(p,q)=\cos(\theta)=\frac{p\cdot q}{\lvert p\rvert\cdot\lvert q\rvert}
$$

几何直觉：向量 $q$ 与 $d_1$、$d_2$ 的夹角 $\alpha$、$\theta$ 越小，文档越相似。

## 4.4.5 基于模型的推荐算法

为什么要换思路（课件对比）：

| 前述方法的缺点               | 机器学习的优点               |
| ---------------------------- | ---------------------------- |
| 启发式，无明确目标           | 对齐明确目标，成熟的优化方法 |
| 相对静态，反应慢             | 时效性灵活，反映可快可慢     |
| 考虑维度较少，个性化程度不足 | 特征维度丰富，个性化程度细腻 |
| 纯手工，改进空间小           | 理论储备丰富，发展空间大     |

主要使用常用的机器学习算法对目标用户建立推荐算法模型，再对用户爱好进行预测推荐、对推荐结果打分排序。

| 层次       | 代表模型                                   |
| ---------- | ------------------------------------------ |
| 浅层模型   | LR、GBDT、特征组合                         |
| 半深度模型 | FM、FFM                                    |
| 深度模型   | Wide & Deep、embedding、LSTM、ESMM、TDM 等 |

前沿（知道即可）：Nature Machine Intelligence 2023《Human–AI adaptive dynamics drives the emergence of information cocoons》指出推荐系统是**动态的人机交互过程**，人机相互适应可能推动"信息茧房"出现。

## 4.4.6 基于图的推荐算法

| 类别                 | 代表性方法                                   | 核心思想          |
| -------------------- | -------------------------------------------- | ----------------- |
| 随机游走 / 图排序    | PersonalRank, ItemRank, SimRank, RWR         | 图上的概率传播    |
| 图嵌入               | DeepWalk, node2vec, LINE, metapath2vec       | 节点低维向量化    |
| 同构 GNN             | GCN, GraphSAGE, GAT, PinSage, NGCF, LightGCN | 邻域消息聚合      |
| 异构图 GNN           | HetGNN, HAN, MAGNN, RGCN, HGT                | 元路径 / 关系聚合 |
| 知识图谱 GNN         | RippleNet, MKR, KGCN, KGAT, KGIN             | 知识图谱增强      |
| 社交图 GNN           | GraphRec, DiffNet, SocialGCN, MHCN           | 社交影响传播      |
| 会话图 GNN           | SR-GNN, GGNN, TAGNN, LESSR                   | 会话序列图建模    |
| 图对比学习           | SGL, SimGCL, XSimGCL, NCL                    | 自监督对比        |
| 图 Transformer / LLM | GraphGPT, LLaGA, GPT4Rec                     | 大模型 + 图       |
| 联邦图推荐           | FedPerGNN, FedGraphNN                        | 隐私保护协同训练  |

趋势：从浅层图嵌入走向深度 GNN，从同构二部图走向异构图 / 知识图谱，从集中式走向联邦与隐私保护，从监督学习走向自监督与对比学习，并开始与大语言模型融合（2022 年 Nature Communications 提出联邦图神经网络框架用于隐私保护个性化推荐）。

## 4.4.7 基于大模型的推荐算法

多用于**大规模、动态兴趣和复杂用户行为**的推荐场景：通过 Transformer、生成模型或大语言模型对用户历史行为、物品信息和上下文进行统一建模，并**直接生成**用户可能感兴趣的 Item 或 Item Token，而不是传统的候选集评分和排序。

流程：

$$
\begin{array}{c}
\text{收集点击、浏览、收藏、购买等历史行为}
\ \to\ \text{分析用户当前关注的内容}\\[4pt]
\to\ \text{学习"先看什么、后看什么"的行为规律}
\ \to\ \text{预测下一步可能感兴趣的内容}\\[4pt]
\to\ \text{输出电影、新闻、商品、音乐等个性化内容}
\end{array}
$$

| 范式        | 核心机制                  | 代表性方法              | 核心优势               | 主要挑战                |
| ----------- | ------------------------- | ----------------------- | ---------------------- | ----------------------- |
| 判别式      | LLM 作为特征编码器        | LLMEmb, CEILLM          | 实现简单，增强现有模型 | 未充分利用 LLM 推理能力 |
| 生成式      | 推荐即文本生成            | P5, TALLRec, RecLM-cgen | 统一框架，可解释性强   | 幻觉，推理延迟          |
| RAG         | 检索 + 生成               | CFRAG                   | 引入外部知识，缓解幻觉 | 检索质量依赖            |
| 图 / 多模态 | LLM + 结构化 / 多模态信息 | KGGLM, Molar            | 融合知识图谱与视觉信号 | 模态对齐复杂            |
| 智能体      | LLM 作为 Agent 大脑       | 自主工具学习 Agent      | 多轮交互，主动规划     | 工程复杂，延迟高        |

| 优点                                                                                                                                         | 缺点                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 能直接建模用户行为序列，捕捉兴趣随时间的变化；可利用文本、标签等丰富的语义信息；推荐从候选集排序转变为生成结果，减少对人工特征和候选集的依赖 | 模型结构复杂，训练和推理成本较高；推荐结果的准确性和可控性仍需进一步约束 |

典型方法：Transformer-based Sequential Recommendation、Generative Retrieval、LLM-based Recommendation。

当前趋势是**混合与融合**：判别式方法为生成式提供高质量的语义表示，RAG 为生成式注入实时知识，图结构为 LLM 补充结构化推理能力。

# 4.6 考前速查表

| 题目出现                                       | 立刻想到                                               |
| ---------------------------------------------- | ------------------------------------------------------ |
| 交易库 + 支持度/置信度门槛                     | 关联规则挖掘（支持度、置信度、强关联规则）             |
| 一个项集频繁 / 非频繁                          | 所有子集也频繁 / 所有超集也非频繁（剪枝）              |
| 项集支持度不会超过其子集                       | 支持度度量的**反单调性**（anti-monotone）              |
| 每层扫一遍数据库 + 连接步 / 剪枝步             | **Apriori**（level-wise，产生-测试）                   |
| $2^{d}-1$、$O(NMW)$                            | brute-force 的候选数 / 时间复杂度                      |
| 100 个项目                                     | 候选项集 $2^{100}-1$ → Apriori 的候选爆炸              |
| 频繁 $k$-项集产生规则条数                      | 最多 $2^{k}-2$ 条                                      |
| 只扫 2 遍库 + 不用候选集 + 快一个数量级        | **FP-growth**                                          |
| 头表、项前缀子树、node_link、count             | FP-树 / 头表的定义                                     |
| 与后缀模式一起出现的前缀路径集                 | **条件模式基**                                         |
| 由条件模式基构造的 FP-子树                     | **条件 FP-树**                                         |
| 页面宝贵、用户意图不确定、用户有差异、行为稀疏 | 为什么需要推荐系统                                     |
| $(P-1)/(T+2)^G$、得票数 / 时间衰减             | 基于流行度的推荐（新用户冷启动）                       |
| 已买频繁集合中若干项 → 买其余项可能性更高      | 基于关联规则的推荐（转化率高）                         |
| "人以群分"、K 近邻、用户增长快是瓶颈           | 基于用户的协同过滤                                     |
| "物以类聚"、物品增长平缓、推荐理由说服力强     | 基于物品的协同过滤                                     |
| 只用 tag／标签，不需要用户评分                 | 基于内容（无冷启动、无热门过度推荐）                   |
| TF-IDF + 余弦相似度                            | 文本 / 内容相似度计算                                  |
| LR、GBDT、FM、FFM、Wide & Deep                 | 基于模型（浅层 / 半深度 / 深度）                       |
| LightGCN、元路径、知识图谱、联邦 GNN           | 基于图的推荐                                           |
| 直接生成 Item / Item Token，不走候选集排序     | 基于大模型的推荐                                       |
| 冷启动                                         | 协同过滤的痛点；流行度（新用户）、内容（新物品）可缓解 |

复习时间分配建议：约 **70%** 放在「定义 4.1–4.9 + 支持度/置信度计算 + Apriori 手工跑例 + FP-tree 条件模式基」，其余放在「各推荐算法的优缺点对比表」。
