# 进程管理

---

## 考点 1：进程状态与转换

### 考点讲解

**进程的三个基本状态（三态模型）：**

1. **就绪态（Ready）**：进程已获得除 CPU 之外的所有资源，一旦获得 CPU 即可运行。多个就绪进程通常排成就绪队列。
2. **运行态（Running）**：进程已获得 CPU，正在执行指令。在单 CPU 系统中，同一时刻最多只有一个进程处于运行态。
3. **阻塞态（Blocked/Waiting）**：进程因等待某事件（如 I/O 完成、收到消息、获取锁）而暂停执行，即使给它 CPU 也无法继续运行。

**合法的状态转换：**

```
就绪 ──(调度程序分配CPU)──→ 运行
运行 ──(时间片用完)──────→ 就绪
运行 ──(等待事件，如I/O)──→ 阻塞
阻塞 ──(事件完成)────────→ 就绪
```

**四种转换中，只有"就绪 → 阻塞"是不合法的**，因为就绪态进程不缺任何资源（只缺 CPU），不可能去等待事件。一个进程必须先运行，才能提出 I/O 请求等需要阻塞的操作。

**初学易错点：**
- 容易混淆"等待 CPU"（就绪态）和"等待事件"（阻塞态）。就绪态是"万事俱备，只欠 CPU"；阻塞态是"条件不满足，给了 CPU 也白给"。
- 时间片用完不会让进程进入阻塞态，只是让它回到就绪队列尾部继续排队。
- 阻塞式系统调用（如 `read()`）完成后，进程进入就绪态而非运行态——它还要等待调度程序分配 CPU。

### 例题

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：若当前进程因时间片用完而让出处理机时，该进程应转变为（ ）状态。

A. 就绪
B. 等待
C. 运行
D. 完成

**解答**：

进程正在 CPU 上运行时，时间片用完意味着该进程本次使用 CPU 的配额已耗尽，但进程本身并不缺少任何其他资源，也没有在等待任何 I/O 事件。因此：
- 它不能继续留在**运行态**（CPU 已被收回）
- 它没有在等待 I/O 或消息，所以不是**等待/阻塞态**
- 它没有执行完毕，所以不是**完成态**

正确的去向是回到**就绪队列**，等待下一次被调度程序选中。因此应转变为**就绪态**（选项 A）。

**解析**：时间片轮转调度中，每个进程获得一个固定长度的时间片，用完即被剥夺 CPU，但进程本身一切正常，只是"轮到别人了"。这种"运行 → 就绪"的转换是分时系统的基础机制。

**例题 2（来自：作业2_进程管理.pdf）**

**题目**：下列进程状态的转换中，哪一个是不正确的（ ）

A. 就绪 → 运行
B. 运行 → 就绪
C. 就绪 → 阻塞

**解答**：

检查各个转换的合法性：

- **A（就绪 → 运行）**：合法。调度程序从就绪队列中选中一个进程，分配 CPU，它就进入运行态。这是最常见的转换。
- **B（运行 → 就绪）**：合法。时间片用完或更高优先级进程抢占时，正在运行的进程被剥夺 CPU，回到就绪态。
- **C（就绪 → 阻塞）**：**不合法**。就绪态的进程唯一的特征是"等待 CPU"，它没有在运行，因此不可能执行任何需要阻塞的系统调用（如 `read()`、`wait()`）。只有**运行态**的进程才能提出 I/O 请求并进入阻塞态。

因此不正确的转换是 **C**。

**解析**：记忆技巧——阻塞态只能从运行态进入，因为只有正在执行的代码才能"请求服务然后等待"。

当一个进程处于（ ）状态时，称其为"等待"或"阻塞"状态。

A. 它正等待中央处理机
B. 它正等待合作进程的一个消息返回
C. 它正等待分给它一个时间片

> 阻塞态的核心定义：进程因等待某一事件（I/O 完成、消息到达、锁释放等）而无法继续执行。

## 考点 2：用户态与内核态

### 考点讲解

**双模式设计（Dual Mode）：**

操作系统为了自我保护，将 CPU 的执行模式分为两种：

| 模式 | 别名 | 权限 | 执行内容 |
|------|------|------|----------|
| **用户态** | 目态（User Mode） | 受限 | 用户程序 |
| **内核态** | 管态/核心态（Kernel Mode） | 完全 | 操作系统内核 |

**特权指令与非特权指令：**
- **特权指令**：只能在**内核态**执行的指令，如：关中断、设置时钟、清内存、修改页表基址、切换进程状态等。如果用户态程序尝试执行，CPU 会触发异常（trap），由操作系统处理。
- **非特权指令**：用户态也可以执行的指令，如：算术运算、逻辑运算、跳转指令、压栈/出栈、函数调用等。

**从用户态切换到内核态的三种途径：**

| 途径 | 触发方式 | 举例 |
|------|----------|------|
| **系统调用** | 用户程序主动请求 | `read()`、`write()`、`fork()` |
| **异常** | 程序运行错误 | 除零、缺页、非法指令 |
| **中断** | 外部设备信号 | 时钟中断、I/O 中断 |

**中断处理 vs 子程序调用：**

| 对比项 | 子程序调用 | 中断处理 |
|--------|-----------|----------|
| 保存 PC | ✅ | ✅ |
| 保存 PSW（程序状态字） | ❌ | ✅ |
| 保存通用寄存器 | 视需要 | ✅ |
| 切换模式 | 不切换（用户态→用户态） | 用户态→内核态 |

中断处理必须保存**程序状态字寄存器（PSW）**，因为中断会改变 CPU 的执行模式（用户态→内核态），返回时需要恢复原来的 PSW 以回到用户态。而子程序调用在同一模式内进行，模式不变，因此不需要保存 PSW。

**初学易错点：**
- 所有系统调用都会导致用户态→内核态切换，但普通库函数调用（如 `sin()`）不会——库函数在用户态执行。
- 关中断指令是典型的特权指令，用户态不可执行。

### 例题

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：下列指令中，不能在用户态执行的是（ ）

A. trap 指令
B. 跳转指令
C. 压栈指令
D. 关中断指令

**解答**：

逐项分析：
- **A（trap 指令）**：trap 是"陷入指令"，用户程序通过它主动陷入内核发起系统调用。trap 指令本身是**可以在用户态执行**的——执行 trap 后 CPU 自动切换到内核态。❌ 不是本题答案。
- **B（跳转指令）**：普通的程序跳转（如 `jmp`、`call`），属于非特权指令，用户态完全可以执行。❌
- **C（压栈指令）**：`push` 等栈操作属于基本数据操作，用户态可以执行。❌
- **D（关中断指令）**：关中断会屏蔽外部中断信号，如果用户程序能关中断，它将霸占 CPU 不被时钟中断打断，破坏分时系统的公平性。因此**关中断是特权指令**，只能在**内核态**执行。✅

**答案**：D

**解析**：判断指令能否在用户态执行的核心标准是——这条指令如果被用户程序滥用，是否会破坏系统的稳定性或安全性。关中断、设置定时器、修改页表等都属于特权指令。

**例题 2（来自：作业2_进程管理.pdf）**

**题目**：中断处理和子程序调用都需要压栈以保护现场，中断处理一定会保存而子程序调用不需要保存的是（ ）

A. 程序计数器
B. 程序状态字寄存器
C. 通用数据寄存器
D. 通用地址寄存器

**解答**：

- **程序计数器（PC）**：中断处理和子程序调用**都需要保存**，因为返回后都需知道从哪条指令继续执行。
- **程序状态字寄存器（PSW）**：记录 CPU 的状态（当前模式、中断标志位等）。中断处理涉及**用户态→内核态**的模式切换，返回时必须恢复原来的 PSW，所以**必须保存**。子程序调用不切换模式，PSW 不变，**不需要保存**。
- **通用数据寄存器 / 通用地址寄存器**：中断处理和子程序调用都可能需要保存（取决于调用约定），但题目问的是"一定会保存"且"子程序调用不需要保存"的区别项。

**答案**：B

**解析**：程序状态字（PSW）寄存器存有当前 CPU 模式位（用户态/内核态）。中断会切换模式，所以必须保存和恢复 PSW；子程序调用在同一模式下进行，PSW 不变，无需保存。

## 考点 3：进程调度 — 周转时间计算

### 考点讲解

**周转时间（Turnaround Time）** 是评价调度算法的重要指标：

$$\text{周转时间} = \text{完成时间} - \text{提交时间}$$

当所有作业同时到达时，周转时间 = 完成时间（因为提交时间为 0）。

$$\text{平均周转时间} = \frac{\sum \text{各作业周转时间}}{\text{作业数量}}$$

**常见调度算法：**

1. **先来先服务（FCFS）**：按到达顺序执行。简单但短作业可能等待很久（ convoy effect 护卫效应）。
2. **最短作业优先（SJF / SPF）**：优先执行预计运行时间最短的作业。能最小化平均周转时间，但可能导致长作业饥饿。
3. **优先级调度（Priority Scheduling）**：按优先级执行，优先级高的先运行。
4. **时间片轮转（RR - Round Robin）**：每个进程分配一个时间片，轮流执行，适合分时系统。

**计算周转时间的步骤（以 SJF / 优先级调度为例）：**

1. 按调度规则确定各作业的执行顺序。
2. 依次计算每个作业的完成时间 = 前一个作业的完成时间 + 当前作业的运行时间。
3. 每个作业的周转时间 = 完成时间 − 提交时间。
4. 将所有周转时间相加，除以作业数，得到平均周转时间。

**注意**：当作业不同时到达时，SJF 的选法是在每次 CPU 空闲时，从**已到达**的作业中选择最短的。

### 例题

**例题 1：优先级调度（来自：作业2_进程管理.pdf）**

**题目**：有 6 个 CPU 密集型批处理作业 A、B、C、D、E 和 F，几乎同时被提交。预计运行时间分别为 12、6、2、4、8 和 2 分钟。忽略进程切换的开销。设进程优先级分别为 4、6、3、2、5 和 1，其中 1 为最高优先级。则采用优先级调度算法，平均进程周转时间为（ ）

A. 16.33 分钟
B. 14.33 分钟
C. 14 分钟
D. 23.33 分钟

**解答**：

**第一步**：按优先级排序（数字越小优先级越高）。

| 作业 | 运行时间 | 优先级 |
|------|----------|--------|
| F | 2 | 1（最高） |
| D | 4 | 2 |
| C | 2 | 3 |
| A | 12 | 4 |
| E | 8 | 5 |
| B | 6 | 6（最低） |

**第二步**：按优先级从高到低的顺序执行，计算每个作业的完成时间。因为作业几乎同时到达，周转时间 = 完成时间（提交时间视为 0）。

- F运行2分钟，完成时间 = 0 + 2 = 2
- D运行4分钟，完成时间 = 2 + 4 = 6
- C运行2分钟，完成时间 = 6 + 2 = 8
- A运行12分钟，完成时间 = 8 + 12 = 20
- E运行8分钟，完成时间 = 20 + 8 = 28
- B运行6分钟，完成时间 = 28 + 6 = 34

**第三步**：计算平均周转时间。

| 作业 | 周转时间（分钟） |
|------|:--------------:|
| F | 2 |
| D | 6 |
| C | 8 |
| A | 20 |
| E | 28 |
| B | 34 |
| **总和** | **98** |

$$\text{平均周转时间} = \frac{98}{6} \approx 16.33 \text{分钟}$$

**答案**：A

**解析**：优先级调度按优先级顺序依次执行，不抢占（因为是批处理作业，不考虑抢占）。每个作业的周转时间 = 它前面所有作业的运行时间之和 + 它自己的运行时间。

**例题 2：SJF 作业调度（不同时到达）（来自：作业2_进程管理.pdf）**

**题目**：假定在单道批处理环境下有 5 个作业，各作业进入系统的时间和估计运行时间如下表所示。如果应用最短作业优先的作业调度算法，则作业的平均周转时间为（ ）分钟。

| 作业 | 进入系统时间 | 估计运行时间(分钟) |
|:---:|:----------:|:----------------:|
| 1 | 8:00 | 40 |
| 2 | 8:20 | 30 |
| 3 | 8:30 | 12 |
| 4 | 9:00 | 18 |
| 5 | 9:10 | 5 |

**解答**：

在单道批处理环境中，内存中最多只有一个作业。SJF 的策略是：**每当 CPU 空闲时，从当前已到达的作业中选择运行时间最短的**。

**第 1 步**：8:00，只有作业 1 到达。运行作业 1（40 分钟）。
- 时间段：8:00 ~ 8:40
- 作业 1 完成

**第 2 步**：8:40，CPU 空闲。此时已到达的作业有：作业 2（8:20 到达，30 分钟）、作业 3（8:30 到达，12 分钟）。选择最短的——作业 3（12 分钟）。
- 时间段：8:40 ~ 8:52

**第 3 步**：8:52，CPU 空闲。此时已到达的作业有：作业 2（30 分钟）。作业 4 和 5 尚未到达（9:00 和 9:10）。只能运行作业 2（30 分钟）。
- 时间段：8:52 ~ 9:22

**第 4 步**：9:22，CPU 空闲。此时已到达的作业有：作业 4（9:00 到达，18 分钟）、作业 5（9:10 到达，5 分钟）。选择最短的——作业 5（5 分钟）。
- 时间段：9:22 ~ 9:27

**第 5 步**：9:27，CPU 空闲。此时剩余作业 4（18 分钟）。运行之。
- 时间段：9:27 ~ 9:45

**第 6 步**：计算各作业的周转时间（完成时间 − 进入时间）：

| 作业 | 完成时间 | 进入时间 | 周转时间 |
|:---:|:--------:|:--------:|:--------:|
| 1 | 8:40 | 8:00 | 40 分钟 |
| 2 | 9:22 | 8:20 | 62 分钟 |
| 3 | 8:52 | 8:30 | 22 分钟 |
| 4 | 9:45 | 9:00 | 45 分钟 |
| 5 | 9:27 | 9:10 | 17 分钟 |

$$\text{平均周转时间} = \frac{40 + 62 + 22 + 45 + 17}{5} = \frac{186}{5} = 37.2 \text{分钟}$$

**解析**：本题关键点在于**作业并非同时到达**，每次调度时只能从已到达的作业中选择。作业 5 虽然运行时间最短（5 分钟），但 9:10 才到达，因此不能优先于作业 3 执行。

## 考点 4：调度算法特性（饥饿、时间片、优先级）

### 考点讲解

**饥饿现象（Starvation）：**

饥饿是指一个进程**无限期地等待**而得不到 CPU 调度。与死锁不同，饥饿的进程没有被阻塞，它一直在就绪队列中，但调度算法一直不选它。

常见导致饥饿的算法：
- **优先级调度**：低优先级进程可能永远得不到 CPU（如果有源源不断的高优先级进程进入系统）。
- **最短作业优先（SJF）**：长作业可能永远被短作业抢占/优先，产生饥饿。
- **非抢占式 SJF**：长作业等待时间极长，但最终会执行，严格说不算"无限期"饥饿。

不导致饥饿的算法：
- **时间片轮转（RR）**：每个进程轮流获得时间片，保证每个进程都能推进。
- **先来先服务（FCFS）**：按到达顺序执行，每个作业最终都会轮到。
- **高响应比优先（HRRN）**：响应比 = (等待时间 + 估计运行时间) / 估计运行时间，等待时间越长优先级自然提升，不会饥饿。

**时间片的选择：**
- 时间片过小 → 频繁的上下文切换，系统开销大，CPU 有效利用率低。
- 时间片过大 → 退化为 FCFS，交互响应慢。
- 合理的分时系统时间片：**几十毫秒**（如 10ms ~ 100ms），既能保证交互响应，又能控制切换开销。

**进程优先级的调整时机：**
- **降低优先级**的合理时机：进程的时间片用完（说明它已经获得了 CPU 时间，应礼让其他进程）。
- **提高优先级**的合理时机：进程刚完成 I/O 进入就绪队列（I/O 密集型进程应尽快获得 CPU 以便发起下一次 I/O）；进程长时间处于就绪队列（避免饥饿）。

**临界区与调度：**
- 进程在临界区（访问共享资源的代码段）时，**可以进行处理机调度**。不要误以为临界区内不能调度——临界区只是对共享资源的互斥访问，CPU 调度是独立的机制。如果临界区内的进程被调度出去，它仍然持有锁，但这属于调度策略的权衡，不是禁止调度。

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：下列调度算法中，不可能导致饥饿现象的是（ ）

A. 时间片轮转
B. 静态优先级调度
C. 非抢占式作业优先
D. 抢占式短作业优先

**解答**：

逐项分析每种算法是否可能产生饥饿：

- **A（时间片轮转）**：每个进程轮流获得一个时间片，严格公平，所有进程都能推进，**不可能产生饥饿**。✅

**题目**：下列选项中，满足短任务优先且不会发生饥饿现象的调度算法是（ ）

A. 先来先服务

C. 时间片轮转
D. 非抢占式短任务优先

**解析**：高响应比优先（HRRN）是 SJF 的改进版，通过让"等待时间"成为响应比的分子，等待越久的进程优先级会自动提升，从而避免了饥饿。公式中的"估计运行时间"在分母上，体现了短任务优先的思想。

## 考点 5：进程同步与互斥

### 考点讲解

**进程同步（Synchronization）** 与 **进程互斥（Mutual Exclusion）** 是两种不同的制约关系：

| 概念 | 定义 | 举例 |
|------|------|------|
| **同步** | 多个进程因**合作**而产生的制约关系。一个进程需要等待另一个进程完成某事件或发来消息后才能继续执行。 | 生产者等待缓冲区不空（消费者已生产），消费者等待缓冲区不满（生产者已消费）。 |
| **互斥** | 多个进程因**竞争同一资源**而产生的制约关系。当一个进程使用临界资源时，其他进程必须等待。 | 多个进程竞争同一台打印机，一次只能有一个进程使用。 |

**可重入代码（Reentrant Code）/ 纯代码（Pure Code）：**

可以被多个进程在任意时刻共享的代码必须是**不能自身修改的代码**（即纯代码/可重入代码）。要求：
- 代码段是只读的，不会在运行中修改自身指令。
- 多个进程可以同时执行同一份代码副本（每个进程有各自的数据段和栈，但代码段共享）。
- 含有自修改功能的代码不能共享，因为一个进程的修改会影响其他进程的执行。

**初学易错点：**
- "互斥"和"同步"常被混淆。**互斥解决的是"竞争"问题**（资源不能同时用），**同步解决的是"协作"问题**（谁先谁后有要求）。
- 互斥是特殊的同步（通常是同步的一种实现手段），但两者不等价。

---

### 例题

**例题 1（来自：作业2_进程管理.pdf）**

A. 同步
B. 互斥
C. 调度
D. 执行

**解答**：

- **同步**：进程间因**合作**而产生的制约。一个进程等待另一个进程发出消息或满足条件才继续，这正是题目描述的场景。✅
- **互斥**：进程间因**竞争资源**而产生的制约（如同时访问共享变量），不是合作关系。❌
- **调度**：操作系统决定哪个进程获得 CPU 的机制，不是进程间的制约关系。❌
- **执行**：过于宽泛，不是专业术语。❌

**解析**：同步关系强调"协调步伐"——进程 A 需要在进程 B 完成某事后才能继续。典型的例子：读进程必须等写进程写入数据后才能读取；消费者必须等生产者生产后才能消费。题目中的"发来消息"和"建立条件"正是同步的典型场景。

## 考点 6：死锁

### 考点讲解

**死锁的四个必要条件（四个条件必须同时满足才会发生死锁）：**

| 条件 | 含义 |
|------|------|
| **互斥** | 资源一次只能被一个进程使用 |
| **持有并等待** | 进程持有至少一个资源，同时等待获取其他进程持有的资源 |
| **不可剥夺** | 已分配给进程的资源不能被强行剥夺，只能由持有者主动释放 |
| **循环等待** | 存在一个进程-资源的循环链，链中每个进程都在等待下一个进程持有的资源 |

**单实例资源 vs 多实例资源：**
- 如果每类资源只有 1 个实例，死锁的检测可以用**资源分配图**（有向图中有环 → 死锁）。
- 如果进程只申请 1 个资源，那么该进程永远不会参与循环等待（因为它不持有资源就等待，或者获取后就释放），因此不会成为死锁的一部分。

**死锁的预防、避免、检测与恢复：**

| 策略 | 方法 | 特点 |
|------|------|------|
| **预防** | 破坏四个必要条件之一 | 保守，可能降低资源利用率 |
| **避免** | 动态判断分配是否安全（银行家算法） | 需要预先知道最大需求 |
| **检测** | 允许死锁发生，定期检测 | 需要检测算法和恢复机制 |
| **恢复** | 终止进程或剥夺资源 | 代价高 |

**避免死锁的最小资源数公式：**

如果系统中有 $M$ 个并发进程，每个进程最多需要 $K$ 台同类资源，那么确保系统不会发生死锁的最少资源数为：

$$\text{最少资源数} = M \times (K - 1) + 1$$

推导思路：最坏情况下，每个进程都分配到 $K-1$ 台资源并等待第 $K$ 台。此时只要有 1 台空闲资源，就能让某个进程满足需求并执行完毕，释放其占有的所有资源。

### 例题

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：系统中有 3 个不同的临界资源 R1、R2 和 R3，被 4 个进程 P1、P2、P3 和 P4 共享。各进程对资源的需求为：P1 申请 R1 和 R2，P2 申请 R2 和 R3，P3 申请 R3，P4 申请 R2。若系统出现死锁，则处于死锁状态的进程数至少是（ ）

A. 1
B. 2
C. 3
D. 4

**解答**：

**第一步**：分析每个进程要多少资源才能完成。

| 进程 | 所需资源 | 说明 |
|:----:|:--------:|:----:|
| P1 | R1, R2 | 需要 2 个资源 |
| P2 | R2, R3 | 需要 2 个资源 |
| P3 | R3 | 只需要 1 个资源 |
| P4 | R2 | 只需要 1 个资源 |

**第二步**：分析哪些进程可以成为死锁的一部分。

死锁需要**循环等待**条件。P3 和 P4 各自只需要 1 个资源——这意味着只要它们获得该资源就能执行完毕并释放，不可能持有一个资源去等待另一个资源，因此它们**不能参与循环等待**。

只有 P1 和 P2 有可能参与循环等待（它们各需要 2 个资源，可能持有 1 个、等待另 1 个）。

**第三步**：构造死锁场景。

考虑以下资源分配状态：

- P1 持有 R1，等待 R2（R2 被 P2 持有）
- P2 持有 R2，等待 R3（R3 被 P3 持有，但 P3 只需要 R3，一旦获得就会完成）

由于 P3 只有 1 个需求（R3），当 R3 分配给 P3 后 P3 立即完成并释放 R3，因此 P3 不会导致死锁。

P4 同理——它只需要 R2，一旦获得即完成。

因此 P1 和 P2 之间的"持有并等待"无法形成闭环，死锁在此系统中实际上不可能发生——因为任何进程要么获得资源后立即完成，要么即使形成 P1→R2→P2→R3 的链条，R3 最终会被 P3 释放。

**但题目假设"若系统出现死锁"**，则最可能的死锁场景需要**至少 2 个进程**参与循环等待（这是形成循环等待的最小规模）。

**答案**：B（2 个）

**解析**：死锁的最少进程数是 2——任何死锁都必须满足循环等待条件，而循环等待至少需要 2 个进程才能形成。单个进程不可能自己死锁自己（除非它等待自己已经占有的资源，这在逻辑上不会发生）。

**例题 2（来自：作业2_进程管理.pdf）**

**题目**：若系统 S1 采用死锁避免方法，S2 采用死锁检测方法，下列叙述中正确的是（ ）

Ⅰ．S1 会限制用户申请资源的顺序
Ⅱ．S1 需要进程提供所需资源总量信息，而 S2 不需要
Ⅲ．S1 不会给可能导致死锁的进程分配资源，S2 会

A. 仅Ⅰ、Ⅱ
B. 仅Ⅱ、Ⅲ
C. 仅Ⅰ、Ⅲ

**解答**：

- **Ⅰ（S1 会限制用户申请资源的顺序）**：❌ 死锁避免（银行家算法）**不限制申请顺序**，只会在每次分配前判断分配后是否处于安全状态。限制申请顺序是**死锁预防**（破坏循环等待条件）的做法。
- **Ⅱ（S1 需要资源总量信息，S2 不需要）**：✅ 银行家算法需要知道每个进程的**最大资源需求量**来判断分配是否安全。死锁检测不需要这个信息，它只在死锁发生后通过资源分配图来检测。
- **Ⅲ（S1 不会给可能导致死锁的进程分配资源，S2 会）**：✅ 死锁避免在分配前做安全性检查，如果不安全就拒绝分配。死锁检测允许分配（不管是否可能死锁），然后定期检查是否真的发生了死锁。

**答案**：B（仅Ⅱ、Ⅲ）

**解析**：区分"预防""避免""检测"三个概念：
- **预防**：通过破坏死锁条件来杜绝死锁（如限制申请顺序、一次性分配所有资源等）——保守。
- **避免**：动态判断每次分配的安全性（银行家算法）——需要最大需求信息。
- **检测**：允许死锁发生，发生后处理——不需要最大需求信息，但需要恢复机制。

**练习 1（来自：作业2_进程管理.pdf）**

某系统有 $N$ 台互斥使用的同类设备，$M$ 个并发进程，每个进程最多需要 $K$ 台设备。可确保系统不会发生死锁的设备数 $N$ 最少为（ ）

A. 9
B. 10
C. 11
D. 12

> [!question]- 点击查看完整解答
> **答案**：B（10）
>
> **解析**：
> 本题使用"死锁避免最小资源数"公式：$N_{\min} = M \times (K - 1) + 1$
>
> 假设 3 个进程，每个最多需要 4 台设备（常见经典题目配置），则：
> $$N_{\min} = 3 \times (4 - 1) + 1 = 3 \times 3 + 1 = 10$$
>
> **推导逻辑**：最坏情况下，每个进程都分配到 $K-1=3$ 台设备，此时共分配到 $3 \times 3 = 9$ 台。只要还有 1 台空闲设备（第 10 台），就能让某个进程得到第 $K$ 台设备并执行完毕，释放其持有的全部设备，从而打破死锁。
>
> 如果只有 9 台，每个进程各 3 台，全部等待第 4 台，就陷入了死锁。

## 考点 7：银行家算法

### 考点讲解

**银行家算法（Banker's Algorithm）** 是 Dijkstra 提出的死锁避免算法。其核心思想：每次分配资源前，模拟分配后的状态，判断系统是否处于**安全状态**——即是否存在一个**安全序列**，使得所有进程都能依次执行完毕。

**数据结构：**

| 符号 | 含义 |
|:----:|:----:|
| $n$ | 进程数 |
| $m$ | 资源类型数 |
| $\text{Available}[m]$ | 当前可用资源数量 |
| $\text{Max}[n][m]$ | 每个进程的最大资源需求 |
| $\text{Allocation}[n][m]$ | 每个进程已分配的资源数量 |
| $\text{Need}[n][m]$ | 每个进程还需要的资源数量 = $\text{Max} - \text{Allocation}$ |
| $\text{Request}[i][m]$ | 进程 $i$ 当前请求的资源数量 |

**安全性检查算法步骤：**

1. 将 $\text{Available}$ 视为当前可用资源。
2. 找一个未完成的进程 $i$，使得 $\text{Need}[i] \leq \text{Available}$（各维度都满足）。
3. 假设该进程完成，释放其所有资源：$\text{Available} = \text{Available} + \text{Allocation}[i]$。
4. 重复 2-3，直到所有进程都完成（安全）或找不到符合条件的进程（不安全）。

**资源请求的处理流程：**

1. 检查 $\text{Request}[i] \leq \text{Need}[i]$？若不满足，请求非法（超过最大声明）。
2. 检查 $\text{Request}[i] \leq \text{Available}$？若不满足，资源不足，进程等待。
3. **试探性分配**：
   - $\text{Available} = \text{Available} - \text{Request}[i]$
   - $\text{Allocation}[i] = \text{Allocation}[i] + \text{Request}[i]$
   - $\text{Need}[i] = \text{Need}[i] - \text{Request}[i]$
4. 执行**安全性检查**。如果安全，正式分配；否则回滚分配，进程等待。

**初学易错点：**
- 安全状态 ≠ 无死锁？**安全状态一定无死锁**，但**不安全状态不一定有死锁**（可能只是有风险）。
- 银行家算法是**死锁避免**，不是**预防**——它不破坏死锁条件，而是避免进入不安全状态。
- 计算时注意看清楚优先级（小/大表示高优先级）和资源维度（各维度需全部满足才算 $\text{Need} \leq \text{Available}$）。

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：设系统中有三种类型的资源 A、B、C，资源数量分别是 17、5、20，五个进程 P1、P2、P3、P4、P5。在 T0 时刻系统状态如下表所示，系统采用银行家算法实施死锁避免策略。在 T0 时刻若进程 P2 请求资源 (0, 3, 4)，是否能实施分配？为什么？

| 进程 | 最大需求(A,B,C) | 已分配(A,B,C) |
|:----:|:---------------:|:-------------:|
| P1 | (5, 5, 9) | (2, 1, 2) |
| P2 | (5, 3, 6) | (4, 0, 2) |
| P3 | (4, 0, 11) | (4, 0, 2) |
| P4 | (4, 2, 5) | (2, 0, 4) |
| P5 | (4, 2, 4) | (3, 1, 4) |

A. 不可以，因为无足够资源完成分配。
B. 不可以，因为分配后进入不安全状态。
C. 可以，分配后存在安全序列 P4→P2→P5→P3→P1。
D. 可以，分配后存在安全序列 P2→P5→P4→P1→P3。

**解答**：

**第 1 步**：计算当前可用资源和各进程的 Need 矩阵。

总资源：$A = 17,\ B = 5,\ C = 20$

已分配之和：
- A：$2 + 4 + 4 + 2 + 3 = 15$
- B：$1 + 0 + 0 + 0 + 1 = 2$
- C：$2 + 2 + 2 + 4 + 4 = 14$

当前可用 $\text{Available} = (17-15,\ 5-2,\ 20-14) = (2, 3, 6)$

各进程的 $\text{Need} = \text{Max} - \text{Allocation}$：

| 进程 | Need (A, B, C) |
|:----:|:--------------:|
| P1 | $(5-2,\ 5-1,\ 9-2) = (3, 4, 7)$ |
| P2 | $(5-4,\ 3-0,\ 6-2) = (1, 3, 4)$ |
| P3 | $(4-4,\ 0-0,\ 11-2) = (0, 0, 9)$ |
| P4 | $(4-2,\ 2-0,\ 5-4) = (2, 2, 1)$ |
| P5 | $(4-3,\ 2-1,\ 4-4) = (1, 1, 0)$ |

**第 2 步**：检查 P2 的请求 $(0, 3, 4)$。

① 检查是否 $\text{Request} \leq \text{Need}$：$(0,3,4) \leq (1,3,4)$ ✅
② 检查是否 $\text{Request} \leq \text{Available}$：$(0,3,4) \leq (2,3,6)$ ✅

**第 3 步**：试探性分配。

若分配，则：
- 新分配量 $\text{Allocation}[2] = (4, 0, 2) + (0, 3, 4) = (4, 3, 6)$
- 新 $\text{Need}[2] = (1, 3, 4) - (0, 3, 4) = (1, 0, 0)$
- 新 $\text{Available} = (2, 3, 6) - (0, 3, 4) = (2, 0, 2)$

**第 4 步**：安全性检查。

可用资源 $\text{Available} = (2, 0, 2)$

| 进程 | Need | Allocation |
|:----:|:----:|:----------:|
| P1 | (3, 4, 7) | (2, 1, 2) |
| P2 | (1, 0, 0) | (4, 3, 6) |
| P3 | (0, 0, 9) | (4, 0, 2) |
| P4 | (2, 2, 1) | (2, 0, 4) |
| P5 | (1, 1, 0) | (3, 1, 4) |

寻找 Need ≤ Available 的进程：

- **P2**：$(1,0,0) \leq (2,0,2)$ ✅ → P2 完成，释放 $(4,3,6)$
  - 新 Available = $(2,0,2) + (4,3,6) = (6,3,8)$
- **P5**：$(1,1,0) \leq (6,3,8)$ ✅ → P5 完成，释放 $(3,1,4)$
  - 新 Available = $(6,3,8) + (3,1,4) = (9,4,12)$
- **P1**：$(3,4,7) \leq (9,4,12)$？B：$4 \leq 4$ ✅ → P1 完成，释放 $(2,1,2)$
  - 新 Available = $(9,4,12) + (2,1,2) = (11,5,14)$
- **P4**：$(2,2,1) \leq (11,5,14)$ ✅ → P4 完成，释放 $(2,0,4)$
  - 新 Available = $(11,5,14) + (2,0,4) = (13,5,18)$
- **P3**：$(0,0,9) \leq (13,5,18)$ ✅ → P3 完成

安全序列：**P2 → P5 → P1 → P4 → P3**（或 P2 → P5 → P4 → P1 → P3 也成立）

**答案**：D

**解析**：分配是可行的（资源足够且分配后系统处于安全状态）。选项 D 中的安全序列 P2→P5→P4→P1→P3 是可行的序列之一。银行家算法在分配前做"试探→检查安全→决定是否分配"，确保不会进入不安全状态。

**题目**：假设 5 个进程 P0、P1、P2、P3、P4 共享 3 类资源 R1、R2、R3，这些资源总数分别为 18、6、22。T0 时刻的资源分配情况如下表所示，此时存在安全序列是（ ）

| 进程 | 已分配资源(R1,R2,R3) | 资源最大需求(R1,R2,R3) |
|:----:|:-------------------:|:---------------------:|
| P0 | (3, 2, 3) | (5, 5, 10) |
| P1 | (4, 0, 3) | (5, 3, 6) |
| P2 | (4, 0, 5) | (4, 0, 11) |
| P3 | (2, 0, 4) | (4, 2, 5) |
| P4 | (3, 2, 4) | (4, 2, 4) |

A. P0, P2, P4, P1, P3
B. P1, P0, P3, P4, P2
C. P2, P1, P0, P3, P4
D. P3, P4, P2, P1, P0

**解答**：

**第 1 步**：计算 Available 和 Need。

总资源：$R1=18,\ R2=6,\ R3=22$

已分配之和：$R1=3+4+4+2+3=16$，$R2=2+0+0+0+2=4$，$R3=3+3+5+4+4=19$

$$\text{Available} = (18-16,\ 6-4,\ 22-19) = (2, 2, 3)$$

Need = Max − Allocation：

| 进程 | Need (R1,R2,R3) |
|:----:|:---------------:|
| P0 | (5-3, 5-2, 10-3) = (2, 3, 7) |
| P1 | (5-4, 3-0, 6-3) = (1, 3, 3) |
| P2 | (4-4, 0-0, 11-5) = (0, 0, 6) |
| P3 | (4-2, 2-0, 5-4) = (2, 2, 1) |
| P4 | (4-3, 2-2, 4-4) = (1, 0, 0) |

**第 2 步**：找安全序列。

Available = (2, 2, 3)

- **P1**：Need (1,3,3) ≤ (2,2,3)？B: $3 \leq 2$ ❌ 不行
- **P3**：Need (2,2,1) ≤ (2,2,3) ✅ → P3 完成

- **P4**：Need (1,0,0) ≤ (4,2,7) ✅ → P4 完成
  - 释放 (3,2,4)，新 Available = (4+3, 2+2, 7+4) = (7, 4, 11)
- **P1**：Need (1,3,3) ≤ (7,4,11) ✅ → P1 完成
  - 释放 (4,0,3)，新 Available = (7+4, 4+0, 11+3) = (11, 4, 14)

安全序列：**P3 → P4 → P1 → P2 → P0**（即选项 D）

## 考点 8：多道程序与并发执行

### 考点讲解

**多道批处理系统中提高效率的关键：CPU 与 I/O 重叠。**

当一个进程在进行 I/O 操作时，CPU 空闲——此时可以让另一个进程使用 CPU，实现 CPU 和 I/O 设备的**并行工作**。

**分析这类问题的步骤（画时间轴法）：**

1. 列出每个作业的 CPU 和 I/O 时间段。
2. 确定到达顺序和调度策略（通常是非抢占的，除非另有说明）。
3. 绘制 Gantt 图 / 时间轴，注意 CPU 和 I/O 设备是否可以同时被不同进程使用。
4. 在 CPU 空闲时（某个进程在 I/O），如果有其他进程需要 CPU，就安排它运行。
5. 计算完成时间和总耗时。

**典型约束：**
- 单 CPU 系统：同一时刻只能有一个进程使用 CPU。
- 单 I/O 设备：同一时刻只能有一个进程使用该 I/O 设备。
- 但 CPU 和 I/O 设备可以**同时工作**（不同进程分别占用 CPU 和 I/O）。

### 例题

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：一个多道批处理系统中仅有 P1 和 P2 两个作业，P2 比 P1 晚 5ms 到达。它们的计算和 I/O 操作顺序如下：

- P1：计算 60ms，I/O 80ms，计算 20ms
- P2：计算 120ms，I/O 40ms，计算 40ms

若不考虑调度和切换时间，则完成两个作业需要的时间最少是（ ）

A. 240ms
B. 260ms
C. 340ms
D. 360ms

**解答**：

**第 1 步**：整理各作业的时间段。

| 作业 | 时间段 1 | 时间段 2 | 时间段 3 |
|:----:|:--------:|:--------:|:--------:|
| P1 | 计算 60ms | I/O 80ms | 计算 20ms |
| P2 | 计算 120ms | I/O 40ms | 计算 40ms |

P2 比 P1 晚 5ms 到达。

**第 2 步**：绘制时间轴（非抢占调度，即正在执行的进程不会被中断）。

```
时间(ms)     P1              P2              CPU状态          I/O设备状态
0           到达             未到达           P1计算
0-5         P1计算           -               P1计算(5/60)
5           P1计算           P2到达           P1计算
5-60        P1计算           -               P1计算(55/60→完成)
60          P1开始I/O(80ms)  P2开始计算       P2计算            P1 I/O(80ms)
60-140      P1 I/O           P2计算(80/120)   P2计算            P1 I/O
140         P1 I/O完成       P2计算(80/120)   
140-180     P1需要计算20ms   P2计算继续       P2计算(40/120)    
180         P1还在等CPU      P2计算完成       P2开始I/O(40ms)   P2 I/O
180-200     P1计算20ms       P2 I/O(40ms)    P1计算            P2 I/O
200         P1完成           P2 I/O(20/40)
200-220     -                P2 I/O继续      CPU空闲            P2 I/O
220         P2 I/O完成       P2需要计算40ms
220-260     -                P2计算40ms      P2计算            -
260         P2完成
```

详细时间轴：

| 时间段 | 谁在用 CPU | 谁在用 I/O |
|:------:|:----------:|:----------:|
| 0 ~ 60 | P1（计算） | — |
| 60 ~ 140 | P2（计算第 1 段） | P1（I/O） |
| 140 ~ 180 | P2（计算第 1 段，继续完成剩余 40ms） | — |
| 180 ~ 200 | P1（计算第 2 段，20ms） | P2（I/O） |
| 200 ~ 220 | — | P2（I/O 继续） |
| 220 ~ 260 | P2（计算第 2 段，40ms） | — |

**第 3 步**：验证各步骤。

- **0~60**：P1 到达（0ms），开始计算 60ms。P2 于 5ms 到达，但 CPU 被 P1 占用，等待。
- **60**：P1 计算完毕，开始 80ms I/O。此时 P2 开始使用 CPU 执行计算（120ms）。
- **60~140**：P1 进行 I/O，P2 进行计算（使用了 80ms CPU 时间，剩余 40ms）。**CPU 和 I/O 并行工作**。
- **140**：P1 的 I/O 完成（60+80=140），P1 需要 20ms 计算。但 P2 仍在用 CPU（它从 60 开始计算，到 140 时运行了 80ms，还剩 40ms）。
- **140~180**：P2 继续用完剩余 40ms 计算时间（总共 120ms）。P1 等待 CPU。
- **180**：P2 计算完毕，开始 40ms I/O。P1 获得 CPU，开始最后 20ms 计算。
- **180~200**：P1 计算（20ms）与 P2 I/O（40ms）**并行**。
- **200**：P1 计算完毕，作业 P1 完成。P2 的 I/O 仍在进行（已 20ms，还需 20ms）。
- **200~220**：CPU 空闲，P2 继续 I/O（共 40ms，到 220 完成）。
- **220**：P2 I/O 完成，开始最后 40ms 计算。
- **220~260**：P2 计算 40ms。
- **260**：P2 完成。

总耗时：**260ms**。

**答案**：B

**解析**：关键技巧是让 P1 的 I/O 与 P2 的 CPU 计算重叠，以及 P2 的 I/O 与 P1 的最后一段计算重叠。通过合理的非抢占调度（先运行先到达的 P1，P1 I/O 时切换 P2），最大限度地利用 CPU 和 I/O 设备的并行能力。若不考虑重叠（如单道程序顺序执行），总时间将是 $60+80+20+120+40+40=360$ms（选项 D），多道批处理节省了约 100ms。

### 练习

**练习 1（来自：作业2_进程管理.pdf）**

某单 CPU 系统中有输入和输出设备各 1 台，现有 3 个并发执行的作业，每个作业的输入、计算和输出时间均分别为 2ms、3ms 和 4ms，且都按输入、计算、输出的顺序执行，则执行完 3 个作业需要的时间最少是（ ）

A. 15ms
B. 17ms
C. 22ms
D. 27ms

> [!question]- 点击查看完整解答
> **答案**：B（17ms）
>
> **解析**：
>
> 三个作业 J1、J2、J3 各需要：输入(2ms) → 计算(3ms) → 输出(4ms)。
>
> **输入设备、CPU、输出设备三者在不同作业间可以流水线并行。**
>
> 时间轴：
>
> | 时间 | 输入设备 | CPU | 输出设备 |
> |:---:|:--------:|:---:|:--------:|
> | 0~2 | J1 输入 | — | — |
> | 2~4 | J2 输入 | J1 计算 | — |
> | 4~5 | J3 输入 | J1 计算(续) | — |
> | 5~6 | J3 输入(续) | J2 计算 | — |
> | 6~7 | — | J2 计算(续) | J1 输出 |
> | 7~8 | — | J3 计算 | J1 输出(续) |
> | 8~9 | — | J3 计算(续) | J2 输出 |
> | 9~10 | — | — | J2 输出(续) |
> | 10~11 | — | — | J3 输出 |
> | 11~13 | — | — | J3 输出(续) |
> | 13~16 | — | — | J3 输出(续) |
> | 16~17 | — | — | J3 输出(续) |
>
> 实际上更简洁的流水线分析：
> - 总输入时间：$3 \times 2 = 6$ms（输入设备串行使用）
> - 总计算时间：$3 \times 3 = 9$ms（CPU 串行使用）
> - 总输出时间：$3 \times 4 = 12$ms（输出设备串行使用）
>
> 但因为**三阶段可以重叠**，总时间 = 最慢设备的串行时间 + 前两阶段中其他设备的启动和结束开销。
>
> 流水线分析：
> - 开始阶段：J1 先输入 2ms → J1 计算 3ms（在此期间 J2 输入 2ms）→ ...
> - 结束阶段：最后一个作业的输出结束才完成。
>
> 具体计算：
> 0~2: J1 输入
> 2~4: J1 计算 + J2 输入
> 4~5: J1 计算 (第 3ms，总计算量中最后 1ms) + J2 输入 (最后 1ms，进入第 3ms)+ J3 开始输入... 
>
> 其实更简单的方法：**流水线总时间 = 第一作业的输入 + 所有作业的计算 + 最后一作业的输出 = 2 + 9 + 4 = 15**。但需要考虑输入设备的瓶颈，以及计算和输出的重叠。
>
> 再仔细算：由于每个阶段都需要独占设备，实际上是三阶段流水线。
> - 阶段 1（输入）：0~2(J1), 2~4(J2), 4~6(J3) → 输入完成为时间 6
> - 阶段 2（计算）：J1 计算 2~5, J2 计算 5~8, J3 计算 8~11 → 计算完成为时间 11  
> - 阶段 3（输出）：J1 输出 5~9, J2 输出 9~13, J3 输出 13~17 → 输出完成为时间 17
>
> 最短总时间 = 17ms。
>
> 另一种分析：
> - 输入设备：从 0 到 6 连续使用
> - CPU：从 2 到 11 连续使用
> - 输出设备：从 5 到 17 连续使用
>
> 所有作业完成时间 = max(输入结束时间 + 计算 + 输出的最后完成时间) = 17ms。
>
> 要点：流水线重叠的关键是**输入设备、CPU、输出设备三者互不冲突，可各自并行处理不同作业**。

## 考点 9：进程与线程概念

### 考点讲解

**进程（Process）与线程（Thread）的区别：**

| 对比维度 | 进程 | 线程 |
|:--------:|:----:|:----:|
| **资源分配单位** | ✅ 是 | ❌ 不是 |
| **调度/分派单位** | 传统 OS 中是 | ✅ 引入线程后是 |
| **地址空间** | 独立（进程间隔离） | 共享所属进程的地址空间 |
| **系统开销** | 创建/切换开销大 | 创建/切换开销小 |
| **通信方式** | IPC（管道、消息队列等） | 直接读写共享变量 |
| **相互影响** | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |

**关键点：**
- **进程是资源分配的基本单位**，始终拥有独立的地址空间和系统资源，无论系统是否支持线程。
- **线程是 CPU 调度的基本单位**（在支持线程的系统中），同一进程内的线程共享代码段、数据段、打开的文件等。
- 线程私有的资源：**栈指针、寄存器、线程局部存储（TLS）**。线程不共享彼此的栈空间。
- 用户级线程的切换在用户空间完成，**不需要内核支持**；内核级线程的切换需要内核支持。

**进程创建的场景：**
- 用户登录成功（如终端进程）
- 用户启动程序执行（如双击可执行文件、shell 执行命令）
- 操作系统创建（如系统服务进程）

**线程共享 vs 不共享的资源（同一进程内）：**

| 共享 | 不共享 |
|:----:|:------:|
| 代码段（.text） | 栈（每个线程有自己的栈） |
| 全局变量（.data/.bss） | 寄存器（每个线程有自己的寄存器副本） |
| 堆（动态分配的内存） | 线程 ID |
| 打开的文件描述符 | 栈指针（SP） |
| 信号处理函数 | 错误码（errno） |
| 当前工作目录 | 信号屏蔽字 |

**可重入/纯代码（Pure Code）：**
可以被多个进程在任意时刻共享的代码必须是**不能自身修改的代码**（纯代码/可重入代码）。代码段一旦加载到内存中就不再改变，多个进程可以同时执行同一份代码副本。

### 例题

**例题 1（来自：作业2_进程管理.pdf）**

**题目**：下面关于线程的叙述中，正确的是（ ）

A. 不论是系统支持线程还是用户级线程，其切换都需要内核的支持。
B. 线程是资源的分配单位，进程是调度和分配的单位。
C. 不管系统中是否有线程，进程都是拥有资源的独立单位。
D. 在引入线程的系统中，进程仍是资源分配和调度分派的基本单位。

**解答**：

逐项分析：

- **A**：用户级线程的切换在用户空间完成（通过线程库在用户态保存/恢复寄存器），不需要内核支持。只有内核级线程的切换需要内核。❌
- **B**：说法颠倒了。进程是资源分配单位，线程是调度单位（在支持线程的系统中）。❌
- **C**：正确。进程始终是资源的拥有者——即使系统中引入了线程，资源（地址空间、文件描述符等）也是分配给进程的，线程只共享这些资源。✅
- **D**：引入线程后，**调度分派的基本单位是线程**，不是进程（进程仍然是资源分配的基本单位）。❌

**答案**：C

**解析**：记住一个核心区分——**资源归进程，调度归线程**。进程负责"有什么资源"（地址空间、文件等），线程负责"执行到哪里了"（PC、栈、寄存器）。

**练习 3（来自：作业2_进程管理.pdf）**

关于进程和线程对共享变量的访问，以下叙述中正确的是（ ）

Ⅰ．同一进程内的多个线程共享该进程的全局变量
Ⅱ．不同进程的地址空间相互独立，一个进程的变量不会被另一进程的线程直接访问
Ⅲ．多个线程同时写同一个共享变量而不加同步，可能导致不确定的结果

A. 仅Ⅰ、Ⅱ
B. 仅Ⅱ、Ⅲ
C. Ⅰ、Ⅱ和Ⅲ
D. 仅Ⅰ

> [!question]- 点击查看完整解答
> **答案**：C
>
> **解析**：
> - **Ⅰ**：正确。同一进程内的所有线程共享进程的代码段、全局变量和堆空间。✅
> - **Ⅱ**：正确。每个进程有独立的地址空间，进程之间互不干扰（除非通过共享内存等 IPC 机制特意共享）。✅
> - **Ⅲ**：正确。当多个线程并发读写同一共享变量而不加锁时，由于**读-改-写**操作不是原子的，会导致**竞争条件（race condition）**，最终结果取决于线程交错执行的具体顺序，因此是不确定的。✅
>
> 核心考点：多线程并发访问共享变量时必须同步（如使用互斥锁、信号量），否则会出现 race condition。
