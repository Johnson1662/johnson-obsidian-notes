## 1约束与触发器 (Constraints & Triggers)

### 1.1 数据库完整性概述

**数据库完整性**是指数据的正确性和相容性。

- **正确性**：数据符合现实世界语义，反映当前实际状况。
  - 例如：学生的学号必须唯一；性别只能是男或女；成绩取值范围为 0~100。
- **相容性**：同一对象在不同关系表中的数据符合逻辑。
  - 例如：学生所选课程必须是学校开设的课程；学生所在院系必须是学校已成立的院系。

为维护数据库完整性，DBMS 必须：

- 提供定义完整性约束条件的机制（SQL 数据定义语言实现）
- 完整性约束条件包括：实体完整性、参照完整性、用户定义完整性

---

### 1.2 约束的种类 (Kinds of Constraints)

**约束 (Constraint)**：DBMS 必须强制执行的数据元素之间的关联关系。

| 约束类型               | 说明                                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| **键 (Keys)**          | 主键 (Primary Key)、唯一键 (Unique Key)，要求特定属性或属性组合的值具有唯一性 |
| **外键 (Foreign Key)** | 参照完整性 (Referential Integrity)，引用其他表的值                            |
| **基于属性的约束**     | 针对特定属性的值施加约束，如非空约束 (NOT NULL)                               |
| **基于元组的约束**     | 定义元组中各分量（属性）之间的关系                                            |
| **断言 (Assertions)**  | 基于任何 SQL 布尔表达式的全局约束                                             |

---

### 1.3 键与外键 (Keys and Foreign Keys)

#### 1.3.1 键约束 (Keys)

**单属性键**：在属性声明的数据类型之后直接放置 `PRIMARY KEY` 或 `UNIQUE` 关键字。

```sql
CREATE TABLE movieexec (
    name      CHAR(30),
    address   VARCHAR(255),
    cert      INT PRIMARY KEY,
    netWorth  INT
);
```

**多属性键**：使用表级约束，在 `PRIMARY KEY` 后指定属性列表。

```sql
CREATE TABLE movies (
    title       CHAR(100),
    year        INT,
    length      INT,
    genre       CHAR(10),
    studioName  CHAR(30),
    producerC   INT,
    PRIMARY KEY (title, year)
);
```

#### 1.3.2 外键约束 (Foreign Keys)

外键：出现在关系 S 的属性 p 中的值，必须同样存在于另一个关系 R 的属性 c 中。

**声明方式一：依附于属性（列级）**

```sql
CREATE TABLE movieexec (
    name      CHAR(30),
    address   VARCHAR(255),
    cert      INT PRIMARY KEY,
    netWorth  INT
);

CREATE TABLE studio (
    name      CHAR(50) PRIMARY KEY,
    address   VARCHAR(255),
    presC     INT REFERENCES movieexec(cert)
);
```

**声明方式二：作为模式元素（表级）**

```sql
CREATE TABLE studio (
    name      CHAR(50) PRIMARY KEY,
    address   VARCHAR(255),
    presC     INT,
    FOREIGN KEY (presC) REFERENCES movieexec(cert)
);
```

> 被参照的目标属性必须已被声明为 `PRIMARY KEY` 或 `UNIQUE`。

#### 1.3.3 外键违约处理

对参照方（studio）和被参照方（movieexec）的修改操作，违约处理方式不同：

| 操作   | studio（参照方）       | movieexec（被参照方） |
| ------ | ---------------------- | --------------------- |
| Delete | OK                     | 拒绝 / 级联 / 置空    |
| Insert | 拒绝（引用不存在的值） | OK                    |
| Update | 拒绝（引用不存在的值） | 拒绝 / 级联 / 置空    |

**三种处理策略**：

1. **默认策略 (Reject)**：拒绝修改操作
2. **级联策略 (Cascade)**：同步更改参照方的数据
   - 删除 movieexec 中 cert=123 的元组 → 自动删除 studio 中 presC=123 的所有元组
   - 更新 cert=345 为 346 → 自动更新 studio 中 presC=345 为 346
3. **置空策略 (Set NULL)**：将参照方的外键值设为 NULL

**指定策略的语法**：

```sql
CREATE TABLE studio (
    name      CHAR(50) PRIMARY KEY,
    address   VARCHAR(255),
    presC     INT REFERENCES movieexec(cert)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);
```

如不指定，默认采用 Reject 策略。

#### 1.3.4 约束延迟检查 (Deferred Checking)

**问题场景**：施瓦辛格创立 "La Vista" 制片厂并自任总裁，需要同时插入 studio 和 movieexec 两条记录。若先插入 studio，会因外键约束失败；若 studio.presC 设了 NOT NULL，也无法先插 NULL 再更新。

**解决方案：延迟检查**

将多个相关 SQL 语句组合成一个事务，告知 DBMS 等到事务提交前再统一检查约束。

```sql
CREATE TABLE Studio (
    name    CHAR(30) PRIMARY KEY,
    address VARCHAR(255),
    presC   INT REFERENCES MovieExec(cert)
        DEFERRABLE INITIALLY DEFERRED
);
```

**修饰符说明**：

| 修饰符                           | 说明                                         |
| -------------------------------- | -------------------------------------------- |
| `NOT DEFERRABLE`                 | 默认，每次执行修改语句后立即检查             |
| `DEFERRABLE INITIALLY DEFERRED`  | 可延迟，初始为延迟状态，事务提交前检查       |
| `DEFERRABLE INITIALLY IMMEDIATE` | 可延迟，但初始为立即检查，可在事务内改为延迟 |

**手动切换检查模式**：

```sql
SET CONSTRAINTS MyConstraint DEFERRED;    -- 改为延迟检查
SET CONSTRAINTS MyConstraint IMMEDIATE;    -- 改为立即检查
```

> 注意：循环约束（如 studio.presC 参照 movieexec.cert，同时 movieexec.cert 参照 studio.presC）无法通过调整步骤解决，必须使用延迟检查。

### 1.4 基于属性与元组的约束

#### 1.4.1 用户定义的完整性

用户定义的完整性是针对具体应用的数据必须满足的语义要求。

**属性上的约束**：

```sql
CREATE TABLE moviestar (
    name      CHAR(30) PRIMARY KEY,
    address   VARCHAR(255),
    gender    CHAR(1) CHECK (gender IN ('F', 'M', 'U')),
    birthdate CHAR(10)
);
```

```sql
CREATE TABLE studio (
    name    CHAR(50) PRIMARY KEY,
    address VARCHAR(255),
    presC   INT REFERENCES movieexec(cert) UNIQUE CHECK (presC >= 100000)
);
```

**CHECK 条件注意事项**：

- 可以引用本属性的名称（如 `CHECK (salary > 0)`）
- 如需引用其他关系表，需放在子查询中（部分数据库如 PostgreSQL 不支持在 CHECK 中使用子查询）
- `CHECK (presc IN (SELECT cert FROM movieexec))` 对 movieexec 的变更不可见，可能导致约束被破坏

#### 1.4.2 基于元组的检查 (Tuple-Based Checks)

CHECK 可作为关系模式级别的元素（与列定义平级），引用该关系的任何属性。

```sql
CREATE TABLE moviestar (
    name      CHAR(30) PRIMARY KEY,
    address   VARCHAR(255),
    gender    CHAR(1),
    birthdate CHAR(10),
    CHECK (gender = 'F' OR name NOT LIKE 'Ms.%')
);
```

**属性约束 vs 元组约束**：

| 约束类型     | 声明位置     | 触发时机         | 是否保证始终成立 |
| ------------ | ------------ | ---------------- | ---------------- |
| 属性级 CHECK | 依附于属性   | 插入或属性更新时 | 若含子查询则否   |
| 元组级 CHECK | 关系模式元素 | 插入或元组更新时 | 若含子查询则否   |

> 如果约束仅涉及一个属性，两者均可；若涉及多个属性，必须写为元组级约束。元组级约束检查更频繁，效率可能较低。

#### 7.4.3 断言 (Assertions)

断言是涉及多个表的更复杂的完整性约束，属于数据库级别的模式元素。

```sql
CREATE ASSERTION RichPres CHECK (
    NOT EXISTS (
        SELECT * FROM studio, movieexec
        WHERE presC = cert AND netWorth < 10000000
    )
);
```

业务规则：除非个人净资产至少为 10,000,000 美元，否则不得成为制片厂总裁。

**断言检查时机**：原则上每次对任何相关关系修改后都需检查，聪明的 DBMS 会优化为仅检查可能违反的修改。

**各类约束对比**：

| 约束类型         | 声明位置       | 触发时机             | 是否保证始终成立 |
| ---------------- | -------------- | -------------------- | ---------------- |
| 属性级 CHECK     | 依附于属性     | 插入或属性更新时     | 若含子查询则否   |
| 元组级 CHECK     | 关系模式元素   | 插入或元组更新时     | 若含子查询则否   |
| 断言 (Assertion) | 数据库模式元素 | 任何提及关系的变更后 | **是**           |

### 7.5 约束的修改

**命名约束**：

```sql
CREATE TABLE moviestar (
    name      CHAR(30) CONSTRAINT nameiskey PRIMARY KEY,
    address   VARCHAR(255),
    gender    CHAR(1) CONSTRAINT noandro CHECK (gender IN ('F', 'M')),
    birthdate CHAR(10),
    CONSTRAINT righttitle CHECK (gender = 'F' OR name NOT LIKE 'Ms.%')
);
```

**修改约束**：

```sql
-- 设置约束的延迟状态
SET CONSTRAINT constraintName DEFERRED;
SET CONSTRAINT constraintName IMMEDIATE;

-- 删除约束
ALTER TABLE relationName DROP CONSTRAINT constraintName;

-- 添加约束
ALTER TABLE relationName ADD CONSTRAINT constraintName CHECK(...);
```

> 注意：动态添加的约束必须能与元组关联（如元组级约束、主键、外键）。添加时表中每一行都必须满足新约束，否则添加失败。

### 7.6 触发器 (Triggers)

#### 7.6.1 触发器概述

触发器 (Trigger) 是事件-条件-动作 (Event-Condition-Action, ECA) 规则：

- **事件 (Event)**：对特定关系的 INSERT、DELETE 或 UPDATE 操作
- **条件 (Condition)**：SQL 布尔表达式，若不满足则不执行动作
- **动作 (Action)**：任意序列的 SQL 语句

**触发时机**：

- **BEFORE**：在操作尝试之前、检查表约束之前执行
- **AFTER**：在操作完成、约束检查之后执行
- **INSTEAD OF**：替代操作，专门用于视图

**触发粒度**：

- **行级触发器 (FOR EACH ROW)**：每修改一行执行一次，可引用 OLD/NEW 值
  - INSERT 不能引用 OLD，DELETE 不能引用 NEW
- **语句级触发器 (FOR EACH STATEMENT)**：整条 SQL 语句只执行一次

#### 7.6.2 触发器示例

**示例1：防止净资产变小（行级 AFTER 触发器）**

```sql
CREATE TRIGGER NetWorthTrigger
AFTER UPDATE OF netWorth ON MovieExec
REFERENCING
    OLD ROW AS OldTuple,
    NEW ROW AS NewTuple
FOR EACH ROW
WHEN (OldTuple.netWorth > NewTuple.netWorth)
BEGIN
    UPDATE MovieExec
    SET netWorth = OldTuple.netWorth
    WHERE cert = NewTuple.cert;
END;
```

**示例2：语句级触发器（检查整体平均净资产）**

```sql
CREATE TRIGGER AvgNetWorthTrigger
AFTER UPDATE OF netWorth ON MovieExec
REFERENCING
    OLD TABLE AS OldStuff,
    NEW TABLE AS NewStuff
FOR EACH STATEMENT
WHEN (500000 > (SELECT AVG(netWorth) FROM MovieExec))
BEGIN
    DELETE FROM MovieExec WHERE (cert, netWorth) IN (SELECT cert, netWorth FROM NewStuff);
    INSERT INTO MovieExec (SELECT * FROM OldStuff);
END;
```

**示例3：BEFORE 触发器（设置默认值）**

```sql
CREATE TRIGGER FixYearTrigger
BEFORE INSERT ON Movies
REFERENCING NEW ROW AS NewRow
FOR EACH ROW
WHEN NewRow.year IS NULL
BEGIN
    UPDATE NewStuff SET year = 1915;
END;
```

## 8. 视图与索引 (Views & Indexes)

### 8.1 虚拟视图 (Virtual Views)

**视图 (View)** 是由查询定义的"虚拟关系"，分为两种：

| 类型                        | 说明                                   |
| --------------------------- | -------------------------------------- |
| **虚拟视图 (Virtual)**      | 不存储，仅保存查询语句，查询时动态计算 |
| **物化视图 (Materialized)** | 实际计算并物理存储在数据库中           |

**声明视图**：

```sql
CREATE VIEW DisneyMovies AS
SELECT title, year
FROM Movies
WHERE studioName = 'Disney';
```

**查询视图**（像查询基表一样使用）：

```sql
SELECT title FROM DisneyMovies WHERE year = 1979;
```

等价于：

```sql
SELECT title FROM Movies WHERE studioName = 'Disney' AND year = 1979;
```

**多表视图示例**：

```sql
CREATE VIEW MovieProd(movieTitle, prodName) AS
SELECT title, name
FROM Movies, MovieExec
WHERE producerC = cert;
```

---

### 8.2 视图修改 (Modifying Views)

#### 可更新视图的条件

视图只有在满足以下条件时才可更新：

1. 定义时只能使用 SELECT，不能用 SELECT DISTINCT
2. FROM 子句中只能有一个基表（不能有 JOIN）
3. WHERE 子句中不能包含对本表的子查询
4. SELECT 选出的列必须足够多，未选中的列应有默认值或允许 NULL

#### 修改示例

**插入**：

```sql
CREATE VIEW DisneyMovies AS
SELECT title, year, studioName
FROM Movie WHERE studioName = 'Disney';

INSERT INTO DisneyMovies VALUES ('Star Trek', 1979, 'Disney');
```

**删除**：

```sql
DELETE FROM DisneyMovies WHERE title LIKE '%Trek%';
-- 等价于：DELETE FROM Movies WHERE title LIKE '%Trek%' AND studioName = 'Disney';
```

**更新**：

```sql
UPDATE DisneyMovies SET year = 2013 WHERE title = 'Frozen';
```

#### INSTEAD OF 触发器

虚拟视图本身不可直接修改，但可通过 INSTEAD OF 触发器拦截修改请求：

```sql
CREATE TRIGGER DisneyInsert
INSTEAD OF INSERT ON DisneyMovies
REFERENCING NEW ROW AS NewRow
FOR EACH ROW
BEGIN
    INSERT INTO Movies(title, year, studioName)
    VALUES(NewRow.title, NewRow.year, 'Disney');
END;
```

---

### 8.3 物化视图 (Materialized Views)

物化视图实际存储查询结果，适合频繁使用的场景。

```sql
CREATE MATERIALIZED VIEW MovieProd AS
SELECT title, year, name
FROM Movies, MovieExec
WHERE producerC = cert;
```

**维护策略**：

| 策略         | 说明                                         |
| ------------ | -------------------------------------------- |
| **增量维护** | 每次基表变化只做相应增量修改，最高效         |
| **完全重建** | 每次变化都完全重新计算，代价高昂             |
| **定期维护** | 定期（如每晚）重建，数据可能非实时但"足够好" |

**增量维护示例**：

- 在 Movie 中插入新电影 → 查找对应制片人，插入物化视图
- 从 Movie 中删除电影 → 从物化视图中删除对应行
- 更新 Movie 中电影信息 → 更新物化视图中对应行

**应用场景**：数据仓库（如沃尔玛夜间用当天销售数据更新数据仓库物化视图，供次日分析预测）。

---

### 8.4 SQL 中的索引 (Indexes in SQL)

**索引 (Index)**：一种数据结构，根据给定的属性值加快对关系中元组的访问速度。通常是 B 树 (B-tree)。

> 索引是"空间换时间"策略：事先构建存储，查询时直接定位。

**声明与删除**：

```sql
-- 声明索引
CREATE INDEX YearIndex ON Movies(year);
CREATE INDEX KeyIndex ON Movies(title, year);  -- 多属性索引

-- 删除索引
DROP INDEX YearIndex;
DROP INDEX KeyIndex;
```

**多属性索引**：属性的排列顺序至关重要。索引可用于查找第一个属性的特定值，但一般不能直接用于仅查找第二个属性。

**索引的作用**：

- 加速指定属性值的查询（如 `WHERE year = 1990`）
- 加速连接查询（如 Movies.title 和 MovieExec.cert 上都有索引时）

---

### 8.5 索引选择 (Selection of Indexes)

#### 权衡取舍

- **好处**：加速查询（尤其是主键查询、连接查询）
- **代价**：使插入、删除、更新操作更复杂耗时（每次修改需同步更新所有相关索引）

> 经验法则：数据修改的代价约是无索引查询的两倍。

#### 有用的索引

| 索引类型       | 适用场景                                                   |
| -------------- | ---------------------------------------------------------- |
| **主键索引**   | 最有用，主键查询非常普遍，最多读取一个磁盘页               |
| **近主键索引** | 属性值几乎唯一（如明星姓名），效果接近主键                 |
| **聚集索引**   | 元组按该属性物理聚集存放（如按年份聚集），连续块读取效率高 |

#### 成本模型

假设关系表存储在 N 个磁盘页中：

- **无索引**：全表扫描，成本 = N
- **主键索引**：最多读取 1 个页，成本 ≈ 1
- **非主键索引**：可能需读取少量几个页
- **聚集索引**：相关元组在连续块中，读取效率极高

#### 索引选择示例

假设 StarsIn(movieTitle, movieYear, starName) 共 10 个磁盘页，平均每位明星出演 3 部电影，每部电影有 3 位明星。

| 操作           | 无索引    | 仅明星索引 | 仅电影索引 | 双索引    |
| -------------- | --------- | ---------- | ---------- | --------- |
| Q1: 按明星查询 | 10        | 4          | 10         | 4         |
| Q2: 按电影查询 | 10        | 10         | 4          | 4         |
| I: 插入        | 2         | 4          | 4          | 6         |
| **总成本公式** | 2+8p1+8p2 | 4+6p2      | 4+6p1      | 6-2p1-2p2 |

- 若 p1=p2=0.1（查询少，插入多）→ 不建索引成本最低
- 若 p1=p2=0.4（查询频繁）→ 双索引成本最低
- 若 p1=0.5, p2=0.1（明星查询多）→ 仅建明星索引
- 若 p1=0.1, p2=0.5（电影查询多）→ 仅建电影索引

#### 自动索引调优

现代 DBMS 提供调优顾问（如微软 DTA），通过以下步骤自动选择索引：

1. 收集代表性查询负载
2. 生成候选索引集
3. 用查询优化器评估每个候选的成本收益
4. 贪心策略：每次选择增量收益最大的索引，直到无正向收益
