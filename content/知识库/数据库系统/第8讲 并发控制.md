## 8.1 并发控制概述

### 8.1.1 并发事务

**并发执行**：多个事务在同一时间段内并发执行

**为什么需要并发控制**？
1. 提高系统吞吐量
2. 减少用户等待时间
3. 充分利用系统资源

**并发带来的问题**：
- 丢失修改问题（Lost Update）
- 读"脏"数据问题（Dirty Read）
- 不可重复读问题（Non-repeatable Read）
- 幻读问题（Phantom Read）

### 8.1.2 并发控制的目标

1. **对于事务**：
   - 隔离事务执行，防止相互干扰
   - 保持数据库的一致性
   
2. **对于系统**：
   - 充分利用系统资源
   - 提高系统吞吐量

## 8.2 锁协议

### 8.2.1 锁的分类

| 锁类型 | 说明 | 兼容性 |
|--------|--------|--------|
| **共享锁**（S锁） | 允许多个事务读同一数据项 | S-S：兼容<br>S-X：不兼容 |
| **排他锁**（X锁） | 禁止其他事务访问数据项 | X-X：不兼容<br>X-S：不兼容 |
| **更新锁**（U锁） | 允许读但限制写 | U-U：兼容<br>U-X：不兼容 |

**锁的转换**：
- **升级（Lock Upgrade）**：S锁 → X锁
- **降级（Lock Downgrade）**：X锁 → S锁

```sql
-- 升级锁示例
LOCK TABLE account IN SHARE MODE;  -- S锁
LOCK TABLE account IN EXCLUSIVE MODE;  -- X锁（升级）
```

### 8.2.2 闭\u9501（Two-Phase Locking, 2PL）

**基本机制**：
将事务的加锁过程分为两个阶段：
1. **扩展阶段**（Growing Phase）：获取锁，不能释放任何锁
2. **收缩阶段**（Shrinking Phase）：释放锁，不能获取新锁

**示例**
```
事务T: lock(A) → lock(B) → unlock(A) → write(A) → unlock(B)
                    ↑            ↑
               扩展阶段     收缩阶段
```

**严格二阶段协议（Strict 2PL）**：
事务持有的所有X锁直到事务提交或回滚时才释放

**先\u884c\u89e3锁协议（Conservative 2PL）**：
事务在执行前先获取所有需要的锁

### 8.2.3 锁的精度

| 锁精度 | 描述 | 冲突概率 | 并发度 |
|--------|--------|--------|--------|
| **对象级锁** | 锁定整个对象（表） | 低 | 低 |
| **页级锁** | 锁定一页数据 | 中 | 中 |
| **行级锁** | 锁定单行数据 | 高 | 高 |
| **属性级锁** | 锁定单个属性值 | 极高 | 极高 |

**多类锁协议**：
- 允许事务对不同大小的数据项使用不同精度的锁
- 需要定义多类锁之间的兼容表

## 8.3 并发控制协议

### 8.3.1 时戳排序协议

**基本思想**：
为每个事务分配一个唯一的时戳，根据时戳决定事务的执行顺序

**时戳系统**：
- 读时戳（Read-TS）：事务最后读数据的时间
- 写时戳（Write-TS）：事务最后写数据的时间

**协议规则**：
1. 事务T读取数据项X时：
   - 如果 Write-TS(X) > TS(T)，则拒绝读操作，T回滚
   - 否则，执行读操作并更新 Read-TS(X) = max(Read-TS(X), TS(T))
   
2. 事务T写入数据项X时：
   - 如果 TS(T) < Read-TS(X)，则回滚T
   - 如果 TS(T) < Write-TS(X)，则不执行写操作（不必修改）
   - 否则，执行写操作，并更新 Write-TS(X) = TS(T)

**优点**：
- 无死锁
- 简单实现

**缺点**：
- 事务可能频繁回滚
- 无法保证可串行性

### 8.3.2 验证协议

**基本思想**：
事务分三阶段执行：
1. **读写阶段**：执行所有操作，不写入数据库
2. **验证阶段**：检查冲突
3. **写入阶段**：所有更新写入数据库

**冲突检测**：
如果事务T1和T2同时访问同一数据项，且至少有一个是写操作，则冲突

**事务串行化**：
事务T1在验证时，不存在任何事务T2：
- 在T1读写阶段后所完成
- 在T1验证前所完成

**协议规则**：
1. 执行读写阶段，记录所有更新
2. 获得验证锁，检查冲突
   - 如有冲突，回滚事务
   - 如无冲突，继续
3. 所有更新写入数据库
4. 释放验证锁

**优点**：
- 并发度高
- 不产生死锁
- 保证可串行性

**缺点**：
- 需要保存读过的数据
- 事务可能因冲突频繁回滚

### 8.3.3 多版本并发控制（MVCC）

**基本思想**：
为每个读取数据的事务分配一个时间戳，数据存储多个版本

**工作原理**：
- 读操作读取数据的时候，不加锁
- 写操作记录提交的时间戳
- 读操作根据时间戳决定读哪个版本

**优点**：
- 读不阻写，写不阻击
- 无死锁
- 高并发性能

**实现**：
- 每个记录包含创建时间戳和删除时间戳
- 读操作读取创建时间戳小于当前时间的记录
- 写操作创建新的记录版本

## 8.4 死锁

### 8.4.1 死锁的概念

**死锁**（Deadlock）：两个或多个事务在执行过程中，因争调系统资源而造成的一种绝望状态

**死锁的四个必要条件**：
1. 互斥条件：资源不能共享
2. 占有且等待条件：已占用资源的任务还在等待其他资源
3. 不可削除条件：已分配的资源在任务完成前不能被强制删除
4. 循环等待条件：存在一个事务的闭合链

### 8.4.2 死锁的处理

**1. 死锁预防**：
- 采用严格的事务排序
- 一致的锁请求顺序
- 预先获取所有需要的锁

**2. 死锁避免**：
- 超时机制：设置等待超时时间
- 回退机制：当发生死锁时，回退任意一个事务

**3. 死锁检测**：
- 等待图法
- 周期性检测

**4. 死锁的解除**：
- 选择回退解除的事务
- 撤销事务所有操作
- 释放事务持有的所有锁

### 8.4.3 死锁的明确 协议

**Oracle中的明确锁定**：
```sql
-- 明确加锁
SELECT * FROM table_name WHERE condition FOR UPDATE;

-- 带等待的明确锁定
SELECT * FROM table_name 
WHERE condition 
FOR UPDATE WAIT 10;  -- 等待10秒

-- 不等待的明确锁定
SELECT * FROM table_name 
WHERE condition 
FOR UPDATE NOWAIT;  -- 立即返回
```
