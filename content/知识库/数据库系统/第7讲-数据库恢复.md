## 数据库恢复概述

### 为什么需要数据库恢复？

数据库系统面临各种故障威胁：
1. **系统故障**：断电、硬件故障、软件崩溃
2. **事务故障**：事务执行失败
3. **介质故障**：磁盘损坏、数据丢失
4. **人为错误**：误删除、误操作

## 事务的概念

### 什么是事务？

**事务**是数据库操作的逻辑单位，具有ACID特性。

### 示例数据库

为了说明恢复机制，我们使用以下数据库：

**Account 表（银行账户）：**

| accountID | owner | balance |
|-----------|-------|---------|
| A001 | 张三 | 1000 |
| A002 | 李四 | 2000 |
| A003 | 王五 | 1500 |

### ACID特性

#### 1. 原子性（Atomicity）

事务中的所有操作要么全部执行，要么全部不执行。

**示例：转账事务**

事务 $T_1$：从账户 A001 转账 100 元到账户 A002

```
BEGIN TRANSACTION
    UPDATE Account SET balance = balance - 100 WHERE accountID = 'A001';
    UPDATE Account SET balance = balance + 100 WHERE accountID = 'A002';
COMMIT
```

**原子性保证：**
- 如果在第一个 UPDATE 后、第二个 UPDATE 前发生故障，系统会回滚第一个 UPDATE
- 要么两个 UPDATE 都执行，要么都不执行

**执行前：**

| accountID | owner | balance |
|-----------|-------|---------|
| A001 | 张三 | 1000 |
| A002 | 李四 | 2000 |

**执行后：**

| accountID | owner | balance |
|-----------|-------|---------|
| A001 | 张三 | 900 |
| A002 | 李四 | 2100 |

#### 2. 一致性（Consistency）

事务执行前后，数据库处于一致状态。

**示例：转账前后总金额不变**

- 执行前：1000 + 2000 = 3000
- 执行后：900 + 2100 = 3000

形式化：$C(S_{before}) = C(S_{after}) = \text{TRUE}$

#### 3. 隔离性（Isolation）

并发执行的事务相互隔离。

**示例：两个并发转账事务**

事务 $T_1$：从 A001 转 100 到 A002
事务 $T_2$：从 A001 转 50 到 A003

**串行执行结果（$T_1$ 然后 $T_2$）：**

初始：A001=1000, A002=2000, A003=1500

$T_1$ 执行后：A001=900, A002=2100, A003=1500
$T_2$ 执行后：A001=850, A002=2100, A003=1550

**隔离性保证：** 并发执行的结果应该与某个串行执行的结果相同

#### 4. 持久性（Durability）

已提交事务的结果永久保存。

**示例：** 如果 $T_1$ 已提交，即使系统崩溃，A001 的余额也应该是 900

## 日志的类型

### 1. 撤销日志（Undo Logging）

**撤销日志**记录事务修改前的数据值，用于回滚未提交的事务。

#### 日志记录格式

$$\langle T, X, V_{old} \rangle$$

其中：
- $T$：事务ID
- $X$：数据项
- $V_{old}$：修改前的值

#### 示例：转账事务的日志

事务 $T_1$：从 A001 转 100 到 A002

初始状态：A001=1000, A002=2000

**日志记录：**

| 序号 | 日志记录 | 说明 |
|------|----------|------|
| 1 | $\langle T_1, start \rangle$ | 事务开始 |
| 2 | $\langle T_1, A001.balance, 1000 \rangle$ | 修改 A001 前记录旧值 |
| 3 | $\langle T_1, A002.balance, 2000 \rangle$ | 修改 A002 前记录旧值 |
| 4 | $\langle T_1, commit \rangle$ | 事务提交 |

**数据库状态变化：**

| 阶段 | A001.balance | A002.balance |
|------|--------------|--------------|
| 初始 | 1000 | 2000 |
| 修改 A001 后 | 900 | 2000 |
| 修改 A002 后 | 900 | 2100 |

### 撤销日志的恢复过程

#### 场景1：事务执行中故障

**故障时刻：** 在日志记录 2 之后、日志记录 3 之前

**日志内容：**
```
⟨T1, start⟩
⟨T1, A001.balance, 1000⟩
-- 故障发生
```

**数据库状态：** A001=900, A002=2000

**恢复过程：**
1. 扫描日志，发现 $T_1$ 未提交（没有 $\langle T_1, commit \rangle$）
2. 找到 $\langle T_1, A001.balance, 1000 \rangle$
3. 将 A001.balance 恢复为 1000
4. 写入 $\langle T_1, abort \rangle$

**恢复后：** A001=1000, A002=2000

#### 场景2：事务提交后故障

**日志内容：**
```
⟨T1, start⟩
⟨T1, A001.balance, 1000⟩
⟨T1, A002.balance, 2000⟩
⟨T1, commit⟩
-- 故障发生
```

**恢复过程：**
1. 扫描日志，发现 $T_1$ 已提交
2. 不需要撤销，保持数据库状态不变

**恢复后：** A001=900, A002=2100

### 撤销日志的规则

#### 规则1：日志记录先于数据写入

$$\text{Write}(X) \Rightarrow \text{LogFirst}(\langle T, X, V_{old} \rangle)$$

**含义：** 在修改数据项 $X$ 之前，必须先将撤销日志记录写入稳定存储器

#### 规则2：提交时强制写入日志

$$\text{Commit}(T) \Rightarrow \text{ForceWrite}(\text{LogRecords}(T))$$

**含义：** 事务提交时，必须将所有日志记录强制写入稳定存储器

## 多事务的日志

### 示例：两个并发事务

事务 $T_1$：从 A001 转 100 到 A002
事务 $T_2$：从 A003 转 50 到 A001

初始状态：A001=1000, A002=2000, A003=1500

**交错执行的日志：**

| 序号 | 日志记录 | 事务 | 说明 |
|------|----------|------|------|
| 1 | $\langle T_1, start \rangle$ | $T_1$ | $T_1$ 开始 |
| 2 | $\langle T_1, A001.balance, 1000 \rangle$ | $T_1$ | 修改 A001 前 |
| 3 | $\langle T_2, start \rangle$ | $T_2$ | $T_2$ 开始 |
| 4 | $\langle T_2, A003.balance, 1500 \rangle$ | $T_2$ | 修改 A003 前 |
| 5 | $\langle T_1, A002.balance, 2000 \rangle$ | $T_1$ | 修改 A002 前 |
| 6 | $\langle T_1, commit \rangle$ | $T_1$ | $T_1$ 提交 |
| 7 | $\langle T_2, A001.balance, 900 \rangle$ | $T_2$ | 修改 A001 前（$T_1$ 已修改为 900） |
| 8 | $\langle T_2, commit \rangle$ | $T_2$ | $T_2$ 提交 |

**数据库状态变化：**

| 阶段 | A001 | A002 | A003 |
|------|------|------|------|
| 初始 | 1000 | 2000 | 1500 |
| $T_1$ 修改 A001 | 900 | 2000 | 1500 |
| $T_2$ 修改 A003 | 900 | 2000 | 1450 |
| $T_1$ 修改 A002 | 900 | 2100 | 1450 |
| $T_2$ 修改 A001 | 850 | 2100 | 1450 |

### 故障恢复示例

**故障时刻：** 在日志记录 7 之后、日志记录 8 之前

**日志内容：**
```
⟨T1, start⟩
⟨T1, A001.balance, 1000⟩
⟨T2, start⟩
⟨T2, A003.balance, 1500⟩
⟨T1, A002.balance, 2000⟩
⟨T1, commit⟩
⟨T2, A001.balance, 900⟩
-- 故障发生
```

**恢复过程：**
1. 从后向前扫描日志
2. $T_1$ 已提交，不需要撤销
3. $T_2$ 未提交，需要撤销：
   - 找到 $\langle T_2, A001.balance, 900 \rangle$，将 A001.balance 恢复为 900
   - 找到 $\langle T_2, A003.balance, 1500 \rangle$，将 A003.balance 恢复为 1500
4. 写入 $\langle T_2, abort \rangle$

**恢复后状态：** A001=900, A002=2100, A003=1500

## 检查点技术

### 什么是检查点？

**检查点**是数据库在某个时间点的一致性快照，用于减少恢复时间。

### 静态检查点示例

**检查点前的日志：**
```
⟨T1, start⟩
⟨T1, A001.balance, 1000⟩
⟨T1, commit⟩
⟨checkpoint⟩  -- 检查点
⟨T2, start⟩
⟨T2, A002.balance, 2000⟩
```

**恢复过程：**
1. 从检查点开始扫描
2. 只需要处理检查点后开始的事务（$T_2$）
3. $T_2$ 未提交，需要撤销

### 动态检查点示例

**检查点记录：**
```
⟨checkpoint, {T2, T3}⟩  -- 记录活跃事务
```

**含义：** 检查点时刻，$T_2$ 和 $T_3$ 正在执行

**恢复过程：**
1. 从检查点开始扫描
2. 只需要处理 $T_2$ 和 $T_3$
3. 已提交的事务不需要处理

## 恢复算法

### 撤销日志恢复算法

```
Input: 日志文件
Output: 恢复后的数据库

1. 从后向前扫描日志
2. 记录所有已提交的事务
3. 对于每个未提交的事务 T：
   a. 找到所有 ⟨T, X, V_old⟩ 记录
   b. 将 X 恢复为 V_old
4. 写入 ⟨T, abort⟩ 记录
```

### 示例

**日志：**
```
⟨T1, start⟩
⟨T1, A, 100⟩
⟨T2, start⟩
⟨T2, B, 200⟩
⟨T1, C, 300⟩
⟨T1, commit⟩
⟨T2, A, 150⟩
-- 故障
```

**恢复过程：**

| 步骤 | 操作 | 数据库状态 |
|------|------|------------|
| 初始 | - | A=?, B=?, C=? |
| 1 | 扫描，记录已提交事务 | 已提交：{T1} |
| 2 | 处理 T2（未提交） | - |
| 3 | 恢复 A = 150 | A=150 |
| 4 | 恢复 B = 200 | A=150, B=200 |
| 5 | 写入 ⟨T2, abort⟩ | 完成 |

## 事务的状态转换

### 状态转换图

```
Active → Partially Committed → Committed
   ↓              ↓
Failed → Aborted
```

### 示例

**正常执行：**
```
⟨T1, start⟩          -- Active
⟨T1, A, 100⟩         -- Active
⟨T1, B, 200⟩         -- Active
⟨T1, commit⟩         -- Committed
```

**失败执行：**
```
⟨T1, start⟩          -- Active
⟨T1, A, 100⟩         -- Active
-- 故障              -- Failed
-- 恢复              -- Aborted
```

## 学习建议

对于初学者，建议：
1. **理解ACID特性**：这是事务处理的基础
2. **掌握日志的基本概念**：了解撤销日志和重做日志的区别
3. **理解恢复的基本原理**：知道如何从故障中恢复
4. **通过例子加深理解**：分析具体的恢复过程

> [!tip] 实践建议
> 建议模拟一个简单的事务执行过程，手动记录日志，然后模拟故障恢复，这样能更好地理解恢复机制。

## 关键概念总结

1. **事务**：数据库操作的逻辑单位，具有ACID特性
2. **原子性**：$\text{Exec}(T) = \text{all or nothing}$
3. **一致性**：$C(S_{before}) = C(S_{after}) = \text{TRUE}$
4. **日志记录**：$\langle T, X, V_{old} \rangle$（撤销）、$\langle T, X, V_{new} \rangle$（重做）
5. **检查点**：减少恢复时间的技术
