# 事务 (Transactions)

• 事务 (Transaction) = 涉及数据库查询和/或修改的过程。  
• ACID 是:

原子性 (Atomic) : 整个事务全部完成，或者完全不执行。  
• 致性 (Consistency ): 事务执行前后，数据库的完整性约束和业务逻辑必须是对的。  
• 隔离性 (Isolated ): 对用户而言，似乎一次只有一个进程在执行。  
• 持久性 (Durable): 进程产生的影响在系统崩溃后依然存在。

# COMMIT vs. ROLLBACK

• SQL 的 COMMIT 导致事务成功完成。

它的数据库修改现在永久保存在数据库中。

• SQL 的 ROLLBACK 也会导致事务结束，但以中止(aborting)的方式。

对数据库没有影响。

# Undo日志 (Undo Logging)

• 日志是由日志记录组成的文件，每条记录说明了某个事务所做的某些事情。  
• 将日志想象成一个仅允许追加写入的文件。  
• Undo logging (撤销日志) — 通过撤销(Undoing)可能在崩溃前未完成的事务影响，来修复数据库状态。

# Undo 日志记录

• 几种形式的日志记录 (log records)

• <START Ti>: 表示事务 Ti 已开始  
• <COMMIT Ti>: 事务 Ti 已成功完成，并且不会再对数据库元素进行任何更改  
• <ABORT Ti>: 事务 Ti 未能成功完成  
• <Ti, X, v>: 事务 Ti 更改了数据库元素 X，其旧值为 v。

# <T, X,v> undo日志/记录

• 事务 Ti 更改了数据库元素 X，其旧值为 v。  
• 更新记录反映的更改通常发生在内存中，而不是磁盘上； 即，日志记录是对 WRITE 操作的响应，而不是对 OUTPUT 操作的响应。

# 注意

• 日志首先写入内存  
• 不会在每个动作上都写入磁盘【块设备的特性，效率】  
• Undo日志不记录数据库元素的新值

• 仅记录旧值

• 恢复管理器将要做的唯一事情  
• 通过恢复旧值来取消事务在磁盘上可能产生的影响

# Undo日志规则 (The Undo-Logging Rules)

• U1: 如果事务 T 修改了数据库元素 X，则必须在将 X 的新值写入磁盘之前，将形如 <T, X, v> 的日志记录写入磁盘。

写入磁盘：先写undo日志， 再写数据

• U2: 如果事务提交，则必须在事务修改的所有数据库元素写入磁盘之后，才将其 COMMIT 日志记录写入磁盘，但此后应尽快写入.

COMMIT：先写数据，再写undo日志Commit

# 按以下顺序写入磁盘

• 与一个事务相关的内容必须按以下顺序写入磁盘  
• a) 记录修改数据库元素的日志  
• b) 更改后的数据库元素本身  
c) commit 日志记录  
• a) 和 b) 的顺序适用于每个单独的数据库元素

HDD：undo日志-> 数据 -> COMMIT记录

• 为了强制将日志记录写入磁盘

– 日志管理器需要一个 flush-log (刷新日志) 命令，该命令告诉缓冲区管理器将以前未复制到磁盘的所有日志块复制到磁盘

– FLUSH LOG

• 事务管理器需要一种方法来告诉缓冲区管理器

– 对数据库元素执行 OUTPUT 操作

# 小结：Undo日志规则

(1) 对于每个 Write 动作，生成 undo 日志记录(记录的是旧值)  
(2) 在磁盘上的 x 被修改之前，关于 x 的 undo 日志记录必须已在磁盘上 (预写式日志: WAL)  
(3) 在 commit flush到日志之前，事务的所有write操作必须已存储在磁盘上。

# 检查点 (Checkpoint)

•为了避免检查整个日志

• 我们可以删除 COMMIT 之前的日志吗？  
• 不行！有关其他活动事务 T 的日志记录可能会丢失

•这个问题的解决方案

• 定期为日志设置检Checkpoint

# 检查点 (Checkpoint)

• 在一个简单的Checkpoint中,

1. 停止接受新事务。  
2. 等待直到所有当前活动的事务提交或中止，并在日志中写入COMMIT 或 ABORT 记录。  
3. 将日志flush到磁盘。  
4. 写入日志记录 <CKPT>，然后再次flush日志。  
5. 恢复接受事务。

# 检查点 (Checkpoint)

# Checkpoint的影响

– 检查点之前执行的任何事务都已经完成  
– 在恢复期间，从尾部扫描日志，当找到 <CKPT> 记录时，所有未完成的事务都已经被看到过了  
– 不需要扫描 <CKPT> 之前的内容，  
– 事实上，该点之前的日志可以安全地删除或覆盖。

# 为什么要用 redo 日志？

• Undo 日志的问题

• 必须在事务提交之前将其更改的数据全部写入磁盘→ 磁盘 I/O太多

• 节省磁盘 I/O

• 让更改的数据暂时只驻留在主存中  
• 使用 redo 日志在发生崩溃时进行修复

# Redo日志的恢复

R1的推论：除非日志中有一条 <COMMIT T> 记录，否则我们确信事务T 对数据库所做的任何更改都没有写入磁盘。

• 在恢复期间，未完成的事务可以被当作从未发生过一样处理。  
• 对于已完成的事务，将 redo 日志中的新值写入磁盘，无论它们是否已经存储在磁盘中。

# 恢复规则: Redo logging

• 在系统崩溃后，使用 redo 日志进行恢复:

• (1) 识别已提交的事务集合 S (日志中有 <commit , Ti>)。  
• (2) 从头开始扫描日志。对于遇到的每个日志记录 <Ti, X, v>：

• 如果 Ti 不在 S 中，什么也不做。  
• 如果 Ti 在 S 中，则写入数据库元素 X 的新值 v。

• (3) 对于每个未完成的事务 Ti (Ti  S)，向日志写入一条<ABORT Ti> 记录。

# 恢复规则: Redo logging

(1) 设 $\mathbb { S } =$ 日志中包含 <commit , Ti> 的 事务(transactions)集合  
(2) 对于日志中的每个 <Ti，X， $\mathbf { \nabla } \mathbf { v } > \mathbf { \nabla } _ { \mathbf { \eta } ^ { \prime } }$ 按照正向顺序 (最早 → 最新) 执行:

- 如果 Ti  S 那么 Write(X, v)Output(X)

(3) 对于每一个 Ti $\not \in { \mathsf { S } } _ { \prime }$ 写入<ABORT Ti>

# 使用 Undo/Redo 日志进行恢复

# • undo/redo 恢复策略是:

• 已提交的：按照“最早优先”的顺序重做已提交的事务。  
• 未提交的：按照“最新优先”的顺序撤销未提交的事务。

# 恢复过程

# 为 Undo/Redo 日志设置检查点

• 对于 undo/redo 日志来说，非静止检查点比其他日志方法稍微简单一些

– 写入一条 <START CKPT (T1, …, Tk)> 记录到日志中，其中 T1, …, Tk 是所有活动的事务，并刷新日志  
– 将所有脏(dirty)缓冲区写入磁盘；即，它们包含一个或多个更改过的数据库元素。  
– 与 redo 日志不同，我们要刷新所有脏(dirty)缓冲区，而不仅仅是那些由已提交事务写入的缓冲区  
– 写入一条 <END CKPT> 记录到日志中并刷新日志
