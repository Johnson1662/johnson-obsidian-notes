# 第8讲 并发控制

## 1. 并发执行方式 (18.1)

### 1.1 为什么需要并发控制

多用户数据库系统允许多个用户同时使用，例如飞机订票系统、银行数据库系统。特点：在同一时刻并发运行的事务数可达数百个。

**三种多事务执行方式：**

| 执行方式                                        | 说明                                                                       | 优缺点                                                           |
| ----------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **(1) 事务串行执行**                            | 每个时刻只有一个事务运行，其他事务必须等到这个事务结束以后方能运行         | 不能充分利用系统资源，无法发挥数据库共享资源的特点               |
| **(2) 交叉并发方式** (Interleaved Concurrency)  | 在单处理机系统中，事务的并行执行是这些并行事务的操作轮流交叉运行           | 并没有真正地并行运行，但能够减少处理机的空闲时间，提高系统的效率 |
| **(3) 同时并发方式** (Simultaneous Concurrency) | 多处理机系统中，每个处理机可以运行一个事务，多个处理机可以同时运行多个事务 | 实现多个事务真正的并行运行                                       |

### 1.2 并发导致的数据异常

并发执行会带来问题：会产生多个事务同时存取同一数据的情况，可能会存取和存储不正确的数据，破坏事务一致性和数据库的一致性。

**示例**：约束条件 A = B，初始 A=25, B=25

T1: Read(A); A ← A+100; Write(A); Read(B); B ← B+100; Write(B);
T2: Read(A); A ← A×2; Write(A); Read(B); B ← B×2; Write(B);

**三种典型异常：**

| 异常类型       | 说明                                                                                                  | 示例                                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **脏读**       | 读取未提交数据。T1 读取 T2 尚未提交的数据，此时如果 T2 发生错误并回滚，那么 T1 读取到的数据就是脏数据 | T2 取款100元（余额200→100），T1 读到余额100（脏读），T2 回滚（余额恢复200），T1 转入200（余额改为300，错误！） |
| **不可重复读** | 前后多次读取，数据内容不一致。在 T1 两次读取期间，T2 修改了数据并提交                                 | T1 第一次查张三成绩96，T2 修改为69并提交，T1 第二次查张三成绩69（不一致）                                      |
| **幻读**       | 一个事务按相同条件重新读取以前检索过的数据，却发现其他事务插入了满足其查询条件的新数据                | T1 查1班平均分78（25人），T2 插入1班新同学90分，T1 再查平均分不再是78                                          |

### 1.3 事务隔离级别

| 隔离级别               | 脏读 | 不可重复读 | 幻读 |
| ---------------------- | ---- | ---------- | ---- |
| READ UNCOMMITTED       | √    | √          | √    |
| READ COMMITTED（默认） | ×    | √          | √    |
| REPEATABLE READ        | ×    | ×          | √    |
| SERIALIZABLE           | ×    | ×          | ×    |

> 事务串行化会极大降低数据库的效率。不同商业版本会有不一样的支持/实现。

### 1.4 串行与可串行化调度

**调度（Schedule）**：表示操作执行的时间顺序。

**串行调度（Serial Schedule）**：操作没有交叉执行，一个事务的所有操作完成后，才开始下一个事务的操作。

假设有 T1、T2 两个事务，约束 A = B，初始 A=25, B=25：

**Schedule A（串行 T1→T2）**：

| Step | T1               | T2             | A       | B       |
| ---- | ---------------- | -------------- | ------- | ------- |
| 初始 |                  |                | 25      | 25      |
| 1    | Read(A); A←A+100 |                | 125     |         |
| 2    | Write(A)         |                |         |         |
| 3    | Read(B); B←B+100 |                |         | 125     |
| 4    | Write(B)         |                |         |         |
| 5    |                  | Read(A); A←A×2 | 250     |         |
| 6    |                  | Write(A)       |         |         |
| 7    |                  | Read(B); B←B×2 |         | 250     |
| 8    |                  | Write(B)       |         |         |
| 结果 |                  |                | **250** | **250** |

**Schedule B（串行 T2→T1）**：

| Step | T1               | T2             | A       | B       |
| ---- | ---------------- | -------------- | ------- | ------- |
| 初始 |                  |                | 25      | 25      |
| 1    |                  | Read(A); A←A×2 | 50      |         |
| 2    |                  | Write(A)       |         |         |
| 3    |                  | Read(B); B←B×2 |         | 50      |
| 4    |                  | Write(B)       |         |         |
| 5    | Read(A); A←A+100 |                | 150     |         |
| 6    | Write(A)         |                |         |         |
| 7    | Read(B); B←B+100 |                |         | 150     |
| 8    | Write(B)         |                |         |         |
| 结果 |                  |                | **150** | **150** |

串行调度一定是正确的！但如果有 T1…Tn 共 n 个事务，有 n! 种串行调度方案。

### 1.5 可串行化调度 (Serializable Schedules)

**定义**：如果存在一个串行调度 S'，使得对于每个初始数据库状态，S 和 S' 的效果相同，那么调度 S 就是可串行化的。

**示例（可串行化调度）**：T1 先执行读/写 A，T2 后执行读/写 A，T1 再执行读/写 B，T2 后执行读/写 B。

| Step | T1               | T2             | A       | B       |
| ---- | ---------------- | -------------- | ------- | ------- |
| 初始 |                  |                | 25      | 25      |
| 1    | Read(A); A←A+100 |                | 125     |         |
| 2    | Write(A)         |                |         |         |
| 3    |                  | Read(A); A←A×2 | 250     |         |
| 4    |                  | Write(A)       |         |         |
| 5    | Read(B); B←B+100 |                |         | 125     |
| 6    | Write(B)         |                |         |         |
| 7    |                  | Read(B); B←B×2 |         | 250     |
| 8    |                  | Write(B)       |         |         |
| 结果 |                  |                | **250** | **250** |

等价于串行调度 T1→T2 ✓

**示例（不可串行化调度）**：

| Step | T1               | T2             | A       | B       |
| ---- | ---------------- | -------------- | ------- | ------- |
| 初始 |                  |                | 25      | 25      |
| 1    | Read(A); A←A+100 |                | 125     |         |
| 2    | Write(A)         |                |         |         |
| 3    |                  | Read(A); A←A×2 | 250     |         |
| 4    |                  | Write(A)       |         |         |
| 5    |                  | Read(B); B←B×2 |         | 50      |
| 6    |                  | Write(B)       |         |         |
| 7    | Read(B); B←B+100 |                |         | 150     |
| 8    | Write(B)         |                |         |         |
| 结果 |                  |                | **250** | **150** |

A≠B，不满足约束，NOT Serializable ✗

> **注意**：如果操作是加法（交换律成立），某些交叉调度可能恰好结果相同。但这不具有普适性。

## 2. 冲突可串行化 (18.2)

### 2.1 事务和调度的符号表示

只关注读（r）和写（w）操作，忽略涉及的实际值：

- $r_T(X)$：事务 T 读取数据库元素 X
- $w_T(X)$：事务 T 写入数据库元素 X

示例事务：
$$T_1: r_1(A); w_1(A); r_1(B); w_1(B);$$
$$T_2: r_2(A); w_2(A); r_2(B); w_2(B);$$

**冲突（Conflict）**：调度中的一对连续操作，如果交换它们的顺序，会改变至少一个事务的行为。

**冲突操作（Conflicting actions）**：不同事务的任意两个操作都可以交换，除非：

- 它们涉及同一个数据库元素
- 且至少有一个是写操作

| 操作对                 | 是否冲突 | 说明                       |
| ---------------------- | -------- | -------------------------- |
| $r_i(X); r_j(Y)$，X≠Y  | 不冲突   | 不同事务读不同元素         |
| $r_i(X); r_j(X)$       | 不冲突   | 两个读操作，即使同一元素   |
| $w_i(X); r_j(Y)$，X≠Y  | 不冲突   | 不同元素                   |
| $w_i(X); w_j(X)$       | **冲突** | 不同事务写同一元素         |
| $r_i(X); w_j(X)$       | **冲突** | 一读一写同一元素           |
| $w_i(X); r_j(X)$       | **冲突** | 一写一读同一元素           |
| 同一事务的任意两个操作 | **冲突** | 不能交换同一事务的操作顺序 |

### 2.2 冲突可串行化 (Conflict-Serializable)

**定义**：如果调度 S 可以通过一系列相邻不冲突操作的交换转换为某个串行调度，则称 S 是**冲突可串行化**的。

- 冲突可串行化是可串行化的**充分条件**（不是必要条件）
- 冲突可串行化调度一定是可串行化调度

### 2.3 优先图 (Precedence Graph)

用于检查调度 S 是否是冲突可串行化的：

- **节点**：S 中的事务（标记为 T1, T2, ...）
- **有向边** $T_i \to T_j$：Ti 的操作 A1 和 Tj 的操作 A2 满足：
  - 在 S 中 A1 在 A2 之前
  - A1、A2 涉及同一个数据库元素
  - 且 A1 和 A2 中至少有一个是写操作

**测试冲突可串行化的步骤：**

1. 构造调度 S 的优先图
2. 检测图中是否存在环
   - 如果存在环 → S **不是**冲突可串行化的
   - 如果不存在环 → S **是**冲突可串行化的
3. 对节点进行拓扑排序，即为冲突等价的串行顺序

**示例**：

$$S: r_2(A); r_1(B); w_2(A); r_3(A); w_1(B); w_3(A); r_2(B); w_2(B);$$

优先图：T2→T1（A上 w2 在 w1 前），T2→T3（A上 w2 在 w3 前），T1→T2（B上 w1 在 w2 前）

该优先图存在环 T1→T2→T1，因此调度 S **不是**冲突可串行化的。

**练习**：判断 $S = w_3(A); w_2(C); r_1(A); w_1(B); r_1(C); w_2(A); r_4(A); w_4(D)$ 是否冲突可串行化。

分析：w3(A)→r1(A)→w2(A)→r4(A)，优先图无环，是冲突可串行化的。串行顺序：T3→T1→T2→T4。

## 3. 通过锁强制实现可串行化 (18.3)

### 3.1 基本概念

**调度器（Scheduler）**：从事务中接收读/写请求，决定是立即执行还是阻塞等待。

**锁（Lock）**：事务必须请求和释放锁来控制对数据的访问。

**符号表示：**

- $l_i(X)$：事务 $T_i$ 请求对数据库元素 X 加锁
- $u_i(X)$：事务 $T_i$ 释放 X 上的锁

### 3.2 事务的一致性与调度合法性

**规则 1：事务的一致性**

- 事务只有在先前请求了某个元素的锁且尚未释放该锁的情况下，才能读取或写入该元素
- 结构良好的事务：$T_i: ... l_i(A) ... r_i/w_i(A) ... u_i(A) ...$

**规则 2：调度的合法性**

- 如果没有先释放锁，任何两个事务不能同时锁定同一个元素
- 如果 $l_i(X)$ 出现在调度中，那么在某个后续位置必然存在 $u_i(X)$

### 3.3 两阶段锁 (Two-Phase Locking, 2PL)

**规则 3：两阶段锁**

- 在每个事务中，所有的加锁请求都必须在所有的解锁操作之前

**"两阶段"：**

1. **第一阶段（扩展阶段）**：获取锁
2. **第二阶段（收缩阶段）**：释放锁

> 两阶段锁保证了：一致事务的合法调度是冲突可串行化的。

**示例（不遵守2PL，导致非可串行化）：**

| Step | T1                      | T2                    | A       | B       |
| ---- | ----------------------- | --------------------- | ------- | ------- |
| 初始 |                         |                       | 25      | 25      |
| 1    | l1(A); Read(A); A←A+100 |                       |         |         |
| 2    | Write(A); u1(A)         |                       | 125     |         |
| 3    |                         | l2(A); Read(A); A←A×2 |         |         |
| 4    |                         | Write(A); u2(A)       | 250     |         |
| 5    |                         | l2(B); Read(B); B←B×2 |         |         |
| 6    |                         | Write(B); u2(B)       |         | 50      |
| 7    | l1(B); Read(B); B←B+100 |                       |         |         |
| 8    | Write(B); u1(B)         |                       |         | 150     |
| 结果 |                         |                       | **250** | **150** |

不遵守2PL（T1在u1(A)后又l1(B)），结果 A≠B，非可串行化 ✗

**示例（遵守2PL，可串行化）：**

| Step | T1                      | T2                           | A       | B       |
| ---- | ----------------------- | ---------------------------- | ------- | ------- |
| 初始   |                         |                              | 25      | 25      |
| 1    | l1(A); Read(A); A←A+100 |                              |         |         |
| 2    | Write(A); l1(B)         |                              | 125     |         |
| 3    | u1(A)                   |                              |         |         |
| 4    |                         | l2(A); Read(A); A←A×2        |         |         |
| 5    |                         | Write(A)                     | 250     |         |
| 6    |                         | l2(B) **Denied!**            |         |         |
| 7    | Read(B); B←B+100        |                              |         |         |
| 8    | Write(B); u1(B)         |                              | 125     |         |
| 9    |                         | l2(B); u2(A); Read(B); B←B×2 |         |         |
| 10   |                         | Write(B); u2(B)              |         | 250     |
| 结果   |                         |                              | **250** | **250** |

T2 请求 l2(B) 被延迟（T1 持有 l1(B)），直到 T1 释放。等价于串行调度 T1→T2 ✓

### 3.4 为什么两阶段锁有效

**直观理解**：每个遵循两阶段锁的事务，在它发出第一个解锁请求的瞬间，就"整体执行完毕"了。对于由 2PL 事务组成的调度 S，总是至少存在一个冲突等价的串行调度，其事务顺序与它们首次进行解锁的顺序相同。

**归纳证明思路：**

- **基础情况**：n=1，S 已经是串行调度
- **归纳步骤**：设 Ti 是第一个执行解锁操作的事务。可以证明 Ti 的所有读写操作可以通过交换非冲突操作向前移动到调度开头，不包含任何与 Ti 冲突的操作。然后对剩余的 n-1 个事务应用归纳假设。

### 3.5 死锁风险

两阶段锁**无法解决**死锁问题。

**死锁示例：**

| T1                      | T2                    |
| ----------------------- | --------------------- |
| l1(A); Read(A); A←A+100 |                       |
| Write(A)                |                       |
| l1(B)                   |                       |
| **等待...**             | l2(B); Read(B); B←B×2 |
|                         | Write(B)              |
|                         | l2(A)                 |
|                         | **等待...**           |

T1 持有 A 的锁等待 B，T2 持有 B 的锁等待 A → **死锁！**

## 4. 具有多种锁模式的锁系统 (18.4)

### 4.1 共享锁和排他锁

**问题**：简单 2PL 中，事务 T 必须在数据库元素 X 上加锁，即使它只是想读取 X。没有理由不让多个事务同时读取 X。

**两种锁模式：**

- **共享锁（Shared Lock, S锁）**：读锁，多个事务可同时持有
- **排他锁（Exclusive Lock, X锁）**：写锁，只有一个事务可持有

**规则**：对于任何数据库元素 X，要么可以有一个排他锁，要么可以有任意数量的共享锁（但不能两者兼有）。

**符号表示：**

- $sl_i(X)$：事务 $T_i$ 请求对 X 加共享锁
- $xl_i(X)$：事务 $T_i$ 请求对 X 加排他锁
- $u_i(X)$：事务 $T_i$ 释放 X 上的锁

**规则 1：事务的一致性（扩展版）**

- 读操作 $r_i(X)$ 之前必须有 $sl_i(X)$ 或 $xl_i(X)$，中间没有 $u_i(X)$
- 写操作 $w_i(X)$ 之前必须有 $xl_i(X)$，中间没有 $u_i(X)$
- 所有锁之后必须跟着对同一元素的解锁操作

### 4.2 相容性矩阵 (Compatibility Matrix)

| 已持有 →<br>请求 ↓ | S   | X   |
| ------------------ | --- | --- |
| **S**              | Yes | No  |
| **X**              | No  | No  |

**锁授予规则**：当且仅当对于每一行 R，如果其他事务已经在 X 上持有 R 模式的锁，且对应列为"Yes"，才能以该模式授予锁。

**示例**：

| Step | T1                        | T2              | A   | B   |
| ---- | ------------------------- | --------------- | --- | --- |
| 1    | sl1(A); Read(A)           |                 |     |     |
| 2    |                           | sl2(A); Read(A) |     |     |
| 3    |                           | sl2(B); Read(B) |     |     |
| 4    | xl1(B) **Denied**         |                 |     |     |
| 5    |                           | u2(A); u2(B)    |     |     |
| 6    | xl1(B); Read(B); Write(B) |                 |     |     |
| 7    | u1(A); u1(B)              |                 |     |     |

T1 和 T2 可以同时持有 A 的共享锁，提高并发度。

### 4.3 锁的升级 (Upgrading Locks)

**场景**：事务 T 首先读取 X 和 B，执行计算后可能需要写入 B。

**选项1：直接请求排他锁**

- T 最初就在 B 上请求排他锁 → 可能被拒绝（其他事务持有共享锁）→ 完成更晚

**选项2：锁升级**

- T 先请求共享锁读 B，需要时再升级为排他锁

**示例（使用升级）：**

| Step | T1                | T2              |
| ---- | ----------------- | --------------- |
| 1    | sl1(A); Read(A)   | sl2(A); Read(A) |
| 2    | sl1(B); Read(B)   | sl2(B); Read(B) |
| 3    | xl1(B) **Denied** |                 |
| 4    |                   | u2(A); u2(B)    |
| 5    | xl1(B); Write(B)  |                 |
| 6    | u1(A); u1(B)      |                 |

> 使用升级策略通常比直接使用排他锁**更早完成**。

**⚠️ 注意**：不加区分地使用升级会引入新的死锁源！

如果 T1 和 T2 都读取和写入 A，且都使用升级方法：

- T1: sl1(A); T2: sl2(A)（都获得共享锁）
- T1: xl1(A) **Denied**（T2 持有共享锁）
- T2: xl2(A) **Denied**（T1 持有共享锁）
- → **死锁！**

### 4.4 更新锁 (Update Locks, U锁)

**解决方案**：使用更新锁避免死锁。

- 更新锁 $ul_i(X)$：赋予事务 $T_i$ 读取 X 而不写入 X 的权限
- 只有更新锁可以在稍后升级为写锁；读锁不能被升级
- **非对称相容性矩阵**：

| 已持有 →<br>请求 ↓ | S   | X   | U   |
| ------------- | --- | --- | --- |
| **S**         | Yes | No  | Yes |
| **X**         | No  | No  | No  |
| **U**         | No  | No  | No  |


**示例（使用U锁避免死锁）：**

| Step | T1                      | T2                      |
| ---- | ----------------------- | ----------------------- |
| 1    | ul1(A); Read(A)         | ul2(A) **Denied**       |
| 2    | xl1(A); Write(A); u1(A) | ul2(A); Read(A)         |
| 3    |                         | xl2(A); Write(A); u2(A) |

T2 请求 ul2(A) 被拒绝（T1 持有 ul1(A)），T2 等待。T1 完成后 T2 获得锁。不会死锁 ✓

### 4.5 死锁的处理

**两类方法：**

#### (1) 死锁的预防

| 方法           | 说明                                                         | 问题                                             |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------ |
| **一次封锁法** | 要求每个事务必须一次将所有要使用的数据全部加锁               | 降低系统并发度；难于事先精确确定封锁对象         |
| **顺序封锁法** | 预先对数据对象规定一个封锁顺序，所有事务都按这个顺序实行封锁 | 维护成本高；很难事先确定每一个事务要封锁哪些对象 |

> 结论：预防死锁的策略并不很适合数据库的特点。DBMS 更普遍采用诊断并解除死锁的方法。

#### (2) 死锁的诊断与解除

**超时法**：

- 如果一个事务的等待时间超过了规定的时限，就认为发生了死锁
- 优点：实现简单；缺点：可能误判，或时限太长不能及时发现

**等待图法（更普遍）**：

- 用事务等待图 $G = (T, U)$ 动态反映所有事务的等待情况
  - T：结点集合，每个结点表示运行中的事务
  - U：边集合，每条边表示事务等待情况（T1→T2 表示 T1 等待 T2）
- 并发控制子系统定期生成事务等待图，检测回路
- 如果发现图中存在回路 → 系统中出现了死锁

**解除死锁**：

- 选择一个处理死锁代价最小的事务，将其撤消
- 释放此事务持有的所有锁，使其它事务能继续运行
