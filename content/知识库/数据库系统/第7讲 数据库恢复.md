## 7.1 数据库故障概述

### 7.1.1 故障的分类

| 故障类型 | 原因 | 影响范围 | 示例 |
|--------|--------|--------|--------|
| **事务故障** | 逻辑错误 | 单个事务 | 当机故障、死锁 |
| **系统故障** | 硬件/软件错误 | 整个DBMS | 当机崩溃、OS故障 |
| **媒体故障** | 硬件损坏 | 数据库 | 硬盘损坏、磁学损伤 |

### 7.1.2 故障的影响

**事务故障影响**：
- 数据不一致（未完成的更新）
- 资源泄漏（未释放的锁）
- 破坏完整性约束

**系统故障影响**：
- 内存中数据丢失
- 文件损坏
- 进程终止

**媒体故障影响**：
- 数据永久性丢失
- 整个数据库可能挂起

### 7.1.3 恢复目标

1. **原子性**：事务要么全部执行，要么全部撤销
2. **一致性**：事务执行前后，数据库状态一致
3. **持久性**：成功完成的事务，其更新是永久的
4. **隔离性**：多个事务并发执行不相互干扰

## 7.2 事务恢复技术

### 7.2.1 日志文件（Transaction Log）

**作用**：记录所有事务的操作，用于事务恢复

**结构**：
- 日志文件是顺序写入的
- 每个记录包含事务ID、操作类型、数据前值、数据后值
- 检点（Checkpoint）记录系统状态

**写前日志协议（WAL）**：
> 在修改数据库之前，必须先将操作写入日志文件

**步骤**：
1. 将更新前的数据（undo）写入日志
2. 将更新后的数据（redo）写入日志
3. 通知日志文件已写入磁盘
4. 执行实际的数据更新

### 7.2.2 恢复算法

**UNDO操作**：撤销未提交事务的更新
- 使用日志中的undo信息
- 逆序执行（最后一个操作最先撤销）

**REDO操作**：重做已提交事务的更新
- 使用日志中的redo信息
- 顺序执行（按时间顺序）

**示例**：
```
日志记录：
[T1 Start]
[T1, A, 1000, 950]  -- A从1000变为950
[T1, B, 2000, 2050] -- B从2000变为2050
[T1 Commit]

恢复过程：
- 找到T1的Commit记录
- 执行REDO：A=950, B=2050
```

### 7.2.3 检点（Checkpoint）

**作用**：
1. 减少恢复时需要扫描的日志数量
2. 提高恢复效率
3. 滚动已完成事务的日志

**检点过程**：
1. 暂停接收新的事务开始请求
2. 等待当前运行的事务完成
3. 将内存中的数据刷入磁盘
4. 在日志文件中写入检点记录
5. 恢复接收新的事务开始请求

**检点重启**：
数据库重启时：
1. 从最近的检点开始扫描日志
2. 执行REDO重做所有已提交事务
3. 执行UNDO撤销未提交事务

## 7.3 备份与恢复

### 7.3.1 备份策略

**完全备份**：
- 备份整个数据库
- 需要较多存储空间
- 恢复简单快速
- **频率**：每天或每周一次

**增量备份**：
- 只备份自上次备份以来的变化
- 节省存储空间
- 恢复需要多个备份
- **频率**：每天或每小时

**差分备份**：
- 备份自上次完全备份以来的变化
- **频率**：每周一次完全备份，每天差分备份

### 7.3.2 备份类型

| 类型 | 说明 | 优点 | 缺点 |
|--------|--------|--------|--------|
| 冷备份 | 数据库关闭时备份 | 一致性好 | 停止服务 |
| 热备份 | 数据库运行时备份 | 不中断服务 | 可能不一致 |
| 照片备份 | 使用快照技术 | 快速、影响小 | 需特殊硬件 |

### 7.3.3 数据库恢复

**完全恢复**：
```sql
-- MySQL完全恢复
mysql -u username -p database_name < backup.sql

-- PostgreSQL完全恢复
pg_restore -U username -d database_name backup.dump

-- Oracle完全恢复
RMAN> RESTORE DATABASE;
RMAN> RECOVER DATABASE;
```

**时间点恢复**（PITR）：
```sql
-- PostgreSQL PITR
-- 在recovery.conf中需要指定备份和WAL日志
restore_command = 'cp /path/to/wal/%f %p'
recovery_target_time = '2024-01-15 10:30:00'
```

## 7.4 高可用性技术

### 7.4.1 备份双机同步

**主从复制**：
```sql
-- MySQL主从复制
-- 主机配置
server-id = 1
log-bin = mysql-bin
binlog-do-db = mydb

-- 从机配置
server-id = 2
replicate-do-db = mydb

-- 启动复制
CHANGE MASTER TO
    MASTER_HOST = 'master_host',
    MASTER_USER = 'replication_user',
    MASTER_PASSWORD = 'password',
    MASTER_LOG_FILE = 'mysql-bin.000001',
    MASTER_LOG_POS = 4;
START SLAVE;
```

**双机热备**：
```sql
-- Oracle Data Guard
-- 主库配置
LOG_ARCHIVE_CONFIG = 'DG_CONFIG=(primary_db,standby_db)'
LOG_ARCHIVE_DEST_2 = 'SERVICE=standby_db ASYNC VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME=standby_db'

-- 备机配置
LOG_ARCHIVE_CONFIG = 'DG_CONFIG=(primary_db,standby_db)'
LOG_ARCHIVE_DEST_2 = 'SERVICE=primary_db ASYNC VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME=primary_db'
```

### 7.4.2 集群技术

**MySQL Cluster**：
```sql
-- 多节点集群
[NDBD]
NodeId = 1
HostName = 192.168.1.1
DataDir = /var/lib/mysql-cluster

[NDBD]
NodeId = 2
HostName = 192.168.1.2
DataDir = /var/lib/mysql-cluster

[MYSQLD]
NodeId = 3
HostName = 192.168.1.3

[MYSQLD]
NodeId = 4
HostName = 192.168.1.4
```

**PostgreSQL流复制**：
```sql
-- 主机配置
wal_level = replica
max_wal_senders = 10
hot_standby = on

-- 备机启动
pg_basebackup -h primary_host -D /var/lib/postgresql/data -U replication_user -P -R
```

## 7.7 宽底恢复（Disaster Recovery）

### 7.7.1 DR计划

**RTO（Recovery Time Objective）**：
- 允许的最大停机时间
- 例：4小时

**RPO（Recovery Point Objective）**：
- 允许的最大数据丢失
- 例：1小时

### 7.7.2 DR实施

```sql
-- 跨地区备份
-- 主数据中心
BACKUP DATABASE TO DISK = '/dc1/backup/full.bak'
WITH COMPRESSION, ENCRYPTION;

-- 备用数据中心
COPY '/dc1/backup/full.bak' TO '/dc2/backup/full.bak';
RESTORE DATABASE FROM '/dc2/backup/full.bak';
```
