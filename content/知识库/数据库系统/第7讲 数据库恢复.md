# 第7讲 数据库恢复

## 1. 故障模式与模型 (17.1)

### 1.1 故障类型

| 故障类型               | 说明                               | 解决方案                      |
| ---------------------- | ---------------------------------- | ----------------------------- |
| **错误的数据输入**     | 源头数据质量问题                   | 约束、触发器                  |
| **介质故障**           | 局部故障（奇偶校验）；严重硬件崩溃 | RAID 磁盘阵列、归档、冗余副本 |
| **灾难性故障**         | 大规模存储丢失                     | 异地备份、分布式副本          |
| **系统故障（软崩溃）** | 导致数据库不一致                   | 非易失性日志 + 恢复操作       |

### 1.2 故障模型假设

1. **可恢复性**：面临系统故障时必须保护数据
   - 日志：undo、redo、undo/redo
   - 备份：RAID、异地备份（完全/增量式）
2. **并发正确性**：数据不能因为同时执行多个查询或修改而损坏

## 2. 事务 (Transactions)

### 2.1 为什么需要事务

数据库系统通常同时被许多用户/进程访问，不良交互会导致数据不一致。

**示例**：Sells(bar, beer, price) 关系，Joe's Bar 卖 $2.50 的 Bud 和 $3.00 的 Miller。

- Sally 查询 Joe's Bar 的最高价和最低价：`SELECT MAX(price)` 和 `SELECT MIN(price)`
- Joe 同时执行删除 Bud 和 Miller，插入 Heineken ($3.50)

不同执行顺序的问题：

| 执行顺序             | 问题                                |
| -------------------- | ----------------------------------- |
| (max)(min)(del)(ins) | MIN < MAX，看似正常但实际已不一致   |
| (del)(max)(ins)(min) | MAX 为 NULL，但 MIN 为 3.50，矛盾！ |

**解决**：将 Sally 和 Joe 的操作各自放入事务（Transaction）中，保证每个事务看到一个一致的数据库状态。

### 2.2 ACID 特性

| 特性   | 英文        | 说明                                         |
| ------ | ----------- | -------------------------------------------- |
| 原子性 | Atomicity   | 事务要么全部执行，要么全部不执行             |
| 一致性 | Consistency | 事务执行前后，数据库完整性约束和业务逻辑正确 |
| 隔离性 | Isolation   | 对用户而言，似乎只有一个进程在执行           |
| 持久性 | Durability  | 事务产生的影响在系统崩溃后依然存在           |

### 2.3 事务定义

**显式声明**：

```sql
BEGIN TRANSACTION
    SQL statement 1
    SQL statement 2
    ...
COMMIT    -- 成功完成，修改永久保存

BEGIN TRANSACTION
    SQL statement 1
    SQL statement 2
    ...
ROLLBACK   -- 中止，对数据库无影响
```

**隐式声明**：每一条 SQL 查询或修改语句都是一个事务。

### 2.4 事务的基本操作

三个地址空间：

| 地址空间             | 说明               |
| -------------------- | ------------------ |
| **事务局部地址空间** | 隔离/独占（local） |
| **数据库缓冲区**     | 可能共享（memory） |
| **磁盘块空间**       | 可能共享（disk）   |

四个基本操作：

| 操作          | 说明                                           |
| ------------- | ---------------------------------------------- |
| `INPUT(x)`    | 包含 x 的块从 disk → buffer                    |
| `OUTPUT(x)`   | 包含 x 的块从 buffer → disk                    |
| `READ(x, t)`  | 如需则先 INPUT(x)，再将 buffer 中 x 的值读入 t |
| `WRITE(x, t)` | 如需则先 INPUT(x)，再将 t 的值写入 buffer 中 x |

> **注意**：一个数据库元素绝不会大于一个磁盘块。

**示例**：约束 A = B，初始 A=8, B=8

```
T1: READ(A, t);    t ← 8
    t ← t×2;      t ← 16
    WRITE(A, t);   A在buffer中变为16
    READ(B, t);    t ← 8
    t ← t×2;      t ← 16
    WRITE(B, t);   B在buffer中变为16
    OUTPUT(A);     A写入磁盘
    OUTPUT(B);     B写入磁盘
```

执行过程状态变化：

| Step | Action     | t   | Mem-A | Mem-B | Disk-A | Disk-B |
| ---- | ---------- | --- | ----- | ----- | ------ | ------ |
| 1    | READ(A,t)  | 8   | 8     | —     | 8      | 8      |
| 2    | t := t×2   | 16  | 8     | —     | 8      | 8      |
| 3    | WRITE(A,t) | 16  | 16    | —     | 8      | 8      |
| 4    | READ(B,t)  | 8   | 16    | 8     | 8      | 8      |
| 5    | t := t×2   | 16  | 16    | 8     | 8      | 8      |
| 6    | WRITE(B,t) | 16  | 16    | 16    | 8      | 8      |
| 7    | OUTPUT(A)  | 16  | 16    | 16    | 16     | 8      |
| 8    | OUTPUT(B)  | 16  | 16    | 16    | 16     | 16     |

> **注意**：直到 OUTPUT 执行前，磁盘上的数据并未被修改！

**原子性问题**：如果故障发生在 OUTPUT(A) 之后、OUTPUT(B) 之前，则磁盘上 A=16, B=8，违反了 A=B 的约束。

## 3. Undo 日志 (17.2)

### 3.1 基本概念

Undo 日志通过**撤销**（Undo）崩溃前未完成事务的影响来修复数据库状态。

**日志记录类型**：

| 记录          | 说明                                       |
| ------------- | ------------------------------------------ |
| `<START Ti>`  | 事务 Ti 已开始                             |
| `<COMMIT Ti>` | 事务 Ti 已成功完成                         |
| `<ABORT Ti>`  | 事务 Ti 中止                               |
| `<Ti, X, v>`  | 事务 Ti 更改了数据库元素 X，其**旧值**为 v |

> Undo 日志只记录旧值，不记录新值。恢复时通过旧值回滚。

### 3.2 Undo 日志规则

**U1**：如果事务 T 修改了数据库元素 X，必须在将 X 的新值写入磁盘之前，将 `<T, X, v>` 写入磁盘。
→ 先写日志，再写数据（WAL：预写式日志）

**U2**：如果事务提交，必须在事务修改的所有数据库元素写入磁盘之后，才将 `<COMMIT T>` 写入磁盘。
→ 先写数据，再写 commit 日志

**写入磁盘顺序**：

1. 修改的日志记录
2. 更改后的数据库元素本身
3. commit 日志记录

### 3.3 Undo 日志示例

沿用前面 T1（A←A×2, B←B×2）的例子，初始 A=8, B=8：

| Step | Action     | t   | Mem-A | Mem-B | Disk-A | Disk-B | Log           |
| ---- | ---------- | --- | ----- | ----- | ------ | ------ | ------------- |
| 1    |            |     |       |       |        |        | `<START T1>`  |
| 2    | READ(A,t)  | 8   | 8     | —     | 8      | 8      |               |
| 3    | t := t×2   | 16  | 8     | —     | 8      | 8      |               |
| 4    | WRITE(A,t) | 16  | 16    | —     | 8      | 8      | `<T1, A, 8>`  |
| 5    | READ(B,t)  | 8   | 16    | 8     | 8      | 8      |               |
| 6    | t := t×2   | 16  | 16    | 8     | 8      | 8      |               |
| 7    | WRITE(B,t) | 16  | 16    | 16    | 8      | 8      | `<T1, B, 8>`  |
| 8    | FLUSH LOG  |     |       |       |        |        |               |
| 9    | OUTPUT(A)  | 16  | 16    | 16    | 16     | 8      |               |
| 10   | OUTPUT(B)  | 16  | 16    | 16    | 16     | 16     |               |
| 11   |            |     |       |       |        |        | `<COMMIT T1>` |
| 12   | FLUSH LOG  |     |       |       |        |        |               |

### 3.4 Undo 恢复规则

系统崩溃后恢复步骤：

1. **识别未完成事务集合 S**：日志中有 `<START Ti>` 但没有 `<COMMIT Ti>` 或 `<ABORT Ti>` 的事务
2. **反向扫描日志**（最新 → 最早），对每个 `<Ti, X, v>`：
   - 如果 Ti ∈ S，则执行 `WRITE(X, v)` 和 `OUTPUT(X)`（撤销到旧值）
3. **对每个 Ti ∈ S**，向日志写入 `<ABORT Ti>` 记录

> Undo 是幂等的（idempotent）：重复撤销多次与撤销一次效果相同。

### 3.5 检查点 (Checkpoint)

**问题**：恢复时需要扫描整个日志，效率低下。

**简单检查点步骤**：

1. 停止接受新事务
2. 等待所有当前活动事务提交或中止
3. 将日志 flush 到磁盘
4. 写入 `<CKPT>` 记录并 flush 日志
5. 恢复接受新事务

**非静止检查点**（允许新事务在检查点期间进入）：

1. 写入 `<START CKPT(T1, …, Tk)>`（T1…Tk 为当前活跃事务），flush 日志
2. 等待 T1…Tk 全部完成，但不禁止其他事务开始
3. 写入 `<END CKPT>` 并 flush 日志

恢复时：

- 如果先遇到 `<END CKPT>`，只需扫描到匹配的 `<START CKPT>` 即可
- 如果先遇到 `<START CKPT>`，说明崩溃发生在检查点期间，需往前找到上一个 `<END CKPT>`

## 4. Redo 日志 (17.3)

### 4.1 为什么需要 Redo 日志

Undo 日志的问题：必须在事务提交之前将所有更改的数据写入磁盘，磁盘 I/O 过多。

**Redo 日志**：延迟修改（deferred modification），将所有修改保留在内存中直到提交，提交后再写入磁盘。崩溃后通过**重做**（Redo）已提交事务的更改来恢复。

### 4.2 Redo 日志规则

**R1**：在修改磁盘上的任何数据库元素 X 之前，必须将 `<Ti, X, w>`（w 为新值）和 `<COMMIT Ti>` 全部写入磁盘。

**写入磁盘顺序**：

1. 更新记录（新值）
2. COMMIT 日志记录
3. 更改的数据库元素本身

→ Redo 日志 = 先写日志，再写数据，且 commit 记录在数据之前。

> Redo 日志只记录**新值**，不记录旧值。

### 4.3 Redo 日志示例

| Step | Action     | t   | Mem-A | Mem-B | Disk-A | Disk-B | Log          |
| ---- | ---------- | --- | ----- | ----- | ------ | ------ | ------------ |
| 1    |            |     |       |       |        |        | `<START T>`  |
| 2    | READ(A,t)  | 8   | 8     | —     | 8      | 8      |              |
| 3    | t := t×2   | 16  | 8     | —     | 8      | 8      |              |
| 4    | WRITE(A,t) | 16  | 16    | —     | 8      | 8      | `<T, A, 16>` |
| 5    | READ(B,t)  | 8   | 16    | 8     | 8      | 8      |              |
| 6    | t := t×2   | 16  | 16    | 8     | 8      | 8      |              |
| 7    | WRITE(B,t) | 16  | 16    | 16    | 8      | 8      | `<T, B, 16>` |
| 8    |            |     |       |       |        |        | `<COMMIT T>` |
| 9    | FLUSH LOG  |     |       |       |        |        |              |
| 10   | OUTPUT(A)  | 16  | 16    | 16    | 16     | 8      |              |
| 11   | OUTPUT(B)  | 16  | 16    | 16    | 16     | 16     |              |

### 4.4 Redo 恢复规则

1. **识别已提交事务集合 S**：日志中有 `<COMMIT Ti>` 的事务
2. **正向扫描日志**（最早 → 最新），对每个 `<Ti, X, w>`：
   - 如果 Ti ∈ S，则将新值 w 写入磁盘（无论是否已经存储）
3. **对每个 Ti ∉ S**，写入 `<ABORT Ti>` 记录

> **推论**：除非日志中有 `<COMMIT T>` 记录，否则事务 T 的任何更改都未写入磁盘，可以直接忽略。

### 4.5 Redo 检查点

**非静止检查点步骤**：

1. 写入 `<START CKPT(T1, …, Tk)>` 并 flush 日志
2. 将 buffer 中在 `<START CKPT>` 之前已提交的数据页逐一写入磁盘
3. 写入 `<END CKPT>` 并 flush 日志

> 与 Undo 不同，Redo 检查点需要将**已提交事务**的脏页（dirty pages）写入磁盘，因为提交后数据可能很久才 flush。

## 5. Undo/Redo 日志 (17.4)

### 5.1 为什么需要 Undo/Redo 日志

| 日志类型  | 缺点                                               |
| --------- | -------------------------------------------------- |
| Undo 日志 | 数据在事务完成后立即写入磁盘，磁盘 I/O 数量多      |
| Redo 日志 | 将所有修改的块保留在内存中直到提交，占用大量缓冲区 |

**Undo/Redo 日志**：记录新旧两个值，提供更大灵活性。

### 5.2 Undo/Redo 日志记录

记录格式：`<Ti, X, v, w>`

- v：旧值
- w：新值

**UR1**：修改磁盘上的 X 之前，`<Ti, X, v, w>` 必须出现在磁盘上（WAL）。
→ 页面 X 可以在 Ti 提交之前或之后 flush。

**UR2**：`<COMMIT T>` 记录一旦出现在日志中，必须尽快 flush 到磁盘。

### 5.3 Undo/Redo 示例

| Step | Action     | t   | Mem-A | Mem-B | Disk-A | Disk-B | Log             |
| ---- | ---------- | --- | ----- | ----- | ------ | ------ | --------------- |
| 1    |            |     |       |       |        |        | `<START T>`     |
| 2    | READ(A,t)  | 8   | 8     | —     | 8      | 8      |                 |
| 3    | t := t×2   | 16  | 8     | —     | 8      | 8      |                 |
| 4    | WRITE(A,t) | 16  | 16    | —     | 8      | 8      | `<T, A, 8, 16>` |
| 5    | READ(B,t)  | 8   | 16    | 8     | 8      | 8      |                 |
| 6    | t := t×2   | 16  | 16    | 8     | 8      | 8      |                 |
| 7    | WRITE(B,t) | 16  | 16    | 16    | 8      | 8      | `<T, B, 8, 16>` |
| 8    | FLUSH LOG  |     |       |       |        |        |                 |
| 9    | OUTPUT(A)  | 16  | 16    | 16    | 16     | 8      |                 |
| 10   |            |     |       |       |        |        | `<COMMIT T>`    |
| 11   | FLUSH LOG  |     |       |       |        |        |                 |
| 12   | OUTPUT(B)  | 16  | 16    | 16    | 16     | 16     |                 |

> 注意：步骤 10（COMMIT）可以在步骤 9 之前、之后或之间，灵活度高。

### 5.4 Undo/Redo 恢复策略

1. **反向扫描**（最新 → 最早）：
   - 构建已提交事务集合 S
   - 撤销不在 S 中的事务（按最新优先顺序）
2. **正向扫描**（最早 → 最新）：
   - 重做 S 中的事务（按最早优先顺序）

### 5.5 Undo/Redo 检查点

1. 写入 `<START CKPT(T1, …, Tk)>` 并 flush 日志
2. 将所有脏缓冲区（dirty buffers）写入磁盘（包括已提交和未提交事务的）
3. 写入 `<END CKPT>` 并 flush 日志

> 与 Redo 不同，Undo/Redo 检查点需要刷新**所有**脏缓冲区。

## 6. 防范介质故障 (17.5)

### 6.1 介质故障

介质故障指非易失性存储丢失（如磁盘损坏）。仅靠日志无法恢复，需要制作数据副本。

### 6.2 解决方案

| 方案                   | 方法                  | 说明                                         |
| ---------------------- | --------------------- | -------------------------------------------- |
| **三重模块冗余**       | 独立磁盘保留 3 个副本 | Output(X) 三次写入；Input(X) 三次输入 + 投票 |
| **冗余写入，单一读取** | N 个副本，写入 N 次   | 读取时若检测到不良数据则尝试另一个副本       |
| **数据库转储 + 日志**  | 定期备份 + 日志重做   | 从备份恢复，再用日志 redo 到最新状态         |

### 6.3 数据库转储 + 日志

- 定期对数据库做完整备份（转储）
- 备份后使用日志中的 redo 条目保持数据最新
- 当活动数据库丢失时，从备份恢复 + 日志重做

> **问题**：什么时候可以丢弃日志？
> 当日志中记录的所有事务对应的数据都已经安全备份后，该部分日志可以丢弃。
