在数据库管理系统中，日志（Logging）是保证事务 **ACID** 特性（特别是原子性和持久性）的核心机制。根据处理数据的逻辑不同，主要分为 **Undo日志**、**Redo日志** 和 **Undo/Redo混合日志**。

### 一、 Undo日志 (Undo Logging)

**1. 原理** Undo日志的核心原理是通过记录被修改属性的**旧值**，在系统发生崩溃或事务回滚时，通过撤销（Undoing）未完成事务对磁盘产生的影响来修复数据库状态。

**2. 基本规则 (WAL 协议)**

- **U1**：如果事务 $T$ 修改了数据库元素 $X$，则必须在将 $X$ 的**新值**写入磁盘之前，将形如 $<T, X, v>$（$v$ 为旧值）的日志记录写入磁盘。
- **U2**：如果事务提交，则必须在事务修改的**所有**数据库元素都已写入磁盘之后，才将其 `<COMMIT T>` 记录写入磁盘。

**3. 事务执行过程**

1. 事务 $T$ 开始，写入 `<START T>` 到日志内存。
2. 执行 `WRITE(X, v)`，将 $X$ 修改为新值，同时在日志中记录旧值 $v$。
3. **FLUSH LOG**：将记录了旧值的日志刷新到磁盘。
4. **OUTPUT(X)**：将修改后的数据写入磁盘物理区。
5. 写入 `<COMMIT T>` 并刷新日志。

**4. 故障恢复算法 (伪代码)**

```
# 从日志末尾向前反向扫描
S = {所有具有 <START T> 但没有 <COMMIT T> 或 <ABORT T> 的事务}
For each log record <T, X, v> in reverse order:
    If T is in S:
        Write(X, v) # 将数据恢复为旧值
        Output(X)    # 确保写回磁盘
For each T in S:
    Write <ABORT T> to log
```

---

### 二、 Redo日志 (Redo Logging)

**1. 原理** Redo日志通过记录被修改属性的**新值**，确保即使已提交事务的更改尚未写入磁盘，也可以在系统崩溃后通过重做（Redoing）这些更改来保证持久性。它允许更改后的数据暂时只驻留在内存中以节省磁盘 I/O。

**2. 基本规则**

- **R1**：在修改磁盘上的任何数据元素 $X$ 之前，必须将有关该修改的所有日志记录（包括更新记录 $<T, X, w>$ 和 `<COMMIT T>` 记录）全部写入磁盘。

**3. 事务执行过程**

1. 事务 $T$ 开始，写入 `<START T>`。
2. 执行 `WRITE(X, w)`，在日志中记录新值 $w$。
3. **FLUSH LOG**：将更新记录写入磁盘。
4. 写入 `<COMMIT T>` 并再次刷新日志。
5. **OUTPUT(X)**：在事务提交后的某个时间点，异步将数据写入磁盘。

**4. 故障恢复算法 (伪代码)**

```
# 识别已提交事务
S = {所有具有 <COMMIT T> 记录的事务}
# 从日志开头正向扫描（最早 -> 最新）
For each log record <T, X, w> in forward order:
    If T is in S:
        Write(X, w) # 将数据更新为新值
        Output(X)   # 确保生效
For each uncommitted transaction T:
    Write <ABORT T> to log
```

---

### 三、 Undo/Redo日志 (Undo/Redo Logging)

**1. 原理** Undo/Redo日志是两者的结合，其日志记录格式为 **$<T, X, v, w>$**，同时记录旧值 $v$ 和新值 $w$。它提供了最大的灵活性：允许在事务提交前将数据写入磁盘（依靠 Undo 恢复），也允许事务提交后不立即写入磁盘（依靠 Redo 保证持久性）。

**2. 基本规则**

- **UR1**：在修改磁盘上任何数据元素 $X$ 之前，更新记录 $<T, X, v, w>$ 必须先刷新到磁盘（WAL）。
- **UR2**：`<COMMIT T>` 记录一旦出现在日志中，必须尽快刷新至磁盘。

**3. 事务执行过程**

1. 事务开始，在内存中准备记录 $<T, X, v, w>$。
2. **FLUSH LOG**：将混合日志刷新到磁盘。
3. **OUTPUT(X) 或 COMMIT**：此时数据写入磁盘和事务提交记录落地的顺序是**任意的**，非常灵活。

**4. 故障恢复算法 (伪代码)**

```
# 1. 扫描日志确定状态
Committed_S = {所有具有 <COMMIT T> 的事务}
Uncommitted_U = {所有只有 <START T> 的事务}

# 2. Undo 阶段：从后向前扫描
For each record <T, X, v, w> in reverse order:
    If T is in Uncommitted_U:
        Write(X, v) # 恢复旧值

# 3. Redo 阶段：从前向后扫描
For each record <T, X, v, w> in forward order:
    If T is in Committed_S:
        Write(X, w) # 应用新值

# 4. 清理
For each T in Uncommitted_U:
    Write <ABORT T>
```

---

### 四、 三种日志的主要区别

|特性|Undo 日志|Redo 日志|Undo/Redo 日志|
|:--|:--|:--|:--|
|**记录内容**|旧值 (v)|新值 (w)|旧值与新值 (v, w)|
|**磁盘写入顺序**|日志 -> 数据 -> COMMIT|日志 -> COMMIT -> 数据|日志 -> (数据/COMMIT 顺序任意)|
|**Commit约束**|提交前数据必须全部落盘|提交前数据绝不能落盘|无约束，最灵活|
|**恢复方向**|仅反向扫描|仅正向扫描|先反向 Undo，再正向 Redo|
|**性能/开销**|增加磁盘 I/O（提交需写数据）|增加内存消耗（需保留块直到提交）|日志记录较长，但系统整体效率最高|

**总结：** **Undo日志**通过强制先写数据来保证安全性，但性能受限；**Redo日志**通过推迟数据写入来提高性能，但依赖 COMMIT 记录的可靠性；**Undo/Redo日志**（如 MySQL InnoDB 所采用的 WAL 模式）结合了两者优点，是现代数据库的主流选择。此外，所有日志恢复操作都具有**幂等性**，即恢复期间再次崩溃并重新执行恢复程序，结果依然正确。

# 检查点
在数据库恢复机制中，引入**检查点（Checkpoint）**的主要目的是为了提高恢复效率，避免在系统崩溃后需要扫描和处理整个庞大的日志文件。

如果考虑检查点，三种日志类型的操作过程和恢复逻辑会发生显著变化：

### 1. 检查点的基本概念与分类

- **为什么需要？**：日志是不断追加的。如果没有检查点，恢复系统必须从日志开头扫描到结尾，这在运行了一年的系统中是不可接受的。
- **静止检查点（Quiescent Checkpoint）**：最简单的形式。它要求系统停止接受新事务，等待当前所有活跃事务提交或中止，将日志和数据全部刷新到磁盘，写入 `<CKPT>` 记录，然后才恢复运行。
- **非静止检查点（Nonquiescent Checkpoint）**：现代数据库常用。它允许在设置检查点期间有新事务进入，不会导致系统停机。

---

### 2. 不同日志类型的检查点机制

#### **Undo 日志的检查点**

由于 Undo 日志要求提交前数据必须落盘，其非静止检查点步骤如下：

1. 向日志写入 `<START CKPT (T1, ..., Tk)>`，其中 $T_i$ 是当前活跃事务。
2. 等待 $T_1, \dots, T_k$ 全部完成（提交或中止）。
3. 一旦这些事务完成，写入 `<END CKPT>` 并刷新日志。

- **恢复影响**：如果恢复时最先遇到 `<END CKPT>`，说明之前的事务都已完成，只需扫描到对应的 `<START CKPT>` 即可停止。

#### **Redo 日志的检查点**

Redo 日志允许提交后数据暂留内存，因此检查点需要确保已提交的数据真正落地：

1. 写入 `<START CKPT (T1, ..., Tk)>` 并刷新日志。
2. **关键步骤**：将缓冲区中所有在 `<START CKPT>` 之前已经提交的事务修改的数据，一页一页地搬进物理磁盘。
3. 写入 `<END CKPT>` 并刷新日志。

- **恢复影响**：如果崩溃前最后一条是 `<END CKPT>`，则只需重做在 `<START CKPT>` 中列出的活跃事务以及之后开始的事务。

#### **Undo/Redo 日志的检查点**

由于混合日志兼具两者的灵活性，其检查点过程最为高效：

1. 写入 `<START CKPT (T1, ..., Tk)>` 并刷新日志。
2. **强制刷新**：将内存中所有的**脏缓冲区（Dirty Buffers）**写入磁盘（无论对应的事务是否已提交）。
3. 写入 `<END CKPT>` 并刷新日志。

---

### 3. 考虑检查点后的故障恢复过程

引入检查点后，恢复子系统的扫描范围被大大缩小：

|日志类型|恢复扫描方向|检查点对恢复的帮助|
|:--|:--|:--|
|**Undo**|仅反向扫描|遇到 `<END CKPT>` 后，只需扫到对应的 `<START CKPT>`，因为该点之前的日志可以安全删除。|
|**Redo**|正向扫描|如果遇到 `<END CKPT>`，只需回头找到对应的 `<START CKPT>`，从列出的最早活跃事务的 `<START Ti>` 开始正向重做。|
|**Undo/Redo**|先反向再正向|只需要回溯到最近的一个完成的 `<END CKPT>` 对应的 `<START CKPT>` 记录即可，该点之前的数据保证已全部落盘。|

### 4. 特殊情况：检查点期间崩溃

如果系统在写入 `<START CKPT>` 之后但在写入 `<END CKPT>` 之前崩溃：

- **处理逻辑**：此时不能只依靠当前的检查点信息。恢复系统必须回溯到**上一个**成功的 `<END CKPT>`，并找到与之对应的 `<START CKPT>` 开始恢复过程。

**总结**： 引入检查点后，数据库可以定期地将内存中的状态同步到磁盘，并以此为界标标记出“安全区”。一旦发生故障，恢复系统只需处理检查点之后的“不稳定区”，极大地缩短了数据库的重启时间。
