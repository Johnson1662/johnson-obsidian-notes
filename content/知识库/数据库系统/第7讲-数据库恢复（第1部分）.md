## 数据库恢复概述

### 为什么需要数据库恢复？

数据库系统面临各种故障威胁：
1. **系统故障**：断电、硬件故障、软件崩溃
2. **事务故障**：事务执行失败
3. **介质故障**：磁盘损坏、数据丢失
4. **人为错误**：误删除、误操作

### 故障模型

#### 处理器故障
- CPU故障
- 内存故障

#### 存储故障
- 磁盘故障
- 数据损坏

### 数据保护的两个要求

#### 1. 系统故障时的数据保护
- **日志记录**（undo、redo、undo/redo）
- **备份**（RAID、归档）

#### 2. 并发操作的数据一致性
- 多个查询或数据库修改同时执行时
- 数据不能被损坏

## 事务的概念

### 什么是事务？

**事务**是数据库操作的逻辑单位，具有ACID特性：

#### ACID特性

1. **原子性（Atomicity）**
   - 事务中的所有操作要么全部执行，要么全部不执行
   - 不允许部分执行

2. **一致性（Consistency）**
   - 事务执行前后，数据库处于一致状态
   - 满足所有完整性约束

3. **隔离性（Isolation）**
   - 并发执行的事务相互隔离
   - 每个事务感觉不到其他事务的存在

4. **持久性（Durability）**
   - 已提交事务的结果永久保存
   - 即使系统故障也不会丢失

## 恢复的基本原理

### 恢复的目标

1. **事务的原子性**：未完成的事务要回滚
2. **事务的持久性**：已提交的事务不能丢失
3. **数据的一致性**：数据库保持一致状态

### 恢复的基本方法

#### 1. 日志记录
- 记录所有数据库修改操作
- 用于重做或撤销操作

#### 2. 备份
- 定期备份数据库
- 用于介质故障恢复

#### 3. 检查点
- 定期建立一致性点
- 减少恢复时间

## 日志的类型

### 1. 撤销日志（Undo Logging）

**撤销日志**记录事务修改前的数据值，用于回滚未提交的事务。

#### 撤销日志的记录格式
```
<T, X, old_value>
```
- T：事务ID
- X：数据项
- old_value：修改前的值

#### 撤销日志的工作原理
1. 事务修改数据前，记录旧值
2. 如果事务回滚，使用旧值恢复数据
3. 系统故障时，回滚所有未提交事务

### 2. 重做日志（Redo Logging）

**重做日志**记录事务修改后的数据值，用于重做已提交的事务。

#### 重做日志的记录格式
```
<T, X, new_value>
```
- T：事务ID
- X：数据项
- new_value：修改后的值

#### 重做日志的工作原理
1. 事务修改数据后，记录新值
2. 如果系统故障，重做所有已提交事务
3. 确保已提交事务的结果不丢失

### 3. 撤销/重做日志（Undo/Redo Logging）

**撤销/重做日志**同时记录旧值和新值，提供最灵活的恢复能力。

#### 撤销/重做日志的记录格式
```
<T, X, old_value, new_value>
```

#### 撤销/重做日志的工作原理
1. 记录修改前后的值
2. 可以支持立即更新或延迟更新
3. 提供最完整的恢复能力

## 撤销日志详解

### 撤销日志的规则

#### 规则1：日志记录先于数据写入
- 在修改数据项X之前
- 必须先将撤销日志记录写入稳定存储器

#### 规则2：提交时强制写入日志
- 事务提交时
- 必须将所有日志记录强制写入稳定存储器

### 撤销日志的恢复过程

#### 正常执行过程
1. 事务开始：`<T, start>`
2. 修改数据：`<T, X, old_value>`
3. 事务提交：`<T, commit>`

#### 故障恢复过程
1. 从后向前扫描日志
2. 对于未提交的事务：
   - 找到所有`<T, X, old_value>`记录
   - 将X恢复为old_value
3. 写入`<T, abort>`记录

### 撤销日志的示例

#### 示例：银行转账事务
```
事务T1：从账户A转账100元到账户B
初始状态：A = 1000, B = 2000
```

日志记录：
```
<T1, start>
<T1, A, 1000>  -- 修改A前记录旧值
<T1, B, 2000>  -- 修改B前记录旧值
<T1, commit>
```

如果事务执行到修改B后故障：
```
<T1, start>
<T1, A, 1000>
<T1, B, 2000>  -- 故障发生
```

恢复过程：
1. 扫描日志，发现T1未提交
2. 将A恢复为1000
3. 将B恢复为2000
4. 写入`<T1, abort>`

### 撤销日志的优缺点

#### 优点
1. **简单**：实现相对简单
2. **快速恢复**：只需撤销未提交事务
3. **节省空间**：只记录旧值

#### 缺点
1. **性能影响**：每次修改都要记录日志
2. **不能恢复已提交事务**：如果已提交事务的数据丢失，无法恢复
3. **需要强制写入**：提交时需要等待日志写入

## 检查点技术

### 什么是检查点？

**检查点**是数据库在某个时间点的一致性快照，用于减少恢复时间。

### 检查点的作用
1. **减少恢复时间**：只需恢复检查点后的事务
2. **清理日志**：可以删除检查点前的日志
3. **简化恢复**：恢复过程更简单

### 静态检查点

#### 做法
1. 停止接受新事务
2. 等待所有活跃事务完成
3. 将所有修改写入磁盘
4. 写入检查点记录
5. 重新开始接受事务

#### 优点
- 简单
- 恢复容易

#### 缺点
- 需要停止服务
- 影响性能

### 动态检查点

#### 做法
1. 在事务执行过程中建立检查点
2. 记录活跃事务列表
3. 将修改的数据写入磁盘

#### 优点
- 不需要停止服务
- 对性能影响小

#### 缺点
- 实现复杂
- 恢复过程稍复杂

## 学习建议

对于初学者，建议：
1. **理解ACID特性**：这是事务处理的基础
2. **掌握日志的基本概念**：了解撤销日志和重做日志的区别
3. **理解恢复的基本原理**：知道如何从故障中恢复
4. **通过例子加深理解**：分析具体的恢复过程

> [!tip] 实践建议
> 建议模拟一个简单的事务执行过程，手动记录日志，然后模拟故障恢复，这样能更好地理解恢复机制。

## 关键概念总结

1. **事务**：数据库操作的逻辑单位，具有ACID特性
2. **日志**：记录数据库修改操作，用于恢复
3. **撤销日志**：记录修改前的值，用于回滚
4. **重做日志**：记录修改后的值，用于重做
5. **检查点**：数据库的一致性快照，用于减少恢复时间
