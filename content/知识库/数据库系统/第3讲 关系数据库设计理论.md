## 3.1 问题的提出

### 3.1.1 数据冗余

**数据冗余**（Data Redundancy）是指在数据库中存在重复的数据。

**带来的问题**：
1. **存储空间浪费**：相同的数据被多次存储
2. **数据更新异常**（Update Anomaly）：
   - 多处更新，容易漏更
   - 更新不一致，导致数据不一致
3. **插入异常**（Insert Anomaly）：
   - 无法插入部分信息
   - 必须插入无用的拟填数据
4. **删除异常**（Delete Anomaly）：
   - 删除数据时造成有用信息丢失

**示例**：
```
课程表（包括学分信息）：
| 课程号 | 课程名 | 学分 | 学生号 |
|--------|--------|------|--------|
| C1     | 数据库 | 4    | S1     |
| C1     | 数据库 | 4    | S2     |
| C2     | 数学   | 3    | S1     |
```

**问题**：
- 课程名和学分多次重复（冗余）
- 更新C1学分，需要更新多行
- 新增课程C3，暂无学生选修，无法插入
- 删除S1的课程记录，导致C2信息丢失

### 3.1.2 函数依赖

**函数依赖**（Functional Dependency）是规范化理论的基础，用于描述属性之间的语义联系。

**定义**：
在关系模式 R(U) 中，X 和 Y 是 U 的子集。若对于 R(U) 的任何一个可能的关系 r，r 中不可能存在两个元组在 X 上的属性值相等，而在 Y 上的属性值不等，则称
**X 函数确定 Y** 或 **Y 函数依赖于 X**，记作 $$ X \to Y $$

**示例**：
在学生表中，学号 → 姓名
因为任两个学生不能有相同的学号

---

## 3.2 函数依赖的类型

### 3.2.1 完全函数依赖与部分函数依赖

设 R(U) 为关系模式，X 和 Y 是 U 的子集。

**完全函数依赖**（Full Functional Dependency）：
若 X → Y，且对于 X 的任何一个真子集 X'，都有 X' → Y，则称
Y 完全函数依赖于 X，记作 $$ X \stackrel{F}{\to} Y $$

**部分函数依赖**（Partial Functional Dependency）：
若 X → Y，但存在 X' ⊂ X，使得 X' → Y，则称
Y 部分函数依赖于 X

**示例**：
在关系模式 SC(Sno, Cno, Grade) 中：
- (Sno, Cno) → Grade 是完全函数依赖
- 因为 Sno → Grade 咋 Cno → Grade 都不成立

### 3.2.2 传递函数依赖

若 X → Y，Y → Z，且 Y → X ，Z ∈ Y，Z ∉ X
则称 Z 传递函数依赖于 X

**示例**：
在学生表中：
学号 → 所在系 → 系主任
因为学号 → 所在系，所在系 → 系主任
故学号 → 系主任 是传递依赖

### 3.2.3 非平凡函数依赖

若 X → Y，且 Y ⊂ X，则称 X → Y 是**平凡函数依赖**
否则称 X → Y 是**非平凡函数依赖**

**示例**：
- Sno → Sname 是非平凡函数依赖（因为 Sname ∉ Sno）
- (Sno, Cno) → Sno 是平凡函数依赖（因为 Sno ∈ (Sno, Cno)）

### 3.2.4 候选码与主属性

若 K → U，则 K 为候选码
- 属于任何一个候选码的属性称**主属性**
- 不包含在任何候选码中的属性称**非主属性**

## 3.3 范式与范式化

### 3.3.1 第一范式（1NF）

**定义**：关系中的每个分量都必须是不可分的数据项。

**说明**：
- 1NF 要求数据库表的每个列都是原子的，不能再分
- 一个列中不能包含多个值
- 每个元组都是原子的

**例子**：

| 好的设计（满足1NF） | 坏的设计（不满足1NF） |
|------|------|
| 学号号 | 学号号 |
| S1   | S1   |
| S2   | S2   |

| 学生名  | 课程名         | 学生名  | 课程名         |
|--------|----------------|--------|------------------|
| 张三   | 数据库,数学 | 张三   | 数据库,数学 |

上表学生表中，"课程名"列包含多个值，应分成多个元组

### 3.3.2 第二范式（2NF）

**定义**：若 R ∈ 1NF，且每个非主属性完全函数依赖于任何一个候选码，则 R ∈ 2NF。

**说明**：
- 2NF 要求不存在部分函数依赖
- 即非主属性对主码是完全函数依赖，而不是部分
- 如果主码只含一个属性，则必然满足2NF

**问题分析**：
原始关系 SC(Sno, Cno, Sname, Cname, Grade)

函数依赖：
- (Sno, Cno) → Grade （完全依赖）
- Sno → Sname （部分依赖）
- Cno → Cname （部分依赖）

**问题**：
- 存在部分函数依赖
- 学生信息重复（Sno相同，Sname就相同）
- 课程信息重复（Cno相同，Cname就相同）

**分解为2NF**：

1. Student(Sno, Sname)
   - 主码：Sno
   - 功能：存储学生信息

2. Course(Cno, Cname)
   - 主码：Cno
   - 功能：存储课程信息

3. SC(Sno, Cno, Grade)
   - 主码：(Sno, Cno)
   - 功能：存储选课和成绩

### 3.3.3 第三范式（3NF）

**定义**：若 R ∈ 2NF，且 R 中每个非主属性都不传递依赖于 R 的任何一个候选码，则 R ∈ 3NF。

**等价定义**：R ∈ 2NF，且 R 中不存在非主属性对候选码的传递依赖

**示例**：
原始关系 Student(Sno, Sname, Sdept, Mgrname)

函数依赖：
- Sno → Sname, Sdept （主函数依赖）
- Sdept → Mgrname （传递依赖）

**问题**：
- 存在传递依赖
- 同一系主任多次重复
- 更新异常，删除异常

**分解为3NF**：

1. Student(Sno, Sname, Sdept)
   - 主码：Sno

2. Dept(Sdept, Mgrname)
   - 主码：Sdept

**BCNF（Boyce-Codd 范式）**：
当 3NF 仍存在主属性对候选码的部分和传递依赖时，进一步规范获得 BCNF

BCNF 比 3NF 更严格，消除了任何属性（主属性和非主属性）对候选码的部分和传递依赖

## 3.4 模式分解

### 3.4.1 分解的目标

1. **消除数据冗余**
2. **消除插入异常**
3. **消除删除异常**
4. **消除更新异常**

### 3.4.2 分解的评价标准

#### 1. 无损连接（Lossless Join）

分解后通过自然连接能够恢复原关系，不产生**虚假元组**（Spurious Tuples）

**定理**：
关系模式 R 分解为 R1 和 R2，分解具有无损连接的充要条件是：
$$ R1 \cap R2 \to R1 - R2 $$ 或 $$ R1 \cap R2 \to R2 - R1 $$
属于 F+（F 的闭包）

**示例**：
R(A, B, C)、F = {A → B, B → C}
分解为：R1(A, B)、R2(B, C)

R1 ∩ R2 = {B}
R1 - R2 = {A}
B → A ？不成立（A → B，但 B → A 不成立）

该分解不具有无损连接

#### 2. 保持函数依赖

分解后，每个函数依赖都能在某个模式中得到保持

#### 3. 分解算法

**3NF 分解算法**：
1. 求 F 的最小依赖集 G
2. 按照左部分属性分组得到的依赖集分为：
   - {X_i → A_i}中只有单个属性，合并为 {X → A_i, ...}
   - {X_j → A_j} 中包含多个属性，保持
3. 去除冗余的依赖
4. 对每个依赖建立模式，如果模式没有包含任何一个候选码，则加入一个候选码
5. 如果任何一个模式包含了 R 的全部属性，则不再建立模式

**BCNF 分解算法**：
1. 求 F 的最小依赖集 G
2. 设 U₀ = U，对 U₀ 中的每个属性求关属闭包 X+。如果 X+ 包含了 U₀ 中的全部属性，让 R = (U₀)，算法结束
3. 否则，在 G 中寻找一个依赖 X → Y，使得 X 包含在某个候选码中，而 X 不包含 U₀ 的全部属性。如果找不到，则取 R 的一个候选码 X，让 R1 = X，原关系为 R2 = (U - X)+
4. 让 U₀ = U₀ - (U - X)+，转到步2

### 3.4.3 分解例子

**原始关系**：S-L-C(Sno, Sloc, Cno, Grade)

**函数依赖**：
- Sno → Sloc
- (Sno, Cno) → Grade

**分解**：
1. SL(Sno, Sloc) - 学生和住宿地
2. SC(Sno, Cno, Grade) - 选课和成绩

**验证无损连接**：
SL ∩ SC = {Sno}
SL - SC = {Sloc}
Sno → Sloc 在 F+，满足无损连接

## 3.5 范式化理论的意义

### 3.5.1 理论意义

1. **为数据库设计提供了理论基础**
   - 指导如何构造合适的数据模型
   - 避免数据冗余和异常

2. **规范化数据库设计**
   - 使数据库结构更加合理
   - 提高数据的一致性

3. **提供评价标准**
   - 判断数据库设计的优劣
   - 指导数据库的改进

### 3.5.2 实际应用

1. **数据库设计工具**
   - PowerDesigner
   - ERWin
   - Visio

2. **开发流程**
   - 需求分析 → E-R 图 → 关系模型 → 范式化 → 物理设计

3. **性能考虑**
   - 3NF 是理论上的规范形式
   - 实际应用中可能需要一定的控制
   - 有时代以空间换时间，适当增加冗余
