## 关系代数作为约束语言

### 两种约束表达方式

关系代数可以用来表达约束条件：

#### 1. 空结果约束
```
R = ∅
```
- **含义**：R的值必须为空
- **解释**：R表达式的结果中没有元组

#### 2. 包含约束
```
R ⊆ S
```
- **含义**：R中的每个元组也必须在S中
- **解释**：R的结果是S的结果的子集

### 示例

```
π_title(σ_year<1900(Movies)) = ∅
```
- 含义：没有1900年以前的电影
- 解释：查询1900年以前电影的结果必须为空

## 参照完整性约束

### 什么是参照完整性？

**参照完整性约束**是数据库中最重要的一类约束，确保外键引用的值必须存在。

### 参照完整性的表示
```
π_A(R) ⊆ π_B(S)
```

### 含义
如果关系R的属性A中有值v，那么由于设计意图，我们期望v会出现在另一个关系S的属性B中。

### 示例

假设有两个关系：
- **Movies**(title, year, length, genre, studioName, producerC#)
- **MovieExec**(name, address, cert#, netWorth)

约束：
```
π_producerC#(Movies) ⊆ π_cert#(MovieExec)
```

**解释**：
- 每个Movies元组的producerC#必须出现在某个MovieExec元组的cert#中
- 这意味着每个电影的制片人必须在MovieExec表中有记录

## 键和外键

### 主键约束

**主键**是关系中唯一标识元组的属性或属性集。

#### 主键的特点
1. **唯一性**：主键值必须唯一
2. **非空性**：主键值不能为空
3. **最小性**：主键是最小的唯一标识

#### SQL中的主键定义
```sql
CREATE TABLE Movies (
    title VARCHAR(100),
    year INT,
    PRIMARY KEY (title, year)
);
```

### 外键约束

**外键**是引用另一个关系主键的属性或属性集。

#### 外键的特点
1. **引用性**：外键引用另一个关系的主键
2. **完整性**：外键值必须在被引用关系的主键中存在
3. **可以为空**：外键值可以为空（除非另有约束）

#### SQL中的外键定义
```sql
CREATE TABLE Movies (
    title VARCHAR(100),
    year INT,
    producerC# INT,
    FOREIGN KEY (producerC#) REFERENCES MovieExec(cert#)
);
```

## 属性和元组上的约束

### 属性约束

**属性约束**限制单个属性的取值。

#### 常见属性约束
1. **NOT NULL**：属性不能为空
2. **CHECK**：属性值必须满足条件
3. **DEFAULT**：属性的默认值

#### SQL示例
```sql
CREATE TABLE Student (
    student_id INT NOT NULL,
    name VARCHAR(50) NOT NULL,
    age INT CHECK (age >= 0 AND age <= 150),
    gender CHAR(1) DEFAULT 'M'
);
```

### 元组约束

**元组约束**限制元组中多个属性之间的关系。

#### 示例
```sql
CREATE TABLE Employee (
    employee_id INT,
    start_date DATE,
    end_date DATE,
    CHECK (end_date IS NULL OR end_date > start_date)
);
```

**解释**：结束日期必须大于开始日期，或者为空

## 约束的修改

### 添加约束
```sql
-- 添加主键约束
ALTER TABLE Movies ADD PRIMARY KEY (title, year);

-- 添加外键约束
ALTER TABLE Movies ADD FOREIGN KEY (producerC#) REFERENCES MovieExec(cert#);

-- 添加检查约束
ALTER TABLE Employee ADD CHECK (end_date > start_date);
```

### 删除约束
```sql
-- 删除主键约束
ALTER TABLE Movies DROP PRIMARY KEY;

-- 删除外键约束
ALTER TABLE Movies DROP FOREIGN KEY fk_producer;
```

## 断言

### 什么是断言？

**断言**是一个谓词，表达了我们希望数据库总能满足的条件。

### 断言的特点
1. **全局性**：断言可以涉及多个关系
2. **复杂性**：可以表达复杂的业务规则
3. **自动检查**：DBMS会自动检查断言是否满足

### SQL中的断言
```sql
CREATE ASSERTION total_salary_check
CHECK (
    (SELECT SUM(salary) FROM Employee) <= 
    (SELECT budget FROM Department WHERE dept_id = 1)
);
```

**解释**：员工总工资不能超过部门预算

### 断言的优缺点

#### 优点
- 可以表达复杂的业务规则
- 自动维护数据完整性

#### 缺点
- 可能影响性能
- 实现复杂

## 触发器

### 什么是触发器？

**触发器**是一段程序，当特定事件发生时自动执行。

### 触发器的组成
1. **事件**：触发器执行的条件（如INSERT、UPDATE、DELETE）
2. **条件**：触发器执行的额外条件
3. **动作**：触发器执行的操作

### SQL中的触发器
```sql
CREATE TRIGGER update_salary
AFTER UPDATE OF salary ON Employee
FOR EACH ROW
WHEN (NEW.salary > OLD.salary * 1.5)
BEGIN
    INSERT INTO SalaryLog (employee_id, old_salary, new_salary, update_time)
    VALUES (NEW.employee_id, OLD.salary, NEW.salary, CURRENT_TIMESTAMP);
END;
```

**解释**：当员工工资涨幅超过50%时，记录到日志表

### 触发器的类型

#### 1. 行级触发器
- 每行数据修改时触发
- 使用FOR EACH ROW

#### 2. 语句级触发器
- 每条SQL语句执行时触发
- 默认类型

### 触发器的应用场景
1. **审计跟踪**：记录数据变更历史
2. **数据验证**：复杂业务规则检查
3. **自动更新**：维护派生数据
4. **安全控制**：限制某些操作

## 约束与触发器的比较

### 约束
- **优点**：声明式，简单易用
- **缺点**：表达能力有限

### 触发器
- **优点**：功能强大，可编程
- **缺点**：复杂，可能影响性能

### 选择建议
- 简单约束使用声明式约束
- 复杂业务规则使用触发器
- 避免过度使用触发器

## 学习建议

对于初学者，建议：
1. **理解约束的重要性**：这是数据完整性的基础
2. **掌握主键和外键**：这是关系数据库的核心
3. **学习简单的约束语法**：NOT NULL、CHECK等
4. **了解触发器的基本概念**：知道它的作用和应用场景

> [!tip] 实践建议
> 建议在数据库系统中创建包含各种约束的表，然后尝试插入违反约束的数据，观察数据库的响应，这样能更好地理解约束的作用。

## 关键概念总结

1. **参照完整性**：外键引用的值必须存在
2. **主键**：唯一标识元组的属性集
3. **外键**：引用另一个关系主键的属性集
4. **断言**：全局性的业务规则
5. **触发器**：事件驱动的自动程序
