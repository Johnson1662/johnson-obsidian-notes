# 第六章 链接

## 1. 本章概述

链接（Linking）是将多个目标文件（如 `.o` 文件）和库文件合并成一个可执行文件的过程。本章介绍链接的全过程，包括符号解析（Symbol Resolution）和重定位（Relocation），以及静态链接与动态链接的区别与原理。

---

## 2. 知识点讲解

### 2.1 链接的基本概念

**通俗定义：** 写好的 C 程序通常分散在多个 `.c` 文件中。每个 `.c` 文件被编译成目标文件（`.o` 文件），但这些文件彼此之间相互引用（比如 `a.c` 调用了 `b.c` 中定义的函数）。链接就是把所有目标文件和库"拼"成一个完整的可执行文件的过程。

**链接的阶段：**
1. **符号解析（Symbol Resolution）**——将每个符号引用与一个符号定义关联起来
2. **重定位（Relocation）**——将符号的引用地址修改为实际的内存地址

**为什么要链接？**
- 模块化开发：一个程序拆成多个源文件，各自编译、各自调试
- 库代码复用：直接使用标准库（如 `printf`），无需重复编写

---

### 2.2 目标文件的三种类型

| 类型 | 后缀 | 说明 |
|---|---|---|
| 可重定位目标文件 | `.o` (Linux) / `.obj` (Windows) | 包含代码和数据，可与其他目标文件合并 |
| 可执行目标文件 | 无后缀（Linux）/ `.exe` (Windows) | 可直接加载到内存执行 |
| 共享目标文件 | `.so` (Linux) / `.dll` (Windows) | 运行时动态加载或链接 |

---

### 2.3 ELF 目标文件格式

Linux 下的目标文件使用 ELF（Executable and Linkable Format）格式，主要组成部分：

```
ELF头          → 文件类型、节区表位置、程序入口等
.text          → 已编译的机器代码（只读）
.data          → 已初始化的全局变量和静态变量
.bss           → 未初始化的全局变量和静态变量（不占磁盘空间，运行时分配）
.symtab        → 符号表（函数名、全局变量名等）
.rel.text      → .text 节的重定位信息
.rel.data      → .data 节的重定位信息
.debug         → 调试符号表（gcc -g 生成）
.line          → 源文件行号与机器代码的映射
.strtab        → 字符串表
```

> **初学易错点：** `.bss` 节不占用磁盘空间，但加载到内存时会分配空间并初始化为 0。初学者常误以为 `.bss` 段也在目标文件中占用文件大小。

---

### 2.4 符号与符号表

**通俗定义：** 符号就是一个"名字"，它代表一个函数、全局变量或静态变量。每个目标文件都有一张符号表（`.symtab`），记录了该文件中定义的和引用的所有符号。

**符号的分类：**

| 符号类型 | 说明 | 示例 |
|---|---|---|
| 全局符号（Global） | 非静态函数和非静态全局变量 | `int g;` `void foo()` |
| 外部符号（External） | 在本模块引用但定义在其他模块的符号 | `extern int g;` |
| 局部符号（Local） | `static` 定义的函数和变量 | `static int x;` |

**注意：** 这里的"局部"是指文件作用域（module scope），不是函数内部的局部变量。函数内部的局部变量（auto 变量）不在符号表中——它们在运行时在栈上分配。

> **初学易错点：** `static` 关键字使得符号成为局部符号（仅本文件可见），这可以防止不同文件中的同名变量发生冲突。

---

### 2.5 强符号与弱符号

**通俗定义：** 链接器在解析符号时，会面临"多个目标文件定义了同名符号"的问题。C 语言对此规定了规则：

| 符号类型 | 定义方式 | 示例 |
|---|---|---|
| 强符号（Strong） | 带初始化的全局变量、函数定义 | `int x = 5;` `void foo() {}` |
| 弱符号（Weak） | 未初始化的全局变量 | `int x;` |

**强符号与弱符号规则（Unix 链接器规则）：**

1. **不允许有多个同名的强符号**——链接报错（重复定义）
2. **如果一个强符号和多个弱符号同名，选择强符号**
3. **如果多个弱符号同名，随机选择一个**

**公式表示：**

设有 $n$ 个目标文件，其中 $m$ 个定义了符号 $S$：

$$
\text{结果} = 
\begin{cases}
\text{链接错误（重复定义）}, & \text{强符号个数} > 1 \\
\text{强符号定义生效}, & \text{强符号个数} = 1 \\
\text{任意一个弱符号定义生效}, & \text{强符号个数} = 0 \text{ 且弱符号个数} \ge 1
\end{cases}
$$

> **初学易错点：** 弱符号机制是 C 语言中一个非常隐蔽的 bug 源。比如一个文件中写了 `int x;`（弱）另一个文件中写了 `int x = 100;`（强），所有对 `x` 的引用实际上都使用了 `x = 100`，而弱符号所在的文件可能完全不知道这件事。更危险的是类型不匹配——两个文件用不同数据类型声明同一个弱符号，编译器不会报错，但运行时行为未定义。

**示例：**
```c
/* m1.c */
int x = 0x1234;    /* 强符号 */
int y = 0x5;       /* 强符号 */
void p1() { x++; }
static void p2() { x += 2; }

/* m2.c */
short x;           /* 弱符号 */
void main() {
    p2();
    printf("%d\n", x);
    p1();
    printf("%d\n", x);
}
```

执行分析：
- `x` 在两个文件中同名：m1.c 中 `int x = 0x1234`（强），m2.c 中 `short x;`（弱）
- 根据规则②，强符号胜出，`x` 被定义为 `int` 类型，初始值 `0x1234`
- 但注意 m2.c 中声明 `short x`（2 字节），而强符号定义是 `int x`（4 字节），类型不匹配！
- 调用 `p2()`（m1.c 中）——做了 `x += 2`，`x = 0x1236`
- 然后调用 `p1()`（m1.c 中）——做了 `x++`，`x = 0x1237`
- 但在 m2.c 中以 `short` 类型读取 `x`，只读取了低 2 个字节

### 2.6 静态链接的过程

**通俗定义：** 静态链接指在编译时（确切地说是链接时）将所有目标文件和库合并成一个独立可执行文件。

**静态链接的两步过程：**

**步骤 1：符号解析（Symbol Resolution）**
- 链接器扫描所有目标文件，建立全局符号表
- 对每个符号引用，找到对应的符号定义
- 根据强/弱符号规则处理冲突

**步骤 2：重定位（Relocation）**
- 合并各个目标文件的相同节区（如所有 `.text` 合并、所有 `.data` 合并）
- 为每个符号分配最终的内存地址
- 修改所有引用处的地址（通过重定位表项完成）

**重定位的类型：**

| 类型 | 说明 | 公式 |
|---|---|---|
| `R_X86_64_PC32` | 相对寻址，计算当前指令与目标地址的偏移 | `新地址 = 目标地址 - 当前PC + 原有偏移` |
| `R_X86_64_32` | 绝对寻址，直接填入目标地址 | `新地址 = 目标地址 + 原有偏移` |

其中 $当前PC$ 通常为当前指令的下一条指令地址。

> **初学易错点：** 重定位之前，目标文件中的符号地址都是"假的"（从 0 开始或临时偏移）。只有重定位完成后，所有符号的地址才变成最终的内存地址。

---

### 2.7 动态链接与共享库

**通俗定义：** 静态链接的可执行文件包含所有用到的库代码，体积大、浪费内存（多个进程用同一库时各自有一份副本）。动态链接在运行时才加载共享库（`.so`/`.dll`），多个进程共享库的一份代码副本。

**动态链接的优点：**
1. 节省磁盘空间：多个程序共享同一个 `.so` 文件
2. 节省内存：多个进程共享库的代码段
3. 库更新方便：只需替换 `.so` 文件，程序无需重新链接

**动态链接的原理：**

```
程序依赖 libc.so
   ↓
加载器（Loader）将程序加载到内存
   ↓
加载器发现程序需要 libc.so（通过 .dynamic 节）
   ↓
加载器查找并加载 libc.so 到内存
   ↓
链接器（ld-linux.so）完成符号重定位
```

**位置无关代码（PIC，Position-Independent Code）：**
- 共享库必须能被加载到任意内存地址而不出错
- 通过 **GOT（全局偏移表）** 和 **PLT（过程链接表）** 实现

**GOT 与 PLT 的工作流程：**

1. 函数调用 → 跳转到 PLT
2. PLT 第一条指令：跳转到 GOT
3. GOT 初始指向 PLT 中的解析代码
4. 首次调用：解析器（ld-linux.so）找到函数地址，写入 GOT
5. 后续调用：GOT 表项已更新为函数实际地址，直接跳转

> **初学易错点：** 很多同学误以为 `#include <stdio.h>` 会把 `printf` 代码包含进来。实际上 `#include` 只是引入头文件（声明），`printf` 的实现代码在 `libc.so` 中，是在链接或运行时才引入的。`#include` 是**编译时**的预处理指令，而链接是**编译后**的独立阶段。

---

### 2.8 库打桩（Library Interpositioning）

**通俗定义：** 库打桩是一种"偷梁换柱"的技术——让你能用自己的函数替换标准库函数。这在调试、性能分析、安全审计中非常有用。

**打桩的三种时机：**

| 时机 | 方式 | 说明 |
|---|---|---|
| 编译时（Compile time） | 使用 `#define` 或 `--wrap` 选项 | 预处理阶段替换函数名 |
| 链接时（Link time） | 使用 `ld` 的 `--wrap` 选项 | 链接器优先链接自定义函数 |
| 运行时（Run time） | 使用 `dlsym` + `RTLD_NEXT` | 通过动态链接机制拦截调用 |

**运行时打桩示例：** 拦截 `malloc` 调用
```c
#define _GNU_SOURCE
#include <dlfcn.h>

void *malloc(size_t size) {
    static void *(*real_malloc)(size_t) = NULL;
    if (!real_malloc)
        real_malloc = dlsym(RTLD_NEXT, "malloc");
    void *ptr = real_malloc(size);
    printf("malloc(%zu) = %p\n", size, ptr);
    return ptr;
}
```

## 3. 典型例题

### 例题 1（来源：[Q0006]）

**题目：** 哪一个选项不是下面代码中的符号？

```c
int data[100];
int main()
{
    static void * handle;
    void (* addvec)(int*, int *, int *, int);
    handle = dlopen("./libvector.so", RTLD_LAZY);
    addvec = dlsym(handle, "addvec");
    addvec(x, y, z, 2);
    return 0;
}
```

A. `data`  
B. `main`  
C. `handle`  
D. `addvec`

**解答：**

我们需要判断每个选项是否在符号表中。

1. **符号的概念**：符号（Symbol）是出现在 `.symtab` 中的名称，代表一个全局变量、函数、或静态变量。函数内部的局部变量（auto 变量）**不在符号表中**。

2. **分析每个选项**：
   - `data`：全局变量 `int data[100]`，是全局符号 → 在符号表中 ✅
   - `main`：函数定义，是全局符号 → 在符号表中 ✅
   - `handle`：在 `main` 内部定义的 `static void * handle`。注意这里的 `static` 关键字在函数内部的意思是"静态局部变量"——它有静态存储期（生命周期贯穿整个程序运行），但作用域是函数内部。在 C 语言中，**函数内部的 `static` 变量不产生模块级的符号**，它通常由编译器在局部作用域处理，不在 ELF 符号表中作为独立符号出现。
   - `addvec`：在 `main` 内部定义的函数指针变量，是普通的局部变量（auto 变量），**不在符号表中**。

3. **关键区别**：
   - `main` 内部的 `static void * handle` 虽然是静态存储期，但它是函数作用域，不产生全局符号
   - `addvec` 是自动局部变量，显然不是符号
   - 所以 `handle` 和 `addvec` 都不是符号，但题目是单选题

4. **再仔细审题**："哪一个选项不是下面代码中的符号？"——即问哪个**不是**符号。`data`、`main` 是符号，`handle` 和 `addvec` 都不是符号。但 `handle` 是 `static` 局部变量，有些编译器的行为下可能会出现在符号表中（带局部作用域标记），而 `addvec` 是普通的自动变量，一定不在符号表中。

   实际上，更严谨地说：**在 ELF 符号表中**，`data` 和 `main` 作为全局符号出现。`static void *handle` 虽然是静态局部变量，但它**确实会出现在符号表中**——因为 `static` 变量有静态存储期，编译器会为它在 `.data` 或 `.bss` 段分配空间，并产生一个局部符号（local symbol）用于调试或内部引用。

   所以唯一**绝对不在符号表中**的是 `addvec`——它是一个函数指针类型的局部变量，分配在栈上，生命周期仅在 `main` 函数执行期间，不需要在符号表中登记。

**答案：D（`addvec`）**

**解析：**
- 符号表只记录**全局的**和**静态存储期**的函数与变量（包括文件作用域的静态变量和函数内 static 变量）
- 自动局部变量（auto）**永不进符号表**——它们在栈上分配，链接器不需要知道它们
- 本题的陷阱在 `handle` 的 `static` 关键字：尽管是局部变量，但 `static` 使其有静态存储期，编译器会为它在 .bss/.data 段中分配空间，因此会产生符号；而 `addvec` 是纯自动变量，不产生符号

### 例题 2（来源：[Q0023]）

**题目：** 阅读以下 C 代码，回答问题。

```c
/* m1.c */
short x = 0x1234;
int y = 0x5;
void p1(){
    x++;
}
static void p2(){
    x=x+2;
}
```

```c
/* m2.c */
short x;
void main(){
    p2();
    printf("x1: %d\n", x);
    p1();
    printf("x2: %d\n", x);
}
```

**（1）m1.c 和 m2.c 中的强符号有哪些？**  
**（2）m1.c 和 m2.c 中的弱符号有哪些？**

**解答：**

**第一步：复习强/弱符号定义**
- **强符号**：带初始化的全局变量、函数定义（非 static）
- **弱符号**：未初始化的全局变量

**第二步：分析 m1.c**

| 符号 | 定义方式 | 类型 |
|---|---|---|
| `x` | `short x = 0x1234;` ——带初始化的全局变量 | **强符号** |
| `y` | `int y = 0x5;` ——带初始化的全局变量 | **强符号** |
| `p1` | `void p1(){...}` ——函数定义 | **强符号** |
| `p2` | `static void p2(){...}` ——static 函数，仅 m1.c 可见 | **局部符号（不在考虑范围内）** |

**第三步：分析 m2.c**

| 符号 | 定义方式 | 类型 |
|---|---|---|
| `x` | `short x;` ——未初始化的全局变量 | **弱符号** |
| `main` | `void main(){...}` ——函数定义 | **强符号** |

**答案：**
1. **强符号**：m1.c 中有 `x`、`y`、`p1`；m2.c 中有 `main`
2. **弱符号**：m2.c 中的 `x` 是弱符号

**解析：**
- `p2` 是 `static` 函数，只在 m1.c 内部可见，不参与跨模块的符号解析，不存在"强/弱"之说
- 两个文件中的 `x` 一个是强符号（m1.c），一个是弱符号（m2.c），根据规则，链接器会选择强符号 `short x = 0x1234`
- 注意：这里 `x` 在两个文件中的类型相同（`short`），所以运行时不会出现类型不匹配的问题
- 程序运行结果分析：
  - 全局 `x` 初始值为 `0x1234`，即十进制的 4660
  - `p2()` 执行 `x = x + 2` → `x = 0x1236`（十进制的 4662）
  - 输出 `x1: 4662`
  - `p1()` 执行 `x++` → `x = 0x1237`（十进制的 4663）
  - 输出 `x2: 4663`

### 例题 3：静态链接中的重定位过程

**题目：** 假设有两个目标文件 `a.o` 和 `b.o`。`a.o` 中定义了一个全局变量 `int g = 42` 和一个函数 `void foo() { ... }`，`b.o` 中调用了 `foo` 和 `g`。请描述链接器将这两个目标文件链接成一个可执行文件时，在重定位阶段做了哪些工作。

**解答：**

**第一步：链接前的状态**
- `a.o` 中，`g` 和 `foo` 的地址是相对于 `a.o` 的偏移（从 0 开始）
- `b.o` 中，对 `g` 和 `foo` 的引用地址是临时的（通常是占位符，如 0），需要链接器填入实际地址

**第二步：合并节区**
- 链接器将 `a.o` 和 `b.o` 的 `.text` 节合并成一个连续的 `.text` 段
- 将 `.data` 节合并成一个连续的 `.data` 段

假设合并后的布局如下：

```
.text 段（从地址 0x400100 开始）：
  0x400100: a.o 的 .text（包含 foo 的代码）
  0x400200: b.o 的 .text（包含对 foo 和 g 的引用）

.data 段（从地址 0x600000 开始）：
  0x600000: a.o 的 .data（包含 g = 42）
```

**第三步：执行重定位**

每个重定位项包含：
- **偏移量**（Offset）：需要修改的位置
- **符号**（Symbol）：引用的目标符号
- **类型**（Type）：`R_X86_64_PC32`（相对寻址）或 `R_X86_64_32`（绝对寻址）

以 `b.o` 中调用 `foo` 的指令为例（假设是 `call foo`）：

1. `call` 指令的机器码中有一个 32 位的偏移量字段
2. 链接器检查 `b.o` 的 `.rel.text` 节，找到该偏移量字段的位置
3. 计算新的偏移量：
   - 目标地址（`foo` 的地址）= `0x400100`
   - `call` 指令的下一条指令地址（PC）= 假设在 `0x400210`
   - 偏移量 = 目标地址 - PC = `0x400100 - 0x400210 = -0x110`（即 -272，向前跳转）

$$
\text{重定位后的值} = 目标地址 - PC + 原有偏移量
$$

以 `b.o` 中访问全局变量 `g` 为例（假设是 `mov g(%rip), %rax`）：

1. 链接器找到对 `g` 的引用位置
2. `g` 的最终地址为 `0x600000`
3. 计算相对寻址的偏移量

**答案：**
重定位阶段主要完成了两件事：
1. 将 `a.o` 和 `b.o` 的同类型节区合并
2. 遍历所有重定位表项（`.rel.text` 和 `.rel.data`），根据符号的最终地址修改引用位置的地址值

**解析：**
- 重定位是静态链接的核心，它把分散目标文件中的"符号引用"变成"符号定义"的精准地址
- 可以理解为：重定位前，代码里写的是"喂，foo 你在哪？"；重定位后，代码里写的是"foo 就在地址 0x400100，直接跳过去"

---

### 例题 4：GOT 与 PLT 的工作原理

**题目：** 简述动态链接中 GOT（全局偏移表）和 PLT（过程链接表）的作用，并说明延迟绑定（Lazy Binding）的工作流程。

**解答：**

**第一步：理解问题背景**
- 动态链接库（`.so`）的位置在编译时是未知的，因为它可能被加载到任何地址
- 所以不能像静态链接那样直接填入绝对地址
- 解决方案：**PIC（位置无关代码）** + **GOT/PLT**

**第二步：GOT 的作用**
- GOT 是一个数据段中的表，每个表项对应一个全局变量或函数
- 函数/变量的实际地址在运行时被写入 GOT 表项
- 代码通过 GOT 间接访问：从 GOT 中读取目标地址，然后跳转

**第三步：PLT 的作用**
- PLT 是代码段中的一段"跳板代码"
- 每个动态调用的函数在 PLT 中有一个条目
- PLT 条目跳转到 GOT 中对应的表项

**第四步：延迟绑定（Lazy Binding）的流程**

延迟绑定意味着**函数地址只在首次调用时才被解析**，而不是在程序启动时一次性解析。

```
首次调用 foo():
  ① 程序跳转到 PLT[foo]
  ② PLT[foo] 跳转到 GOT[foo]
  ③ GOT[foo] 初始值指向 PLT[foo] + 6（解析代码）
  ④ 解析代码调用动态链接器（ld-linux.so）
  ⑤ 动态链接器查找 foo 的实际地址
  ⑥ 动态链接器将实际地址写入 GOT[foo]
  ⑦ 动态链接器跳转到 foo 执行

后续调用 foo():
  ① 程序跳转到 PLT[foo]
  ② PLT[foo] 跳转到 GOT[foo]
  ③ GOT[foo] 已保存 foo 的实际地址 → 直接跳转到 foo ✅
```

**答案：**
- GOT 是保存函数和变量实际地址的数据表
- PLT 是辅助 GOT 实现延迟绑定的跳板代码段
- 延迟绑定通过"首次调用→解析→更新GOT→第二次起直接调用"的机制，避免了程序启动时解析所有库函数的开销

**解析：**
- 为什么要延迟绑定？因为程序可能有很多动态库函数，但实际运行中只用到了其中一小部分。延迟绑定避免了一次性解析所有函数，加快了程序启动速度
- GOT 在动态链接中是可写的（因为需要运行时写入），PLT 是只读的
- 这也是很多安全漏洞利用技术（如 GOT 覆写）攻击的目标——攻击者修改 GOT 表项来劫持函数调用

### 例题 5：链接器处理多重定义的规则

**题目：** 现有三个源文件：

```c
/* a.c */
int x = 100;        /* 全局变量，带初始化 */
int y;              /* 全局变量，未初始化 */
void f() { ... }    /* 函数 */

/* b.c */
int x;              /* 全局变量，未初始化 */
double y = 3.14;    /* 全局变量，带初始化 */
void f() { ... }    /* 函数 */

/* c.c */
int x = -5;         /* 全局变量，带初始化 */
int y;              /* 全局变量，未初始化 */
void g() { ... }    /* 函数 */
```

回答以下问题：
（1）将 `a.o`、`b.o`、`c.o` 链接在一起，会发生什么？为什么？
（2）如果只链接 `a.o` 和 `b.o`，结果如何？
（3）如果只链接 `b.o` 和 `c.o`，结果如何？

**解答：**

**第一步：分析每个文件中的符号属性**

| 符号 | a.c | b.c | c.c |
|---|---|---|---|
| `x` | 强（`int x = 100`） | 弱（`int x;`） | 强（`int x = -5`） |
| `y` | 弱（`int y;`） | 强（`double y = 3.14`） | 弱（`int y;`） |
| `f` | 强（函数定义） | 强（函数定义） | — |
| `g` | — | — | 强 |

**第二步：应用强/弱符号规则**

规则①：**不允许有多个同名的强符号**——链接报错
规则②：**强符号覆盖弱符号**
规则③：**多个弱符号随机选一个**

**问题（1）：三个文件都链接**

- `x`：a.c 中强，b.c 中弱，c.c 中强 → 两个强符号冲突！→ **链接错误**
- 即使忽略 `x` 的问题，`f` 在 a.c 和 b.c 中都是强符号 → 也**链接错误**

**结论：三个文件一起链接必定失败。**

**问题（2）：只链接 a.o 和 b.o**

- `x`：a.c 中强（`int x = 100`），b.c 中弱 → 规则②，选择强符号，`x = 100`，**int 类型**
- `y`：a.c 中弱（`int y;`），b.c 中强（`double y = 3.14`） → 规则②，选择强符号，`y = 3.14`，**double 类型**
- `f`：a.c 中强，b.c 中强 → 规则①，**两个同名强符号冲突 → 链接错误**

**结论：a.o + b.o 因 `f` 重复定义而链接失败。**

**问题（3）：只链接 b.o 和 c.o**

- `x`：b.c 中弱（`int x;`），c.c 中强（`int x = -5`） → 规则②，选择强符号，`x = -5`
- `y`：b.c 中强（`double y = 3.14`），c.c 中弱（`int y;`） → 规则②，选择强符号，`y = 3.14`
- 没有符号冲突 → **链接成功**

**答案：**
（1）三个文件一起链接：失败。`x` 在两个文件中同时为强符号（a.c 和 c.c），`f` 在 a.c 和 b.c 中同时为强符号，违反规则①。
（2）只链接 a.o 和 b.o：失败。`f` 在两个文件中都是强符号，冲突。
（3）只链接 b.o 和 c.o：成功。`x` 和 `y` 的强弱各有不同但无冲突，且没有函数名冲突。

**解析：**
- 本题展示了强/弱符号冲突的两种结果：**链接错误**（同名强符号）和**静默覆盖**（强弱符号）
- 第（2）问中如果 `f` 不存在，链接能成功，但类型不匹配（`int y` vs `double y`）会在运行时产生难以调试的 bug
- 这就是为什么全局变量一定要避免在多个文件中使用同一个名字——否则要么链接报错，要么出现隐蔽的运行时错误

## 4. 自测题

### 自测题 1

**题目：** 静态链接和动态链接各有什么优缺点？列举至少各两条。

> [!question]- 点击查看完整解答
> **静态链接的优点：**
> 1. **独立性**：生成的可执行文件不依赖外部的 `.so` / `.dll` 文件，部署简单
> 2. **性能**：函数调用没有动态链接的间接跳转开销，运行速度略快
> 3. **确定性**：库的版本在链接时固定，不会因为系统更新而导致程序行为变化
>
> **静态链接的缺点：**
> 1. **文件体积大**：每个可执行文件都包含一份标准库代码的副本，磁盘占用大
> 2. **内存浪费**：多个进程运行同一个程序（或不同程序使用同一库）时，内存中有多份相同代码
> 3. **更新不便**：库有 bug 需要修复时，所有使用该库的程序都必须重新链接
>
> **动态链接的优点：**
> 1. **节省磁盘和内存**：共享库代码在磁盘和内存中只有一份，多个进程共享
> 2. **更新方便**：替换 `.so` 文件即可，无需重新链接所有程序
> 3. **减小可执行文件体积**：程序本身只包含自己的代码
>
> **动态链接的缺点：**
> 1. **依赖问题**：如果系统缺少某个版本的 `.so` 文件，程序无法运行（"DLL Hell"）
> 2. **启动稍慢**：加载器需要在启动时解析动态库的依赖关系
> 3. **性能略有损失**：通过 GOT/PLT 间接调用比直接调用多一次内存访问

### 自测题 2

**题目：** 下列哪些项会在 ELF 文件的符号表中出现？（多选）
A. 在一个函数内部定义的 `static int count;`
B. 在一个函数内部定义的 `int temp;`
C. 文件作用域定义的 `static int flag;`
D. 函数定义的形参 `int argc`

> [!question]- 点击查看完整解答
> **分析每个选项：**
>
> **A. 函数内部的 `static int count;`**
> - `static` 局部变量有静态存储期，生存期贯穿整个程序
> - 编译器会在 `.bss` 或 `.data` 段为其分配空间
> - 会生成一个局部符号（local symbol），名字通常是编译器修饰过的（如 `count.0`）
> - ✅ **在符号表中**
>
> **B. 函数内部的 `int temp;`**
> - 自动局部变量，在栈上分配
> - 链接器不需要知道它的存在
> - ❌ **不在符号表中**
>
> **C. 文件作用域的 `static int flag;`**
> - 文件作用域的 `static` 变量（内部链接属性）
> - 编译器在 `.bss` 段为其分配空间
> - 会生成局部符号（local symbol），只在当前目标文件内可见
> - ✅ **在符号表中**
>
> **D. 函数形参 `int argc`**
> - 形参是自动变量，在栈上分配（或被优化到寄存器中）
> - ❌ **不在符号表中**
>
> **答案：A、C**
>
> **解析：** 判断一个变量是否出现在符号表中的关键是看它是否有**静态存储期**（static storage duration）且具有**文件作用域或链接属性**。函数内部的普通自动变量、形参都不满足条件。

### 自测题 3

**题目：** 请解释为什么以下代码在链接时可能出错或出现未定义行为。

```c
/* foo.c */
int global_var;

void set_val(int v) {
    global_var = v;
}
```

```c
/* bar.c */
double global_var = 3.14;

int main() {
    set_val(42);
    printf("global_var = %f\n", global_var);
    return 0;
}
```

> [!question]- 点击查看完整解答
> **分析：**
>
> 1. **符号类型判断：**
>    - `foo.c` 中 `int global_var;` ——未初始化全局变量 → **弱符号**
>    - `bar.c` 中 `double global_var = 3.14;` ——带初始化全局变量 → **强符号**
>
> 2. **链接规则应用：**
>    - 根据规则②，强符号覆盖弱符号
>    - 链接器选择 `bar.c` 中的 `double global_var` 作为最终定义
>    - 变量在内存中占用 **8 个字节**（`double` 类型）
>
> 3. **问题所在：**
>    - `foo.c` 中的代码把 `global_var` 当作 `int`（4 字节）来写入
>    - 执行 `set_val(42)` 时，写入的是低 4 个字节
>    - `bar.c` 中的代码把 `global_var` 当作 `double`（8 字节）来读取
>    - **类型不一致导致数据解释错误**
>
> 4. **运行结果：**
>    - `global_var` 的 8 字节内存布局：
>      - 低 4 字节：被写入 42（`0x0000002A`）
>      - 高 4 字节：保持原来的 `double 3.14` 的高 4 位
>    - 当作 `double` 读取时，这串二进制不再表示 3.14，而是某个无意义的浮点数
>
> **答案：** 链接可以成功（一个强符号一个弱符号，无冲突），但运行时行为**未定义**。强符号是 `double`（8 字节），弱符号却当作 `int`（4 字节）写入，导致内存被部分覆盖，读取结果不可预测。
>
> **教训：** 强/弱符号规则只解决了"选择哪个定义"的问题，**不检查类型一致性**。类型不匹配是链接器静默通过的，需要程序员自己保证所有文件中对同一个全局变量的声明类型一致。最佳实践：把全局变量声明放在一个头文件中，各 `.c` 文件 `#include` 该头文件，避免重复声明。

### 自测题 4

**题目：** 简述 ELF 目标文件中 `.text`、`.data`、`.bss` 三个节区的区别，并说明各节区在可执行文件加载到内存时分别被映射到什么区域。

> [!question]- 点击查看完整解答
> **三个节区的区别：**
>
> | 节区 | 存储内容 | 是否占文件空间 | 是否初始化 | 读写属性 |
> |---|---|---|---|---|
> | `.text` | 机器指令代码 | ✅ 占用 | 由编译生成 | 只读（RX） |
> | `.data` | 已初始化的全局/静态变量 | ✅ 占用 | 初始值由代码指定 | 可读写（RW） |
> | `.bss` | 未初始化的全局/静态变量 | ❌ 不占用 | 运行时自动置 0 | 可读写（RW） |
>
> **加载到内存的映射：**
>
> 当程序加载时（以 Linux 为例）：
>
> 1. **`.text` 段** → 映射到代码区（通常从 `0x400000` 附近开始），权限为 **可读 + 可执行**
> 2. **`.data` 段** → 映射到数据区，跟在 `.text` 之后，权限为 **可读 + 可写**
> 3. **`.bss` 段** → 在内存中紧跟在 `.data` 之后分配空间，并**初始化为 0**，权限为 **可读 + 可写**。由于它不占文件空间，加载器会通过 `mmap` 分配匿名内存并填零
>
> **记忆要点：**
> - `.bss` 不占文件空间，但占**运行时内存**空间
> - 可以这样理解：文件是一个"蓝图"，`.bss` 说"这里将来需要一段空间，全填 0"，所以蓝图里不必真的画满 0，只要记一个"大小"即可

### 自测题 5

**题目：** 假设你收到一个 Linux 可执行文件，没有任何源代码。你需要在 `printf` 每次被调用时打印一条日志信息，要求不修改可执行文件本身。请问可以怎么做？简述原理。

> [!question]- 点击查看完整解答
> **方法：使用动态链接器的 `LD_PRELOAD` 机制进行运行时库打桩（Run-time Interpositioning）。**
>
> **步骤：**
>
> 1. 编写一个共享库，其中定义一个同名的 `printf` 函数：
>
> ```c
> #define _GNU_SOURCE
> #include <stdio.h>
> #include <dlfcn.h>
>
> int printf(const char *format, ...) {
>     static int (*real_printf)(const char *, ...) = NULL;
>
>     // 第一次调用时，通过 dlsym 找到真正的 printf
>     if (!real_printf) {
>         real_printf = dlsym(RTLD_NEXT, "printf");
>     }
>
>     // 先输出我们的日志
>     fprintf(stderr, "[INTERPOSED] printf was called!\n");
>
>     // 然后调用真正的 printf
>     va_list args;
>     va_start(args, format);
>     int result = real_printf(format, args);
>     va_end(args);
>     return result;
> }
> ```
>
> 2. 编译成共享库：
> ```bash
> gcc -shared -fPIC -o myprintf.so myprintf.c -ldl
> ```
>
> 3. 运行目标程序时设置环境变量：
> ```bash
> LD_PRELOAD=./myprintf.so ./target_program
> ```
>
> **原理：**
>
> - `LD_PRELOAD` 告诉动态链接器，在加载任何其他共享库**之前**先加载指定的共享库
> - 因为 `myprintf.so` 先被加载，其中定义的 `printf` 符号会**覆盖**标准 libc 中的 `printf` 符号
> - 我们的 `printf` 内部使用 `dlsym(RTLD_NEXT, "printf")` 来找到"下一个" `printf`（即 libc 中真正的 `printf`）
> - 这样我们就实现了一个"包裹层"：先做自己的操作，再调用原始函数
>
> **注意事项：** 这种方法只对通过动态链接调用 `printf` 的程序有效。如果程序是静态链接的或者直接使用系统调用写输出，则无法拦截。
