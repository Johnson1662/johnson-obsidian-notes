# 并行程序设计方法学

## PCAM 方法学

设计并行程序的四个阶段：
- **划分（Partitioning）**：分解成小任务，开拓并发性
- **通讯（Communication）**：确定任务间数据交换，监测划分合理性
- **组合（Agglomeration）**：依据局部性，组合成更大任务
- **映射（Mapping）**：将每个任务分配到处理器，提高算法性能

---

## 划分（Partitioning）

### 方法描述
- 充分开拓算法的并发性和可扩放性
- 先进行数据分解（域分解），再进行功能分解（计算功能分解）
- 使数据集和计算集互不相交
- 划分阶段忽略处理器数目和目标机器体系结构

### 两种划分方式

#### 域分解（Domain Decomposition）
划分对象是数据（输入数据、中间数据、输出数据）：
- 将数据分解成大致相等的小数据片
- 划分时考虑数据上的相应操作
- 如果一个任务需要别的任务中的数据，则会产生通讯

数据分解模式：
- **1D 分解**：按块（BLOCK）、循环（CYCLIC）分配
- **2D 分解**：*,BLOCK、*,CYCLIC、BLOCK,BLOCK、CYCLIC,CYCLIC
- **3D 分解**：三维网格，各格点计算重复
- **递归分解**：如快速排序，递归划分数组
- **不规则区域分解**：根据问题结构自适应划分

#### 功能分解（Functional Decomposition）
划分对象是计算：
- 将计算划分为不同的任务
- 研究不同任务所需的数据
- 数据不相交则划分成功；数据有重叠则需重新划分
- 功能分解是更深层次的分解

**示例**：
- 搜索树：根生成任务，叶结点分到各处理器并行搜索
- 气候模型：不同物理过程分解为独立任务

### 划分判据
- 是否具有灵活性？
- 是否避免了冗余计算和存储？
- 任务尺寸是否大致相当？
- 任务数与问题尺寸是否成比例？
- 功能分解是否合理？

## 通讯（Communication）

### 方法描述
- 通讯是PCAM设计过程的重要阶段
- 划分产生的任务一般不能完全独立执行，需要数据交流
- 功能分解确定了任务间的数据流
- 任务并发执行，但通讯限制了并发性

### 四种通讯模式

| 类型 | 说明 |
|------|------|
| 局部/全局通讯 | 局部：限制在邻域内；全局：如All-to-All、Master-Worker |
| 结构化/非结构化通讯 | 结构化：通讯模式统一；非结构化：无统一模式（如非结构化网格） |
| 静态/动态通讯 | 静态：通讯模式预先确定；动态：运行时确定 |
| 同步/异步通讯 | 同步：阻塞等待；异步：不阻塞，可重叠计算 |

### 通讯判据
- 所有任务是否执行大致相当的通讯？
- 是否尽可能使用局部通讯？
- 通讯操作是否能并行执行？
- 同步任务的计算能否并行执行？

## 组合（Agglomeration）

### 方法描述
- 组合是从抽象到具体的过程
- 将组合的任务在目标并行机上有效执行
- 合并小尺寸任务，减少任务数
- 如果任务数恰好等于处理器数，则同时完成映射
- 增加任务粒度和重复计算，减少通讯成本
- 保持映射和扩展的灵活性，降低软件工程成本

### 表面-容积效应
- 通讯量与任务子集的**表面**成正比
- 计算量与任务子集的**体积**成正比
- 增加粒度（增大体积/表面比）可减少通讯开销

### 重复计算
- 重复计算减少通讯量，但增加计算量，需保持平衡
- 目标：减少算法总运算时间

**示例：N个处理器求N个数的全和**

| 方法 | 步骤数 | 说明 |
|------|--------|------|
| 二叉树求和 | $2\log N$ | 无重复计算，每轮逐层归约 |
| 蝶式求和 | $\log N$ | 使用重复计算，每轮所有处理器均参与 |

### 组合判据
- 增加粒度是否减少了通讯成本？
- 重复计算是否已权衡其得益？
- 是否保持了灵活性和可扩放性？
- 组合的任务数是否与问题尺寸成比例？
- 是否保持了类似的计算和通讯？
- 有没有减少并行执行的机会？

## 映射（Mapping）

### 方法描述
- 将每个任务映射到具体的处理器（计算资源）
- 任务数大于处理器数时，存在负载平衡和任务调度问题
- 映射目标：减少算法执行时间
- 并发的任务 → 不同处理器
- 高通讯的任务 → 同一处理器
- 映射是一种权衡，属于NP完全问题

### 任务映射考虑因素

#### 计算量
| 难度 | 说明 |
|------|------|
| Easy | 所有任务成本相同（unit cost），如branch-free loops |
| Harder | 任务有不同的已知时间，如稀疏矩阵-向量乘法 |
| Hardest | 任务成本在执行前未知，如搜索问题 |

#### 依赖关系
| 难度 | 说明 |
|------|------|
| Easy | 任务可按任意顺序执行（无依赖） |
| Harder | 任务有可预测的依赖结构，如矩阵计算（Cholesky分解） |
| Hardest | 结构动态变化，如稀疏LU分解 |

#### 通信关系
| 难度 | 说明 |
|------|------|
| Easy | 任务创建后不通信（embarrassingly parallel） |
| Harder | 任务按可预测模式通信（规整/非规整），如PDE求解器 |
| Hardest | 通信模式不可预测，如离散事件模拟 |

### 映射模式

#### 静态映射
任务预先映射到计算资源，需对每个任务大小有良好估计（NP完全问题）。
- **基于数据划分的映射**：依照"拥有者进行计算"原则，如按行/列/块分布
- **基于任务图划分的映射**：根据任务依赖图映射（NP完全问题，结构化图有启发式方法）
- **复合映射**：结合数据划分和任务图划分

**数据分布模式示例**：
- 行分布（row-wise）：每行数据分配给一个处理器
- 列分布（column-wise）：每列数据分配给一个处理器
- 块分布（block）：二维/三维块分配给处理器
- 循环分布（cyclic）：轮流分配给各处理器

#### 动态映射
任务在运行时映射到计算资源，适用于任务产生于运行过程中或计算量不可预知的场景。

**集中式动态映射**：
- 主进程分配任务，从进程完成工作后请求新任务
- 主进程可能成为瓶颈，可通过增大块尺寸缓解

**分布式动态映射**：
- 各进程地位相同（P2P方式），互相发送/接收任务
- 减轻集中式瓶颈，需协商调度方案
- 关键问题：进程如何配对？谁初始化传输？传多少数据？何时启动？

### 映射原则：最小化交互开销
- **最大化数据局部性**：复用中间数据，缩小数据重用窗口
- **最小化数据交换量**
- **最小化交互频度**
- **最小化竞争和热点**
- **计算与通信重叠**：使用非阻塞通信、多线程、预取隐藏时延
- **使用成组通信**而非点对点通信

### 映射判据
- 采用集中式负载平衡方案，是否存在通讯瓶颈？
- 采用动态负载平衡方案，调度策略的成本如何？

## PCAM 小结

| 阶段 | 说明 |
|------|------|
| 划分 | 分解为可并行执行的任务（域分解和功能分解） |
| 通讯 | 任务间的数据交换 |
| 组合 | 合并部分任务使计算过程更高效 |
| 映射 | 将任务分配到处理器，保持负载平衡 |

## 并行程序设计模式

### 设计模式
设计模式描述在特定条件下解决重复出现问题的有效方法，记录成功经验供参考。每个模式包括：模式名称、问题、解决方案、效果。

并行程序设计模式分为四个层次：

| 层次 | 说明 |
|------|------|
| 分析并发性 | 关注应用问题宏观分析，完成问题分解 |
| 算法结构 | 细化设计方案，使设计更接近可并行执行的程序 |
| 支持结构 | 将算法转换为程序 |
| 实现机制 | 映射到具体并行计算环境，描述进程/线程管理和数据交换 |

**实现机制包括**：
- 执行单元（UE）管理：线程控制、进程控制
- 同步：内存同步/fences、互斥锁、路障
- 通信：消息传递、组通信、其他通信方式

## 并行编程框架

### 出发点
简化一类问题的并行编程难度和复杂度。

### 实现方式
- 对并行算法的抽象描述
- 提供编程API
- 兼容多种并行计算平台的运行时环境
- 自动任务分配和调度
- 运行期监控和容错

### 结束语
- 从应用问题出发，分析设计并行算法，有一定章法可循
- 并行计算平台多样性致使并行程序设计复用性不足，性能优化困难
- 并行编程框架是并行计算方法与技术的集成
- 我国高性能计算基础软件亟需：并行编程框架、高性能算法库、编译器与编译环境
