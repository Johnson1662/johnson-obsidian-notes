## 2.1 应用层原理（Principles of the Application Layer）

### 应用层的地位

应用层是"网络存在的原因"——互联网架构设计的最终目的就是支持各种应用程序。从电子邮件到社交媒体，从流媒体到搜索引擎，所有用户能感知到的互联网功能都运行在应用层。

一个值得注意的事实是：今天我们所熟知的大部分应用程序（社交媒体、Web、流媒体、在线游戏等）都是在互联网架构确定之后才发展起来的。互联网的分层设计和稳定的传输层抽象（TCP/UDP）为这些前所未有的应用提供了基础，这证明了互联网架构的前瞻性。

### 网络应用架构

网络应用的架构主要有两种模式：

**客户端-服务器模型（Client-Server Model）**
- 服务器（server）是始终在线的主机，拥有固定的、众所周知的IP地址
- 客户端（client）向服务器发起请求，服务器响应请求
- 客户端之间不直接通信，必须通过服务器中转
- 典型例子：Web（HTTP）、电子邮件（SMTP）、文件传输（FTP）
- 大型服务通常使用数据中心（data center）来部署大量服务器

**对等模型（Peer-to-Peer Model, P2P）**
- 没有专门的服务器，每个节点既是客户端又是服务器
- 节点之间直接通信，利用对方的计算和存储资源
- 具有自扩展性（self-scalability）：每个新节点既是消费者也是提供者
- 典型例子：BitTorrent、早期的Skype
- 挑战：安全性、激励、免费搭车（free-riding）问题

### 进程通信

应用层通信的本质是进程之间的通信。进程通过套接字（socket）与传输层交互，套接字是应用层与传输层之间的接口。

进程通信需要解决两个核心问题：
1. 如何标识对方主机？——通过IP地址
2. 如何标识对方主机上的特定进程？——通过端口号（port number）

### 传输层服务需求

不同应用对传输层服务的需求各不相同：

| 需求 | 说明 | 典型应用 |
|------|------|----------|
| 可靠性 | 数据必须完整、正确地到达 | 文件传输、Web页面 |
| 时延 | 数据必须在一定时间内到达 | 视频会议、在线游戏 |
| 带宽 | 需要足够的传输带宽 | 视频流媒体 |
| 安全性 | 数据需要加密和认证 | 网上银行、电子商务 |

### 互联网提供的传输层协议

互联网传输层提供两种协议，应用层需要根据需求选择：

- **TCP**：面向连接、可靠传输、流量控制、拥塞控制。适合需要可靠传输的应用
- **UDP**：无连接、不可靠、无流量控制和拥塞控制。适合对延迟敏感、能容忍少量丢失的应用

值得注意的是，互联网传输层不提供时延保证和带宽保证，这是互联网"尽力而为"服务模型的体现。

## 2.2 Web 与 HTTP

### Web 基础

Web（World Wide Web）是最广泛使用的互联网应用之一。Web页面由对象（object）组成，每个对象通过URL（Uniform Resource Locator）寻址。

**URL格式**：`协议://主机名:端口/路径?查询参数#片段`

### HTTP 协议

HTTP（HyperText Transfer Protocol）是Web的应用层协议，定义了浏览器和Web服务器之间的通信规则。

**HTTP的特点**：
- 使用TCP作为传输层协议（默认端口80，HTTPS为443）
- 无状态协议（stateless）：服务器不保存客户端的先前请求信息
- 请求/响应模型：客户端发送HTTP请求，服务器返回HTTP响应

**HTTP请求方法**：
- GET：请求获取资源
- POST：提交数据给服务器
- PUT：上传资源
- DELETE：删除资源
- HEAD：获取资源的元信息

**HTTP响应状态码**：
- 200 OK：请求成功
- 301 Moved Permanently：资源已永久移动
- 400 Bad Request：请求有误
- 404 Not Found：资源未找到
- 500 Internal Server Error：服务器内部错误

### 持久连接与非持久连接

**非持久连接（Non-persistent Connection）**：
- 每个HTTP请求/响应对使用一个独立的TCP连接
- 缺点：每次连接需要三次握手，增加RTT开销
- HTTP/1.0默认使用非持久连接

**持久连接（Persistent Connection）**：
- 多个HTTP请求/响应对可以复用同一个TCP连接
- 减少了连接建立的开销和延迟
- HTTP/1.1默认使用持久连接

### Cookie

由于HTTP是无状态协议，服务器无法自动识别用户。Cookie机制解决了这个问题：

1. 服务器在响应中设置Cookie（Set-Cookie头部）
2. 客户端（浏览器）保存Cookie
3. 后续请求中，客户端自动携带Cookie发送给服务器
4. 服务器通过Cookie识别用户身份和状态

Cookie的应用：用户认证、购物车、个性化推荐等。

### Web 缓存（Web Cache）

Web缓存（也称代理服务器，proxy server）是代表原始服务器响应客户端请求的网络实体。

**工作原理**：
1. 浏览器配置为将请求发送到Web缓存
2. 缓存检查是否有所请求的对象
3. 如果有（缓存命中，cache hit），直接返回给客户端
4. 如果没有（缓存未命中，cache miss），缓存向原始服务器请求对象，保存副本后返回给客户端

**Web缓存的优势**：
- 减少客户端请求的响应时间（缓存离客户端更近）
- 减少机构访问链路上的流量
- 减轻原始服务器的负载

**性能量化示例**：
假设接入链路带宽1.54 Mbps，对象大小100 Kbit，请求速率15 req/s，则接入链路利用率约为97%，排队延迟极高。安装Web缓存后（假设40%命中率），只有60%的流量需要从原始服务器获取，链路利用率大幅降低。

### 条件 GET（Conditional GET）

条件GET允许缓存验证其保存的对象是否仍然是最新的：
- 缓存发送带有`If-Modified-Since`头部的GET请求
- 如果对象未修改，服务器返回304 Not Modified（不传输对象内容）
- 如果对象已修改，服务器返回新的对象

### HTTP/2

HTTP/2的主要改进：
- 多路复用（multiplexing）：在单个TCP连接上并行传输多个请求/响应
- 头部压缩（header compression）
- 服务器推送（server push）
- 减少页面加载时间

## 2.3 电子邮件（Email）

### 电子邮件概述

电子邮件是一个已经存在很长时间的应用程序（自1972年以来）。它可能不是最令人兴奋的应用程序，但它是客户端-服务器模型的一个很好的例子。

电子邮件系统作为分布式应用程序，有三个组件：
1. **用户代理（User Agent）**：邮件客户端，用户使用的软件（如Outlook、Gmail网页版）
2. **邮件服务器（Mail Server）**：包含邮箱（mailbox）和消息队列（message queue）
3. **SMTP（Simple Mail Transfer Protocol）**：位于电子邮件核心的邮件传输协议

本节将关注两件事：
- 电子邮件的基础设施（作为分布式应用的用户代理和邮件服务器）
- SMTP协议

### 电子邮件传输过程

发送邮件的完整流程：
1. 发送方用户代理通过SMTP将邮件发送到发送方邮件服务器
2. 发送方邮件服务器通过SMTP将邮件传输到接收方邮件服务器
3. 接收方用户代理从接收方邮件服务器获取邮件（通过POP3或IMAP）

### SMTP（Simple Mail Transfer Protocol）

SMTP的特点：
- 使用**可靠的TCP连接**，端口25
- 是一个"推"（push）协议——发送方主动将邮件推送到接收方服务器
- 使用持久连接（在连接打开时可以传输多个消息）
- 邮件内容必须是**7位ASCII格式**（最初的设计限制，后来通过MIME扩展支持非ASCII内容）
- **命令/响应模型**：发送方发出命令，接收方返回三位的响应码

**SMTP交互示例**：
```
S: 220 mail.server.com                    // 服务器就绪
C: HELO client.com                        // 客户端标识
S: 250 Hello client.com                   // 服务器确认
C: MAIL FROM: <alice@client.com>         // 发件人
S: 250 OK                                 // 确认
C: RCPT TO: <bob@server.com>             // 收件人
S: 250 OK                                 // 确认
C: DATA                                   // 开始传输数据
S: 354 Start mail input                   // 可以发送数据了
C: （邮件正文）                             // 邮件内容
C: .                                      // 数据结束标志
S: 250 OK                                 // 传输成功
C: QUIT                                   // 断开连接
S: 221 Bye                                // 再见
```

**SMTP的关键特性**：
- SMTP客户端（发送方服务器）在建立TCP连接后，使用一系列命令与服务器通信
- 邮件头部（header）和正文（body）之间用空行分隔
- 邮件以单独的一行"."结束
- 如果接收方用户不可达，邮件会放在队列中稍后重试

### 邮件访问协议

SMTP是"推"协议，负责将邮件从发送方推送到接收方的邮件服务器。但接收方用户**获取**邮件需要使用"拉"（pull）协议：

**POP3（Post Office Protocol version 3）**：
- 端口110
- 功能简单：下载邮件、可选在服务器上保留或删除
- 无文件夹管理功能
- 一旦下载到本地，用户可以在本地管理邮件

**IMAP（Internet Mail Access Protocol）**：
- 端口143
- 功能更强大
- 邮件保留在服务器上，支持多设备同步
- 支持文件夹管理、在服务器上搜索邮件等
- 更适合现代多设备使用场景

**HTTP**：
- 现代Web邮件（Gmail、Outlook.com）使用HTTP作为邮件访问协议
- 用户通过浏览器与邮件服务器交互

### 邮件格式

邮件由**头部（header）和正文（body）**组成。RFC 5322定义了邮件格式标准。

```
From: alice@client.com
To: bob@server.com
Subject: Hello

This is the message body.
```

头部字段包括From、To、Subject、Date等。最初邮件只支持ASCII文本，后来通过MIME（Multipurpose Internet Mail Extensions）扩展支持非ASCII字符、附件等。

### 电子邮件基础设施的更多细节

**邮件服务器之间的中继**：
- 邮件可能经过多个SMTP中继服务器才到达目的地
- 每个中继服务器接收邮件并转发到下一跳
- DNS的MX记录用于查找目标域的邮件服务器

**邮件队列**：
- 如果接收方服务器暂时不可用，发送方服务器会将邮件放入队列
- 定期重试发送
- 多次重试失败后，发送退信通知给原始发件人

## 2.4 DNS 域名系统（Domain Name System）

### DNS 的作用

DNS是互联网的核心基础设施，负责将人类可读的主机名（如 gaia.cs.umass.edu）翻译为机器可识别的IP地址（如 128.119.41.86）。

DNS不仅仅提供名称到IP地址的翻译，还提供以下服务：
- **主机别名（Host Aliasing）**：将简单别名映射到复杂的主机名
- **邮件服务器别名（Mail Server Aliasing）**：如 mail.cs.umass.edu 映射到实际邮件服务器
- **负载均衡（Load Distribution）**：一个主机名对应多个IP地址，DNS轮询返回不同IP

### DNS 的分布式架构

DNS采用分层分布式数据库的设计，而非集中式。集中式设计的缺点包括：
- 单点故障
- 流量集中
- 远距离访问延迟大
- 维护困难，无法扩展

**DNS层次结构**：

1. **根DNS服务器（Root DNS Servers）**：全球有13个逻辑根服务器（实际通过任播部署了数百个物理实例），由ICANN管理。根服务器不直接提供最终解析，而是指引查询到正确的顶级域服务器

2. **顶级域服务器（Top-Level Domain Servers, TLD）**：负责 .com、.edu、.net、.org 等国家代码顶级域（如 .cn、.uk）

3. **权威DNS服务器（Authoritative DNS Servers）**：每个组织维护自己的权威DNS服务器，负责解析其域内的名称。如 UMass 的权威服务器负责所有 *.umass.edu 的解析

此外，还有**本地DNS服务器（Local DNS Server / ISP DNS Resolver）**：每个ISP都运行一个本地DNS服务器，作为代理执行DNS查询。

### DNS 解析过程

以解析 www.amazon.com 为例：

1. 客户端向本地DNS服务器发送查询请求
2. 本地DNS服务器向根DNS服务器查询 .com TLD服务器的地址
3. 本地DNS服务器向 .com TLD服务器查询 amazon.com 权威服务器的地址
4. 本地DNS服务器向 amazon.com 权威服务器查询 www.amazon.com 的IP地址
5. 本地DNS服务器将结果返回给客户端

**递归查询 vs 迭代查询**：
- 递归查询：客户端要求本地DNS服务器必须返回最终结果
- 迭代查询：本地DNS服务器依次向各级服务器查询，每次返回下一级服务器的地址

### DNS 缓存

DNS服务器会缓存已解析的记录，缓存时间由TTL（Time To Live）字段指定。缓存机制大幅减少了DNS查询的延迟和网络流量。

### DNS 记录格式

DNS记录（Resource Record, RR）的格式为：`(Name, Value, Type, TTL)`

| Type | Name | Value | 说明 |
|------|------|-------|------|
| A | 主机名 | IP地址 | 主机名到IPv4地址的映射 |
| AAAA | 主机名 | IPv6地址 | 主机名到IPv6地址的映射 |
| NS | 域名 | 权威DNS服务器主机名 | 指定该域的权威服务器 |
| CNAME | 别名 | 规范主机名 | 主机别名到规范名的映射 |
| MX | 域名 | 邮件服务器主机名 | 指定域的邮件服务器 |

### DNS 协议

DNS协议使用UDP传输（端口53），消息格式包含：
- 头部：标识符、标志、问题数、回答数等
- 问题段：查询的主机名和类型
- 回答段：资源记录
- 权威段：权威服务器记录
- 附加段：额外信息

## 2.5 P2P 文件分发

> 注：本节字幕文件缺失，以下基于课程知识体系整理。

### P2P 分发的时间分析

在P2P架构中，文件分发时间取决于：
- 服务器上传带宽（u_s）
- 每个对等方的上传带宽（u_i）
- 每个对等方的下载带宽（d_i）
- 对等方数量（N）
- 文件大小（F）

P2P分发时间：D_P2S = max{F/u_s, F/d_min, NF/(u_s + Σu_i)}

当N很大时，P2P架构的优势明显：每个新加入的对等方既是下载者也是上传者，系统总带宽随用户数增长而增长。

## 2.6 视频流与内容分发网络（Video Streaming and CDNs）

### 视频的本质

视频是由一系列图像（帧）组成的，通常以每秒24-30帧的速率播放。每个图像由像素矩阵组成，通过编码技术压缩以减少数据量。

**视频编码**：
- 空间编码（Spatial Coding）：利用图像内部的冗余（如大片相同颜色的区域）
- 时间编码（Temporal Coding）：利用帧与帧之间的冗余（只传输变化的部分）
- 编码标准：MPEG-1、MPEG-2、MPEG-4、H.264、H.265等
- 恒定比特率（CBR）vs 可变比特率（VBR）

### 流媒体面临的挑战

1. **带宽变化**：源和目的之间的可用带宽随时间变化（家庭网络拥塞、接入网、核心网等）
2. **延迟变化**：分组交换网络中的延迟不固定，没有电路交换的保证

### 客户端缓冲（Client Buffering）

为了应对可变的网络延迟，客户端使用缓冲区：
- 服务器以恒定速率发送视频
- 客户端将数据存入缓冲区
- 播放从缓冲区中取出数据
- 只要缓冲区不为空，播放就不会中断

**连续播放约束**：客户端的播放时间必须与视频录制时间匹配，不能出现卡顿。

### DASH（Dynamic Adaptive Streaming over HTTP）

DASH是一种基于HTTP的自适应流媒体技术：
- 视频被编码为多个不同比特率的版本
- 每个版本被分割为小的片段（chunk），通常2-10秒
- 客户端根据当前可用带宽动态选择下一个片段的比特率
- 带宽好时选择高比特率，带宽差时选择低比特率
- 所有片段通过HTTP GET请求获取，可以利用现有的Web基础设施

### CDN（Content Distribution Network）

CDN是支撑大规模视频流服务的分布式基础设施。

**CDN的核心思想**：将内容复制到地理上分布的多个服务器上，使用户能从最近的服务器获取内容。

**CDN的工作原理**：
1. 内容提供商将内容分发到CDN服务器
2. 用户请求内容时，DNS将用户引导到最近的CDN服务器
3. CDN服务器向用户提供内容

**CDN的优势**：
- 减少用户访问延迟
- 减轻源服务器的负载
- 提高内容的可用性和可靠性

**CDN的典型代表**：Akamai、Cloudflare、Amazon CloudFront

**Netflix的CDN架构**：
- Netflix使用自己的CDN（Open Connect）
- 将视频内容预部署到ISP网络内部的服务器
- 用户直接从ISP网络内的服务器获取视频，不经过公共互联网

## 2.7 Socket 编程

### Socket 概述

套接字（Socket）是应用层代码与传输层服务之间唯一的API接口。如果想从分布式应用程序的一部分向另一部分发送应用层消息，直接访问互联网的传输层服务，就必须使用套接字。

从系统角度看，应用程序写在用户空间（操作系统之外），而传输层在操作系统内部。套接字是应用层程序和传输层之间的接口门（interface door）。

套接字API提供两种类型的传输层服务：
1. 可靠的、拥塞控制的、面向字节流的数据传输（TCP服务）
2. 面向数据报的不可靠服务（UDP服务）

### 一个简单的客户端-服务器示例

课程通过一个简单的Python客户端-服务器应用程序来演示套接字编程：

**应用程序功能**：
- 客户端从键盘读取一行字符数据
- 将数据发送到服务器
- 服务器接收数据，将字符转换为大写
- 将大写翻译后的结果发送回客户端
- 客户端从服务器接收并显示在屏幕上

### UDP Socket 编程

使用UDP服务时，客户端和服务器之间没有连接，意味着之前没有握手过程。客户端发送数据报时必须明确包含服务器的IP地址和端口号。

UDP提供的是不可靠的、实际上无序的数据报传输服务。数据报在传输过程中可能丢失，也可能被错误排序。

**客户端步骤**：
1. 创建UDP套接字
2. 从键盘读取一行字符数据
3. 将数据发送到服务器（需指定服务器IP地址和端口号）
4. 等待接收服务器的响应
5. 关闭套接字

**服务器端步骤**：
1. 创建UDP套接字
2. 绑定端口
3. 等待接收客户端的数据报
4. 从数据报中提取客户端IP地址和端口号
5. 将字符转换为大写
6. 将结果发送回客户端
7. 关闭套接字

### TCP Socket 编程

TCP是面向连接的协议，客户端和服务器在通信前需要建立连接。

**客户端步骤**：
1. 创建TCP套接字
2. 与服务器建立连接（三次握手）
3. 发送数据
4. 接收服务器的响应
5. 关闭连接

**服务器端步骤**：
1. 创建TCP套接字
2. 绑定端口
3. 监听连接请求
4. 接受客户端连接（创建新的连接套接字）
5. 通过连接套接字收发数据
6. 关闭连接

## 核心概念总结

| 概念 | 英文 | 说明 |
|------|------|------|
| 应用层 | Application Layer | 网络应用程序运行的最高层 |
| HTTP | HyperText Transfer Protocol | Web应用层协议 |
| SMTP | Simple Mail Transfer Protocol | 邮件传输协议 |
| DNS | Domain Name System | 域名系统，将主机名翻译为IP地址 |
| Cookie | Cookie | 服务器在客户端保存的状态信息 |
| Web缓存 | Web Cache / Proxy | 代表源服务器响应请求的中间服务器 |
| CDN | Content Distribution Network | 内容分发网络 |
| DASH | Dynamic Adaptive Streaming over HTTP | 基于HTTP的动态自适应流媒体 |
| Socket | Socket | 应用层与传输层之间的接口 |
| 持久连接 | Persistent Connection | 复用TCP连接传输多个HTTP请求 |
| 非持久连接 | Non-persistent Connection | 每个HTTP请求使用独立TCP连接 |
