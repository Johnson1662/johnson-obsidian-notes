## 3.1 传输层服务与协议概述

### 传输层在互联网架构中的地位

传输层是互联网架构的关键部分之一。本章将研究以下根本性的重要挑战：

1. 两个实体如何通过消息可能被破坏或丢失的通道进行可靠通信
2. 分布式实体如何同步共享状态
3. 不同实体的集合如何调整通信速率，以避免溢出和耗尽网络资源

### 研究方法

课程采用"从原则到实践"的方法：先学习多路复用/分解(multiplexing/demultiplexing)、可靠数据传输、流量控制和拥塞控制的基本原则，再研究这些原则如何体现在Internet传输协议UDP和TCP中。

### 传输层提供的两种主要服务

- UDP（User Datagram Protocol）：提供无连接的、尽最大努力(best-effort)的服务
- TCP（Transmission Control Protocol）：提供可靠的、面向连接的、具备流量控制和拥塞控制的服务

### 逻辑通信的概念

从传输层的角度来看，通信双方（发送者和接收者）在逻辑上通过直接链路相互连接。尽管两台主机可能位于地球两侧，中间隔着许多不同的路由器和链路，但从逻辑上可以抽象为发送者和接收者直接相连。

通信信道可能丢失消息、重新排序消息或翻转消息中的比特，但传输层将两个通信进程之间的一切抽象化，专注于连接它们的信道特性。

### 传输层与网络层的区别

用一个类比来说明：

- 两栋房子 = 两台互联网主机
- 每栋房子里的十二个孩子 = 每个主机上运行的进程
- 房子之间传递的信封 = 应用程序级消息
- 邮政服务 = 网络层协议（负责在主机之间投递数据）
- 房子里把信交给对应孩子的过程 = 传输层协议（负责把数据交付给正确的进程）

网络层协议（如IP）相当于邮政服务，只负责在主机之间投递信件；传输层协议负责将到达主机的数据交付给适当的应用进程。

### 传输层发送方和接收方的操作

**发送方：**
1. 应用层进程创建消息并放入套接字(socket)
2. 传输层接收应用层消息，确定头字段值，创建传输层段(segment)
3. 将段传递给网络层（IP协议）
4. IP协议将IP数据报通过Internet传递到接收主机

**接收方：**
1. 传输层从网络层接收段
2. 检查头字段值（如校验和），确保段未被损坏
3. 提取应用层消息
4. 将消息解复用(demultiplex)到适当的应用层套接字

### TCP与UDP的对比

| 特性 | TCP | UDP |
|------|-----|-----|
| 可靠性 | 可靠、有序交付 | 不可靠、尽力而为 |
| 连接性 | 面向连接 | 无连接 |
| 流量控制 | 有 | 无 |
| 拥塞控制 | 有 | 无 |
| 数据语义 | 字节流 | 面向消息 |

### 互联网传输层不提供的服务

互联网传输层不保证消息之间的时间延迟（timing guarantee），即不保证消息从发送到接收的最大时延。

## 3.2 多路复用与多路分解

> 注意：本节字幕内容存在提取错误，无法从字幕中获取有效内容。以下基于课程知识体系补充核心概念。

### 基本概念

多路复用(multiplexing)和多路分解(demultiplexing)是传输层的基本功能：

- **多路复用**：在发送方，从多个套接字收集数据块，为每个数据块封装上头部信息（包含源端口号和目的端口号），生成段，然后将段传递给网络层。
- **多路分解**：在接收方，传输层检查段中的目的端口号，将段中的数据交付到正确的套接字。

### 端口号的作用

端口号是一个16位的整数（0-65535），用于标识主机上的特定进程：
- 知名端口号（well-known ports）：0-1023，预留给标准服务（如HTTP=80，DNS=53）
- 注册端口号：1024-49151
- 动态/私有端口号：49152-65535

### 无连接的多路复用与分解（UDP）

UDP套接字由二元组标识：(目的IP地址, 目的端口号)。两个UDP段如果具有相同的目的IP地址和目的端口号，就会被导向同一个套接字，无论它们的源IP地址和源端口号是否相同。

### 面向连接的多路复用与分解（TCP）

TCP套接字由四元组标识：(源IP地址, 源端口号, 目的IP地址, 目的端口号)。TCP服务器通常使用一个欢迎套接字(listening socket)接受连接请求，然后为每个客户端创建一个新的连接套接字。因此，不同源（不同客户端）的段即使目的端口相同，也会被分解到不同的套接字。

## 3.3 无连接传输：UDP

### UDP概述

UDP（User Datagram Protocol，用户数据报协议）是一个极其简单的协议，提供尽力而为的服务。UDP段可能丢失，可能无序到达。UDP发送方和接收方之间不需要握手，不需要共享状态，因此UDP被称为无连接协议。

### 为什么需要UDP

尽管UDP非常简单，但它有存在的充分理由：

1. **无连接建立延迟**：UDP发送方无需等待连接建立即可直接发送数据报
2. **无共享连接状态**：发送方和接收方不需要维护连接状态
3. **头部开销小**：UDP头部非常简单
4. **无拥塞控制**：UDP发送方可以按自己的速率发送数据，即使网络拥塞也不受影响，这对某些应用（如实时流媒体）非常重要

### UDP的适用场景

- 流式多媒体应用：能容忍一定数量的段丢失，但对延迟敏感，不能接受拥塞控制带来的速率波动
- DNS、SNMP等：在网络拥塞时仍能正常操作非常重要
- 需要在应用层构建可靠传输的场景：如HTTP/3在UDP之上实现了自己的可靠传输机制

### UDP的RFC规范

UDP在RFC 768中定义，规范非常简短（仅约三页），是最容易阅读的互联网RFC之一。

### UDP发送方和接收方的操作

**发送方：**
1. 应用层将消息传递给UDP
2. UDP填写头部字段值，形成UDP段（应用层消息作为有效载荷）
3. 将UDP段传递给IP
4. IP将IP数据报转发到接收主机

**接收方：**
1. UDP从网络层接收段
2. 执行UDP校验和检查
3. 提取应用层消息
4. 将消息解复用到适当的应用层套接字

### UDP段格式

UDP段结构非常简单，头部只有四个字段：

| 字段 | 说明 |
|------|------|
| 源端口号（16位） | 发送方的端口号，用于多路分解 |
| 目的端口号（16位） | 接收方的端口号，用于多路分解 |
| 长度（16位） | UDP段的总长度（头部+数据），因为有效载荷长度可变 |
| 校验和（16位） | 用于检测段在传输过程中的错误 |

### UDP校验和（Internet Checksum）

UDP校验和的作用是检测UDP段在发送方到接收方传输过程中是否发生了比特翻转。

**计算方法：**
1. 发送端将UDP段的内容视为16位整数的序列
2. 将这些16位整数相加，取补数和（one's complement sum）
3. 将计算结果放入UDP校验和字段
4. 接收端重新计算接收段的校验和
5. 比较计算结果与校验和字段中的值：
   - 如果不相等，说明检测到错误
   - 如果相等，未检测到错误（但仍可能有未检测到的错误）

**直观理解：** 假设发送方要发送两个数5和6，同时发送它们的和11。接收方收到三个数后，将前两个数相加，检查是否等于第三个数。如果5被翻转为4，接收方计算4+6=10，与收到的校验和11不一致，即可发现错误。

## 3.4 可靠数据传输原理

### 问题背景

可靠数据传输（Reliable Data Transfer）是网络中最根本的挑战之一：两个分布式实体如何在本身不可靠的通道上可靠通信？通道可能丢失消息、损坏消息或重新排序消息。

### 基本模型

- 发送进程希望通过可靠通道将数据发送到接收进程
- 可靠通道是单向的（数据从发送方到接收方）
- 实现以可靠数据传输协议（rdt, reliable data transfer protocol）的形式进行
- 协议有发送端和接收端两个方面
- 协议实体之间通过不可靠的双向信道交换消息

### 关键认识

协议的一方不知道另一方发生了什么或信道中发生了什么，他们之间好像有一道帘子。发送方无法直接知道它发送的消息是否到达接收方，只有当接收方向发送方发回确认信号时，发送方才能获知。

### 协议接口（API）

- 发送端：数据从应用层进程向下传递到传输层，传输层添加头部创建段，通过不可靠信道发送
- 接收端：从不可靠信道接收段，提取数据，传送到应用层的接收进程
- 要求：从发送端发送的每一条数据都准确地传递一次且仅一次到接收进程

### 有限状态机（Finite State Machine, FSM）

为了正式指定协议，课程采用有限状态机作为协议规范技术。

**核心概念：**
- **状态（State）**：系统在某时刻所处的状况（如灯泡的"开"或"关"）
- **事件（Event）**：导致状态转换的触发条件（如按下开关）
- **动作（Action）**：状态转换时系统执行的操作（如灯泡发光）

**灯泡示例：**
- 状态：开、关
- 事件：按下开开关、按下关开关
- 转换：关→开（按下开开关，灯亮）；开→关（按下关开关，灯灭）

> 注意：本节字幕内容在关键部分被截断，以下基于课程知识体系补充可靠数据传输的核心协议机制。

### rdt协议的发展

**rdt1.0：完美信道**
- 假设信道完全可靠，不丢失、不损坏、不乱序
- 发送方直接发送数据，接收方直接接收

**rdt2.0：有比特错误的信道**
- 引入校验和检测错误
- 引入ACK（确认）和NAK（否定确认）反馈机制
- 发送方收到ACK后发送下一段，收到NAK后重传
- 停等协议（stop-and-wait）：发送方每次只发送一个段

**rdt2.1：处理ACK/NAK损坏**
- 为序列号（sequence number）引入序列号字段
- 发送方在每个段中添加序列号（0或1交替）
- 接收方通过序列号判断是否为重复段

**rdt2.2：无NAK协议**
- 用ACK+序列号替代NAK
- 接收方在ACK中携带期望接收的下一个序列号

**rdt3.0：有丢失和比特错误的信道**
- 引入超时（timeout）机制
- 发送方设置计时器，超时未收到ACK则重传
- 需要权衡：超时太短导致过早重传，太长导致响应慢

### 流水线技术（Pipelining）

停等协议的效率很低，因为发送方在等待ACK期间处于空闲状态。流水线技术允许发送方同时发送多个段而不必等待确认。

流水线协议需要：
1. 更大的序列号范围
2. 发送方和接收方需要更大的缓冲空间

**两种流水线协议：**
- **回退N步（Go-Back-N, GBN）**：发送方可以连续发送最多N个未确认的段（窗口大小为N），接收方只按序确认。如果某个段丢失，发送方需要重传该段及其之后的所有段。
- **选择重传（Selective Repeat, SR）**：发送方和接收方都维护窗口，接收方对每个段单独确认，发送方只重传丢失的段。

## 3.5 TCP：可靠性、流量控制与连接管理

### TCP概述

TCP（Transmission Control Protocol，传输控制协议）的特性：

- **点对点（point-to-point）**：在一个发送者和一个接收者之间运行
- **有序字节流**：提供可靠的、有序的字节流语义（与UDP的面向消息不同）
- **全双工（full-duplex）**：数据有效载荷可以双向流动
- **最大段大小（MSS, Maximum Segment Size）**：通常为1460字节
- **累积确认（cumulative acknowledgment）**：使用累积确认机制
- **流水线（pipelined）**：采用流水线协议，不是停等协议
- **面向连接（connection-oriented）**：在数据流动之前需要握手建立连接
- **流量控制（flow control）**：发送者和接收者进行速度匹配

### TCP段结构

TCP段头部包含以下字段：

| 字段 | 说明 |
|------|------|
| 源端口号（16位） | 用于多路复用/分解 |
| 目的端口号（16位） | 用于多路复用/分解 |
| 序列号（32位） | 该段有效载荷中第一个字节的字节流编号 |
| 确认号（32位） | 接收方期望从发送方接收的下一个字节的序列号，用作累积确认 |
| 头部长度 | TCP头部的长度（因为选项字段使头部长度可变） |
| 选项 | 可变长度的选项字段 |
| 校验和（16位） | 检测传输错误 |
| RST位、SYN位、FIN位 | 用于连接管理 |
| 接收窗口（16位） | 流量控制：接收方告诉发送方愿意接受的字节数 |
| 拥塞通知位（2位） | 用于显式拥塞通知（ECN） |
| 紧急数据指针（16位） | 实践中很少使用 |

### 序列号和确认号

TCP实现的是字节流抽象。TCP段头中携带的序列号指示该段有效载荷数据中第一个字节的字节流编号。确认号字段由接收方使用，告诉发送方预期接收的下一个字节的序列号，该数字用作累积确认。

**示例（telnet场景）：**
- 主机A向主机B发送一个字符，主机B将单个字符回显
- 序列号和确认号的关系：确认号 = 触发确认的段的序列号 + 1
- 例如：A→B的段序列号为4，则B→A的确认号为5

**无序段的处理：** TCP规范对接收方如何处理无序段没有强制要求，取决于具体实现。

### RTT估计与超时设置

如何设置超时值是TCP的关键问题：

- 超时太短 → 过早超时（premature timeout），取消实际上未丢失的段
- 超时太长 → TCP对段丢失反应过慢

**测量RTT：** 在段传输时启动计时器，收到对应的ACK时停止计时器，得到一个SampleRTT。

**指数加权移动平均（EWMA）：** 由于SampleRTT在样本间可能有很大差异，TCP使用指数加权移动平均来平滑估计：

```
EstimatedRTT_new = (1 - α) × EstimatedRTT_old + α × SampleRTT
```

- α的典型值为0.125
- 这反映了最近测量对估计RTT的影响

**超时间隔计算：**
```
TimeoutInterval = EstimatedRTT + 安全裕度
```

安全裕度的设置考虑了RTT样本的变化程度：如果RTT变化大，安全裕度应更大。

### 流量控制（Flow Control）

流量控制是一种避免接收方被发送速度过快的发送方淹没的机制。它允许接收方显式地控制发送者，防止发送方溢出接收方的缓冲区。

**类比：** 没有人想从消防水管里喝水。

**TCP实现流量控制的方式：**
1. 接收方通知发送方有多少空闲缓冲区空间
2. 发送方被限制发送不超过这个数量的数据
3. 接收方设置的限制表示为变量rwnd（接收方广告窗口）
4. 此信息通过TCP头部的接收方广告窗口字段从接收方传送到发送方
5. 该值随空闲缓冲区空间的数量随时间波动而变化

### 连接管理

TCP是面向连接的，发送方和接收方需要在通信开始前建立共享状态，包括：
1. 双方同意进行通信
2. 协商连接参数：初始序列号、初始接收方广告窗口

#### 双向握手的问题

双向握手（客户端发送连接请求，服务器回复接受）在网络环境中存在严重问题：

**场景1（正常）：** 客户端发送序列号为x的连接请求 → 服务器接受 → 双方进入已建立状态 → 正常通信 → 正常关闭。没有问题。

**场景2（延迟的重传连接请求）：** 客户端的连接请求被延迟重传，在第一个连接关闭后到达服务器。服务器误以为是新连接请求，发送接受消息并进入已建立状态，但客户端并不在等待。导致服务器在无客户端的情况下维持一个连接。

**场景3（延迟的重传连接请求+数据）：** 除了场景2的问题外，如果延迟的数据段也在连接关闭后到达，服务器可能将其作为新连接的数据处理，导致同一条消息被执行两次（如"从银行账户取出100美元"被执行两次）。

#### TCP三次握手

TCP使用三次握手来解决上述问题：

1. **第一次握手：** 客户端向服务器发送SYN段（TCP段，头部中设置SYN位），包含初始序列号x
2. **第二次握手：** 服务器接收SYN段，回复SYNACK段，包含自己的初始序列号y，以及对客户端序列号的确认（x+1）
3. **第三次握手：** 客户端接收SYNACK段，回复ACK段，包含对服务器序列号的确认（y+1），此时可以携带应用数据

三次握手确保双方都同意建立连接，并交换了初始序列号，同时避免了双向握手的延迟重传问题。

## 3.7 TCP拥塞控制

### 拥塞崩溃

拥塞崩溃（congestion collapse）是一种非常非直觉的行为：随着TCP发送者提高总发送速率，端到端的总吞吐量实际上反而下降了。

在20世纪80年代，TCP还没有拥塞控制机制，拥塞崩溃开始在网络中观察到。

### Van Jacobson的开创性贡献

1988年，网络研究员Van Jacobson发表了关于避免和控制拥塞的开创性论文，为TCP拥塞控制奠定了基础。令人惊叹的是，这一机制三十年来基本未变，即使互联网承载的流量已上升超过十亿倍。

### TCP拥塞控制的基本思想

TCP采用端到端的方法进行拥塞控制，通过丢失事件检测拥塞（而非依赖网络路由器发出信号）：

- 当网络路径不拥塞时（TCP连接没有丢失），发送者可以提高发送速率
- 当段丢失发生时，发送者必须降低发送速率

### 加法递增乘法减少（AIMD）

TCP使用的特殊递增递减算法称为加法递增乘法减少（Additive Increase, Multiplicative Decrease, AIMD）：

- **加法递增（AI）**：每个RTT将发送速率增加一个段
- **乘法减少（MD）**：当丢失发生时，将发送速率减半

这导致了一种锯齿行为：发送速率逐步增加，直到发生丢失事件后减半，然后再次逐步增加。

**AIMD的直观理解：** TCP发送者试图找到不遭受损失的最快传输速率。就像孩子不断要求更多，直到家长说"够了"，然后退后，过一段时间又开始试探新的限制。

### 丢失检测的两种情况

1. **三个重复ACK（triple duplicate ACKs）**：当连续三个累积确认到达时（意味着有一个段丢失，但该段之后的三个段已收到），TCP将拥塞窗口减半
2. **超时（timeout）**：如果发生超时，TCP将拥塞窗口大小重置为一个段

### TCP拥塞窗口（Congestion Window, cwnd）

TCP通过调节拥塞窗口（cwnd）的大小来控制发送速率：

- 已确认的段（绿色）
- 已发送但未确认的段（黄色）
- 可以发送的段（拥塞控制算法允许发送）
- 不能发送的段（发送它们意味着TCP发送太快）

TCP发送速率的计算：
```
发送速率 = cwnd / RTT （字节/秒）
```

### 慢启动（Slow Start）

TCP连接初始阶段采用慢启动算法：

- 初始发送速率为每RTT一个MSS
- 每个RTT使发送速率翻倍（指数级增长）
- 尽管名为"慢启动"，实际上增长是指数级的

慢启动阶段持续到发生丢失事件或达到慢启动阈值（ssthresh），然后进入拥塞避免阶段。

### AIMD的稳定性

AIMD算法已被正式证明是一种分布式异步优化算法：不同的发送者单独设置发送速率，基于各自接收到的丢失反馈信号，这种分布式算法实际上优化了整体流量并具有良好的稳定性。

### 基于延迟的拥塞控制

除了基于丢失的经典TCP拥塞控制外，还有基于延迟的方法，通过测量RTT的变化来检测拥塞。

### 显式拥塞通知（ECN, Explicit Congestion Notification）

显式拥塞通知是一种网络辅助的拥塞控制方法，IP路由器在拥塞控制中发挥积极作用，通过标记IP数据报来通知发送方网络出现拥塞，而不是等待段丢失。

### TCP公平性

TCP拥塞控制的一个重要特性是公平性：当多个TCP连接共享同一条瓶颈链路时，它们最终会收敛到公平分配带宽的状态。这是因为AIMD算法的特性——当带宽被占用时，所有连接都会因拥塞而减半，从而实现公平分配。

## 3.8 传输层演进

### TCP与UDP的40年历程

TCP和UDP协议已经存在了40多年（TCP经历了一些修改）。40年的使用证明了它们提供了一套简单但足够的服务，能够适应从最早期的互联网应用（电子邮件、FTP、telnet）到后来才出现的应用（Web、流媒体、VoIP、游戏等）的惊人范围。

在过去20年中，出现了多种针对特定场景的TCP变体，其中一些已在实践中部署。但从根本上说，之前学习的TCP版本仍然是主流部署。

### HTTP/3 与 QUIC

传输层不提供的服务（如实时服务支持、安全性）主要在应用层添加——通过应用层协议和分布式应用层基础设施（如CDN、数据中心）。

一个重要的变化是：**HTTP/3** 正在将大量传输层能力构建在应用层，然后运行在UDP之上。

**QUIC（Quick UDP Internet Connections）**：
- 是一个应用层协议，位于HTTP之下，运行在UDP之上
- 已在Google服务器、Chrome浏览器和YouTube移动应用中广泛部署
- 正在IETF标准化过程中

从技术角度看，QUIC采用了与TCP相同的可靠性、拥塞控制和连接管理方法。熟悉TCP的读者会发现QUIC的算法与TCP高度并行。

**QUIC的连接建立**：
- QUIC是面向连接的协议，需要握手建立连接
- 传统HTTP的做法：先建立TCP连接（1个RTT），再在TCP之上建立TLS安全连接（又一个RTT），数据开始流动前需要2个RTT
- QUIC的做法：一次RTT握手同时完成可靠性、拥塞控制和安全状态的建立

**QUIC的多路复用**：
- QUIC引入了单个连接内多路复用多个应用级流（stream）的概念
- 传统HTTP：多个对象需要逐个连续检索
- QUIC：多个流可以同时检索多个Web对象
- 每个流有自己的可靠性和安全性，但共享同一个拥塞控制协议
- 关键优势：某个流出现错误恢复时，其他流不会被阻塞（避免了HTTP/2中的队头阻塞问题）

### 传输层演进的其他方向

1. **TCP变体**：TCP CUBIC、TCP BBR等针对不同网络环境优化拥塞控制
2. **多路径传输**：MPTCP允许单个TCP连接同时使用多条网络路径
3. **HTTP/3的普及**：基于QUIC的HTTP/3正在成为Web的新标准
