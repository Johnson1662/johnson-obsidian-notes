# 一、Agent 基础与设计

## 1.1 Agent 是什么，和 Chain / Workflow 的区别

**常见问法**

- 简述 Agent 的基本架构组成
- Agent 和 LLM Chain 有什么区别
- Agent 和 Workflow 各适合什么场景，怎么选型
- 智能客服该用 ReAct 还是 Workflow

**答题要点**

1. **定义**：Agent = LLM + 规划(Planning) + 记忆(Memory) + 工具使用(Tool Use)。它是带目标的执行者——你给它目标，它自己拆任务、做判断、选工具、执行，并根据结果动态调整。
2. **和 Chain 的区别**：Chain 是预定义的、线性硬编码工作流，路径写死；Agent 靠自主性，通过推理循环(Reasoning Loop)自己决定执行路径。
3. **和 Workflow 的本质区别**：不在"有没有自动化"，而在"谁做判断"。判断都由人提前设计好 → Workflow；系统根据中间结果自己做决策 → Agent。Workflow 稳定、Agent 灵活。
4. **选型判断**：
   - 规则清晰、路径固定、重复性强、审计要求高 → Workflow
   - 目标明确但过程充满不确定性、步骤顺序/次数/条件都不固定 → Agent
   - 生产级方案多是混合：外层 Workflow 控节奏保证可控，内层 Agent 处理高不确定性的局部任务
5. **避坑**：能用普通多轮对话解决的就别硬套 Agent；把简单任务塞给 Agent 是"大炮打蚊子"，徒增成本和不确定性。

**出处**：AI有点东西、秃头续命(米哈游)、黑马程序员AI就业(淘天)、路飞HH、海云日记。

## 1.2 ReAct / Plan-and-Execute / ToT-LATS ★

**常见问法**

- ReAct 的局限性是什么
- CoT 和 Planning 的本质区别
- Plan-Then-Act、ReAct + 轻规划、Tree/Graph Planning 的区别、场景、优缺点
- ToT / LATS 原理，相对线性规划的优势
- 推理断层、结果偏离目标怎么解决

**答题要点**

1. **ReAct**：Thought → Action → Observation 循环，边想边做。优点是灵活、用户中途改需求能跟上；缺点是每步都推理费 token，中间出错不好处理，长任务容易跑偏。经验上 3–8 步任务表现好，超过 8 步成功率明显下降。
2. **Plan-and-Execute**：先一次性把任务拆成步骤清单（可用 DAG 并行调度），再逐步执行、观察反思。优点是省 token、适合长任务；缺点是中间出岔子时重规划成本高。
3. **CoT vs Planning**：CoT 只是把推理过程写出来；Planning 是产出一张可执行的任务表（含每步的输入、输出、依赖、约束）。
4. **ToT / LATS**：让 LLM 做蒙特卡洛树搜索，能探索多条解题路径并回溯评估，比线性规划更容易找到最优解，代价是算力开销大。
5. **混着用是加分答法**：大体先出计划，执行细节遇到异常再切到 ReAct 局部调整。
6. **应对推理断层/跑偏**：提示工程上设检查点和里程碑、让模型每步对齐 to-do list；架构上引入记忆机制保留关键决策；失败时回退到稳定状态重规划。

**出处**：知识分享官01p(MiniMax二面)、林北北、添砖java。

## 1.3 五种常见 Agent 设计模式

**常见问法**：讲讲你用的 Agent 设计模式；有哪些常见的 Agent 范式。

**答题要点**

记住五个名字 + 一句话记忆点：

| 模式 | 核心 | 适用场景 | 一句话 |
|---|---|---|---|
| RAG | 外挂私有知识库，先查再答 | 知识库问答、文档解读 | 先查资料，再回答 |
| 单 Agent | 自己规划、调工具 | 自动化任务、简单工作流 | 自己规划自己干活 |
| Multi-Agent RAG | 多专用 Agent 分库检索再聚合 | 多来源调研 | 专人专库，分头检索 |
| Plan-and-Execute | 先列完整计划再逐步执行 | 长任务、多步骤工程任务 | 先列计划，再落地 |
| ReAct | 思考→行动→观察循环 | 边推理边验证、搜索求证 | 想一步做一步看一步 |

**出处**：添砖java。

## 1.4 多 Agent vs 单 Agent ★

**常见问法**

- Multi-Agent 和 Single-Agent 最大区别、各自优势、会带来哪些额外问题
- 为什么不能用一个 Agent + 多个 Skill 替代 Multi-Agent
- 一个 Query 含多个任务怎么拆，串行还是并行
- 路由是规则做还是大模型判断
- Agent 之间怎么做上下文隔离和通信，能不能互看完整历史
- 简单任务还生成完整 Plan 会不会降效

**答题要点**

1. **优势**：职责清晰、上下文隔离、可并行、便于单独评测和替换。
2. **额外问题**：通信开销、状态共享与冲突仲裁、上下文膨胀、调试困难。
3. **克制用法（面试官认可）**：MainAgent 默认自己处理短任务，只在三类情况 fork 子 Agent——①任务可并行；②上下文需要隔离；③调用链路深。别为了"看起来高级"堆一堆 Planner/Searcher/Reviewer，一问为什么讲不清就是减分项。
4. **拆分与路由**：任务拆分后能并行的并行；路由可以规则 + 模型判断结合，简单高频用规则兜底、复杂用模型语义判断。
5. **通信方式**：Agent 之间传结构化的中间结果（带任务 ID 的 JSON），不要互塞完整对话历史；避免上下文越来越长。
6. **Skill vs Agent**：Skill 是被调用的能力/流程，Agent 是有独立规划和上下文的执行体。什么写进 Prompt、什么封装成 Skill，看复用频率和上下文成本。

**出处**：熊掌与鱼🐟(字节抖音一面)、会敲代码的泡(阿里面试官视角)、Java面小猫🐱、林北北、小鱼向上游、Offer面试官。

## 1.5 MCP / Function Calling / Skill / A2A ★

**常见问法**

- MCP 是什么，和 Function Calling 什么关系
- Agent Skill 和 MCP 的区别
- 工具很多时怎么选、怎么按需加载
- MCP 的传输层差异、Tool 动态发现与注册流程
- A2A 了解吗，Agent Card 怎么设计，和 MCP 的本质区别，被调用方耗时高怎么办

**答题要点**

1. **Function Calling**：模型输出结构化的工具调用，解决的是"模型怎么调工具"。
2. **MCP（Model Context Protocol，模型上下文协议）**：标准化的连接协议，解决的是"工具/数据/上下文怎么被统一接入、发现和复用"。它更像工具连接层——把搜索、数据库、业务系统、函数等外部能力用统一接口接进来。追问点：传输层差异、Tool 的动态发现与注册流程。
3. **A2A（Agent-to-Agent Protocol）**：面向 Agent 之间通信协作的协议。核心是智能体之间如何相互发现（Agent Card 描述能力）、交换信息、沟通任务状态、做任务委派。
4. **两者关系（高频）**：连接对象不同——MCP 面向 AI 与工具/数据，A2A 面向 AI 与 AI。不是谁替代谁，而是互补，可同时出现在同一系统：主 Agent 通过 MCP 调工具，通过 A2A 委派任务给专业 Agent。

   | 维度 | MCP | A2A |
   |---|---|---|
   | 连接对象 | 工具、数据、上下文、外部能力 | 其他智能体 |
   | 解决问题 | Agent 如何调用外部能力 | 多个 Agent 如何协作 |
   | 典型场景 | 访问数据、调用工具、获得上下文 | 智能体发现、沟通、任务委派 |
   | 系统角色 | 工具连接层 | 智能体协作层 |

5. **工具太多怎么办**：别把所有工具描述都塞上下文（占窗口、互相干扰），做分层过滤 / 基于检索的按需预选。
6. **被调用方 Agent 耗时高**：异步委托 + 任务状态轮询，A2A 里靠任务状态协商和超时兜底。

**出处**：以安、会敲代码的泡(阿里面试官视角)、程序员峰哥(月之暗面)、黑马程序员AI就业(淘天)、章鱼笔记(深度求索)、阿里云开发者社区(协议对比)。

## 1.6 Harness 工程 ★

**常见问法**

- Harness engineering 是什么，和上下文工程有什么区别
- 生产级 Harness 至少要看哪几件事

**答题要点**

1. **定义**：Harness 是包在 Agent 外面的工程控制层（直译"马具/线束"）。模型负责判断 next step，Harness 负责让这一步真正可执行、可追踪、可恢复——即约束、记录、验证、恢复。
2. **三件事**：①编排推理循环（ReAct / Plan-and-Execute / Reflection）；②管理工具生命周期（注册、鉴权、参数校验、调用、结果回写）；③上下文工程（窗口管理、压缩、交接、恢复）。
3. **生产级四看**：
   - **状态**：当前做到哪一步，哪些功能 failing / passing
   - **工具**：哪些能用、参数怎么校验、失败怎么重试
   - **上下文管理**：长任务怎么压缩消息、怎么交接、怎么恢复
   - **验收**：什么时候算 done，证据是什么
4. **回答节奏**：先用定义破题，再按"状态/工具/上下文/验收"四点铺开，最后挂自己的项目逐条对应。

**出处**：会敲代码的泡（两篇）、亚慧AI产品经理、黑马程序员AI就业(淘天)、CSDN 生产级 Harness 实践。

# 二、记忆与上下文工程 ★

> 这一节是你的主攻方向，面试会往深里追，每个点都要能展开讲细节。

## 2.1 记忆分层 ★

**常见问法**

- Agent 的长期记忆怎么设计（存储结构、更新策略、检索机制）
- 短期记忆和长期记忆分别怎么存
- Agent 怎么记住三年前说过的话
- 讲讲你的三层记忆架构

**答题要点**

1. **分层设计**：
   - **工作/短期记忆**：当前会话消息 + 状态变量（走到哪步、中间结果），存 Context Window 或 Redis。
   - **情景记忆**：把会话压缩成摘要，或抽取关键事实/用户偏好，Embedding 后存向量库；相关话题时召回塞回上下文。
   - **用户画像**：结构化的长期偏好（比如"不要塑料""预算 300 以内"）。
2. **存储结构选择**：向量库存语义/情景记忆，图库存关系型记忆，结构化画像用 KV 或关系库。
3. **更新策略**：记忆合并（去重、冲突解决）、遗忘机制（时间衰减 + 重要性打分），避免记忆无限膨胀。
4. **检索机制**：混合检索 + 重排序，相关记忆才注入，控制注入量。
5. **一句话答法**：短期靠上下文，长期靠 RAG（经验检索 Experience Retrieval），中间用摘要层级结构递归压缩。

**出处**：知识分享官01p(MiniMax)、林北北、小熊饼干_(三层记忆)、AI有点东西、创想致学-小美老师讲ai。

## 2.2 长上下文超限与压缩 ★

**常见问法**

- 历史远超上下文窗口怎么办
- 滑动窗口 vs 总结压缩 vs 向量检索，优劣对比
- 用户聊到第 20 轮，Agent 把最早的关键信息忘了，你第一步查什么
- 摘要丢了关键信息怎么补，跨块关联怎么保证
- skill 全塞进 prompt，上下文太大怎么办

**答题要点**

1. **三种方案对比**：

   | 方案 | 做法 | 优点 | 缺点 |
   |---|---|---|---|
   | 滑动窗口 | 只保留最近 N 轮 | 简单、token 可控 | 丢早期信息 |
   | 总结压缩 | 分层摘要，保留关键决策点和工具结果 | 保留全局脉络 | 细节可能丢失 |
   | 向量检索 | 历史向量化，按需召回 | 按需取用、不占窗口 | 依赖检索质量 |

2. **实用组合**：分层摘要 + 关键信息优先召回 + 工具结果裁剪。把实体、决策、约束等关键信息单独抽出，做优先召回。
3. **跨块关联**：给摘要块建索引或关联 ID，关键信息在多个块里保留锚点。
4. **排查顺序（面试官想听的思路）**：先查有没有做记忆分层 → 再查长期记忆召回是否命中 → 再看上下文是不是被塞爆。
5. **前沿答法**：长文本模型直接吃超长历史，或用摘要层级结构递归压缩；skill 按需加载而不是全塞 prompt。

**出处**：知识分享官01p(MiniMax)、程序员峰哥(月之暗面)、后端大奇、AI有点东西、啊涛聊AI、Offer面试官。

## 2.3 Prompt 工程 vs 上下文工程 ★

**常见问法**

- Prompt Engineering 和 Context Engineering 的区别
- Harness 和上下文工程是什么关系
- 上下文工程有哪些实践经验
- 做了 to-do list 吗，为什么能让模型更聚焦

**答题要点**

1. **Prompt 工程**：关注"单条指令怎么写清楚"——角色、任务、场景、限制条件、示例五块结构。
2. **上下文工程**：关注"整个上下文窗口放什么、怎么组织、怎么动态管理"——会话历史、工具结果、记忆注入、to-do list 都归它管。
3. **关系**：Prompt 工程是上下文工程的子集；上下文工程比"写好一句 prompt"更系统。
4. **to-do list 的作用**：把任务显式列成清单，让模型每步对齐、减少跑偏，也方便检查进度和失败定位。
5. **常用手法**：知识前置（把参考资料放前面）、分条写而非长句、明确负向约束（信息不足要反问、不许杜撰）。

**出处**：AI大模型学习、亚慧AI产品经理、K1ra / Java面小猫🐱(字节)、啊涛聊AI、大厂面试观察员。

# 三、RAG 与检索 ★

## 3.1 完整流程与为什么需要 RAG

**常见问法**

- 讲讲 RAG 的完整流程
- 为什么需要 RAG
- RAG 能消除幻觉吗
- 什么时候该上 RAG，什么时候该微调

**答题要点**

1. **定义**：RAG（检索增强生成）= 让模型开卷考试。从自有知识库检索相关信息，注入 Prompt，让模型基于资料回答。核心是"检索 + 生成"。
2. **三个动机**：幻觉、时效性、私有数据安全。微调能解决一部分但成本高、知识更新慢；RAG 不改模型只改输入，轻量可控。
3. **完整链路（离线 / 在线分开讲）**：
   - 离线：文档加载 → 文本切片 → 向量化(Embedding) → 建索引 → 存入向量库（FAISS / Chroma / Milvus / ES）
   - 在线：用户提问 → 问题向量化 → Top-K 召回 → 拼进 Prompt 模板 → LLM 生成
4. **RAG 不能消除幻觉**：检索不准时会基于无关信息编；模型也可能忽略检索结果、用自己的记忆答。所以只能缓解。
5. **RAG vs 微调**：缺知识、知识常变 → RAG；要改行为/风格/格式遵循 → 微调。能靠 Prompt/RAG 解决的就别上微调。

**出处**：予枫 Agent、Alio、以安、黑马程序员AI就业、知乎《一文读懂 RAG》。

## 3.2 切片、Query 改写、混合检索、重排 ★

**常见问法**

- chunk size / overlap 怎么定
- Query Rewrite 把用户原始意图改错了怎么办
- 为什么用 BM25 + Dense，只用 Dense 不行吗
- 什么是混合检索
- 三层检索策略是怎么回事
- rerank 怎么接、多维查询改写是什么、RAG 什么时候触发检索

**答题要点**

1. **切片**：常见有句分割、固定长度分割、递归分割。经验值 chunk_size 500 / overlap 50，配较大 Top-K 平衡召回率和准确率。切太大语义噪声多，切太小信息不完整。边界：别超 Embedding 模型的 token 限制。
2. **Query 改写**：多维度改写（同义扩展、拆解子问题、HyDE）。防改错意图的兜底——原始 Query 一起参与检索、置信度低时不改、改写结果可解释。
3. **混合检索**：向量检索擅长语义相似，BM25/全文检索擅长关键词、专有名词、数字。工业级必须两者融合，否则专有名词、编号这类会搜不到。相似性计算常用余弦、欧氏距离；全文检索靠倒排索引。
4. **三层检索**：召回层（混合检索，求全）→ 融合层（结果合并）→ 精排层（rerank，求准），可加动态召回数量。目标是在上下文预算内兼顾"准"和"全"。
5. **Agent 里的接法**：先判断要不要检索 → query 改写 → 混合检索 → rerank → 注入上下文。
6. **高级方法（加分）**：RAG Fusion（多查询生成）、Self-RAG（自反思）、Corrective RAG（纠错检索）、上文扩展（small-to-big）。

**出处**：予枫 Agent、知识分享官01p(MiniMax)、熊掌与鱼🐟(字节)、AI产品果果姐、K1ra(字节)、程序员峰哥、知乎《一文读懂 RAG 含高级方法》。

## 3.3 检索评测与 Agentic RAG ★

**常见问法**

- 召回效果怎么评估，没有用户反馈怎么抽检
- Agentic RAG 的核心环节
- 大模型认知和检索结果冲突怎么解决
- badcase 怎么定位到检索环节

**答题要点**

1. **评测指标**：检索侧看命中率、召回率、MRR、NDCG；生成侧看忠实度（是否基于检索内容）、答案相关性、幻觉率。
2. **无用户反馈时**：建固定评测集 + LLM-as-Judge 自动打分，人工抽检校准。
3. **Agentic RAG 关键**：Query Rewriting（查询改写）+ Adaptive Retrieval（自适应决定检不检索、检索几次、何时停）。
4. **认知与检索冲突**：以检索证据为准，要求模型给引用；Prompt 里明确"检索结果优先于内部知识"；仍冲突时触发二次检索或交由人工。
5. **badcase 定位**：先看检索有没有召回正确文档 → 再看 rerank 有没有排到前面 → 再看是不是模型忽略证据。分层归因。

**出处**：Java面小猫🐱(字节)、会敲代码的泡(阿里面试官视角)、黑马程序员AI就业(淘天)、小熊饼干_。

## 3.4 Text-to-SQL（工程难点样板）

**常见问法**：Text-to-SQL 难在哪；从 Demo 到生产的挑战。

**答题要点**（四类挑战）

1. **选对表列比生成 SQL 更重要**：面对上百张表，全量塞上下文不可取，简单取 Top-K 又会丢掉连接键和桥接表。用向量检索、两级召回、双向检索、图路径搜索，在预算内保留完整查询依赖。
2. **SQL 能跑通 ≠ 业务口径正确**：销售额是否扣退款、客户数是否去重、"上个月"是自然月还是滚动 30 天——这些不报错。靠业务语义层 + RAG 补充指标定义，靠执行反馈和结果校验发现偏差。警惕多个候选结果一致但犯了同一个错。
3. **复杂查询要规划不是无限重试**：多表 JOIN、嵌套聚合、窗口排名，先问题分解、显式查询规划、多候选生成与局部修订；修复时保留已确认条件，没新证据就停，别反复碰运气。
4. **性能别只盯 token**：并行生成缩短等待但增加调用和扫描；LIMIT 限制返回行数但未必减少全表扫描。用大小模型路由、模板缓存、EXPLAIN 检查、请求级超时和资源预算综合权衡。

**出处**：Ryan聊大模型。

# 四、模型与推理

## 4.1 Transformer 与 Attention

**常见问法**

- Self-Attention 实现原理，为什么分 Q/K/V，同一 token 在不同位置向量是否一样
- Transformer 的两个 mask 机制
- 手撕 self-attention / multi-head attention / Transformer Encoder

**答题要点**

1. **QKV**：Q 是查询、K 是索引/键、V 是内容/值。分开是为了做相似度匹配（Q·K 算权重）并保留三个可学习的线性投影，增强表达能力。
2. **计算**：Attention(Q,K,V) = softmax(QKᵀ/√dₖ)·V，除以 √dₖ 防止点积过大导致 softmax 梯度消失。
3. **同一 token 不同位置**：不一样。输入会加位置编码，经过自注意力后还融合了上下文，所以位置不同、上下文不同，向量都不同。
4. **两个 mask**：padding mask（屏蔽填充位，避免 attention 到无效 token）+ causal mask（屏蔽未来 token，保证自回归生成只看过去）。
5. **多头**：把 QKV 投影到多个子空间并行算 attention，拼接后再投影，捕捉不同维度的关系。

**出处**：K1ra / Java面小猫🐱(字节)、LLMCat、小森学AI、抱紧刺猬🦔。

## 4.2 推理优化 ★

**常见问法**

- KV Cache 原理，为什么省算力
- Prefix Caching 为什么只优化 Attention
- continuous batching、vLLM 是什么，线上高峰吞吐多少
- RoPE、Flash Attention、手撕 MHA

**答题要点**

1. **KV Cache**：自回归生成时，已生成 token 的 K/V 每步都会重算。把它们缓存起来，后续只算新 token 的 Q 与缓存 K/V 做 attention，省大量重复计算。代价是显存随序列长度线性增长。
2. **Prefix Caching**：多个请求共享相同前缀（system prompt、长文档）时，复用这段的 KV，命中就直接跳过其计算。它只作用于 Attention 的 KV 部分，因为 FFN 是逐 token 独立计算的、没有跨 token 复用空间。
3. **vLLM / PagedAttention**：用分页方式管理 KV Cache，像操作系统管理内存一样按需分配块，减少显存碎片、提高利用率。
4. **Continuous batching**：不像静态 batching 等整批生成完，而是每个 token 步动态地把新请求拼进 batch、把完成的移出，显著提高吞吐。
5. **RoPE**：旋转位置编码，用旋转矩阵把位置信息编码进 Q/K，使 attention 分数只依赖相对位置，外推性好、可处理长序列。
6. **Flash Attention**：通过分块计算和 IO 感知，避免显式物化完整 attention 矩阵，省显存又快。

**出处**：秃头续命(米哈游)、K1ra / Java面小猫🐱(字节)、抱紧刺猬🦔、章鱼笔记(深度求索)。

## 4.3 微调与对齐

**常见问法**

- SFT / LoRA / QLoRA / RLHF / DPO 区别
- 什么时候用 RAG，什么时候微调
- 模型幻觉怎么优化

**答题要点**

1. **SFT**：监督微调，用指令-回答数据教会模型遵循指令和特定格式。
2. **LoRA / QLoRA**：冻结基座权重，只训练低秩适配器，成本低；QLoRA 再把基座量化到 4bit，显存更省。
3. **RLHF / DPO**：对齐人类偏好。RLHF 要训奖励模型 + PPO，流程复杂；DPO 直接用偏好数据优化，更简单稳定。
4. **选型阶梯**：Prompt → RAG → LoRA/QLoRA → 全参微调，成本和改动递增。缺知识用 RAG，改行为/风格/格式用微调，能靠前两级解决就别上微调。
5. **幻觉优化**：RAG 注入证据 + Prompt 约束"不知道就说不知道" + 事实校验 + 生成后核验。

**出处**：知识分享官01p、黑马程序员AI就业、章鱼笔记(深度求索)。

# 五、工程与系统设计

## 5.1 Agent Loop 与可靠性 ★

**常见问法**

- agent loop 怎么设计，终止条件除了 max_turns 还控哪些
- 模型返回 tool_call 后做什么
- Agent 死循环 / 重复调同一工具怎么检测处理
- 工具失败、超时怎么兜底，结果过大怎么办
- 模型说"任务完成了"就直接信吗

**答题要点**

1. **终止条件**：max_turns + token 预算 + 耗时 + 成本 + 重复动作检测 + 置信度阈值。多个条件是"与"关系，任一触发即停，UI 要给出终止原因。
2. **tool_call 处理链路**：参数校验（JSON Schema / Pydantic，类型校验 + 业务逻辑校验两层）→ 权限校验（用户范围 + 工具操作范围）→ 沙箱执行 → 结构化结果回灌。
3. **死循环检测**：状态指纹（prompt 摘要 + 已调用工具序列做 hash 或 embedding 相似度，滑动窗口只比最近 N 轮）+ 同轮去重 + 回退到稳定状态 + 切策略或人工介入。
4. **失败处理**：指数退避重试、熔断、幂等、结果校验、降级人工兜底；关键工具备备用 API。
5. **结果过大**：截断或摘要后再回灌，避免撑爆上下文。
6. **结果校验**：模型说完成不能直接信，做断言和结果校验再确认。

**出处**：程序员峰哥(月之暗面)、熊掌与鱼🐟(字节)、后端大奇、林北北、黑马程序员AI就业(淘天)。

## 5.2 状态、并发、checkpoint、可观测 ★

**常见问法**

- 多 Agent 并发改同一文件/资源怎么防冲突，锁粒度怎么定
- Agent 执行到一半服务重启，checkpoint 存什么、放哪、怎么恢复
- 线上怎么评测埋点，badcase 怎么归因和回流
- 流式输出下工具事件怎么推前端，断线重连怎么恢复
- SSE 和 WebSocket 区别，流式回复用哪个

**答题要点**

1. **并发冲突**：加文件或资源锁，锁粒度按资源划分（别一把大锁锁全局，也别细到开销过大）；用版本号做乐观锁，冲突时重试或仲裁。
2. **checkpoint**：存任务状态、已调用工具及结果、上下文摘要、当前进度；放持久化存储（DB / Redis），服务重启后据此恢复现场，而不是从头跑。
3. **线上埋点**：任务成功率、工具选错率、参数错误率、成本、耗时；每个环节打日志，支持日志重放。
4. **badcase 归因**：分四类——模型 / Prompt / 检索 / 工具，定位到具体 Agent 环节，回流成回归集，判断要不要对某个 Agent 做 SFT。
5. **流式推送**：用 SSE 推工具调用事件到前端（文本流 SSE 足够，双向交互才用 WebSocket）；断线重连靠事件 ID 或 checkpoint 恢复。
6. **human-in-the-loop**：用户驳回或超时后，任务挂起、转人工或按兜底策略续跑。

**出处**：程序员峰哥(月之暗面)、小熊饼干_、冒个泡泡.(追觅)、后端大奇、Java面小猫🐱。

## 5.3 Agent 系统设计题 ★

**常见问法**：基于某业务场景设计一个 Agent 系统（快手问过"AI 自动定位线上报警原因"，字节问过"带 TUI 的交互式视频剪辑工具 MVP"，OpenAI 有 LLM sysdesign）。

**答题要点**

备一套通用模板往里套，从输入到输出一步步设计，每步说清选型理由：

1. **需求澄清**：先问清边界、用户、成功标准（面试官常先看你会不会澄清需求）
2. **输入层**：多模态内容怎么解析和组织
3. **意图识别与路由**：规则 + 小模型 + 大模型结合，可并行化意图识别
4. **规划层**：ReAct / Plan-and-Execute 选型并说为什么
5. **工具与检索**：定义工具、RAG 检索、按需加载
6. **记忆注入**：短期/长期记忆怎么接
7. **执行与编排**：单 Agent 还是多 Agent，串行并行
8. **结果校验与兜底**：失败重试、异常收敛
9. **监控评测闭环**：埋点、评测、badcase 回流
10. **补充边界**：成本、延迟、安全、并发

**出处**：小芽青青、北美面试王牌辅导、Java面小猫🐱。

## 5.4 安全

**常见问法**：Prompt 注入怎么防、危险工具怎么拦、敏感数据怎么脱敏、沙箱怎么设计。

**答题要点**

1. **Prompt 注入**：输入隔离和清洗、指令与数据分离、关键操作二次确认、输出审核校验。
2. **危险工具拦截**：工具分级 + 权限校验，高危操作要人工确认（human-in-the-loop）。
3. **敏感数据脱敏**：入模前脱敏、日志脱敏、最小权限。
4. **沙箱**：网络白名单、文件系统隔离、CPU/内存配额，内核级隔离 + 资源审计，不是写个 Dockerfile 就够。

**出处**：程序员峰哥(月之暗面)、黑马程序员AI就业(淘天)、秃头续命(米哈游)。

## 5.5 手撕题

**答题要点**（分三类准备）

1. **模型手撕**：self-attention、multi-head attention、RoPE、safe softmax、LayerNorm / RMSNorm、KL 散度、简单 KV-Cache、Transformer Encoder（给随机 tensor 跑通 forward）。
2. **算法**：hot100 反复刷——三数之和、第 K 大、接雨水、LIS、编辑距离、买卖股票、合并 K 链表、岛屿面积；还有带 parent_id 的扁平 JSON 恢复成树、TTL LRU Cache（get/put O(1)）、求 sqrt。
3. **AI Coding**：限时给小项目任务，考问题拆解、写 prompt、审查 AI 写的代码并迭代。

# 六、项目深挖与表达 ★

**常见问法**

- 介绍一个你最熟的 Agent 项目
- 用户输入 Query 后完整执行链路是什么
- 为什么这么选型，能力边界在哪
- "这不就是个玩具吗"怎么应对
- Badcase 怎么定位到具体环节，该对哪个 Agent 做 SFT

**答题要点**

1. **讲项目五段式**：背景 & 目标 → 技术方案 → 我负责什么 → 关键问题 & 怎么解 → 结果 & 指标。原则：说"我"不说"我们"，有坑有解有数据，别堆名词。
2. **完整链路要能顺着讲**：用户输入 → 意图识别 → 多 Agent 路由 → RAG 检索 → 记忆注入 → LLM 生成 → 监控评测闭环，每一环的输入输出都要说清。
3. **讲清 Demo 和生产级的差别**：
   - 架构取舍：为什么用 AgentLoop、为什么拆子 Agent、为什么有的工具主 Agent 直接调有的要派发
   - 工程治理：限流 / 重试 / 超时 / 熔断 / 缓存 / 队列 / 可观测，并说清 Trade-off
   - 评测闭环：今天改好一个 case，别明天坏三个
4. **应对"太 toy"**：亮出真实业务链路 + 工程细节 + 评测集（长期记忆召回、多轮后事实不丢、工具异常不编造）。核心一句：面对大模型的不确定性，用工程化手段给用户确定的交付结果。
5. **每个选型都要有理由**：比如"选 Chroma 因为轻量、适合快速验证"，别只说"我们用了 X"。
6. **数据说话**：准确率从多少到多少、幻觉率降多少、响应时间多少，避免"提升明显""效果不错"。

**出处**：黑马程序员AI就业(项目模板)、会敲代码的泡(两篇)、小熊饼干_(EchoMind)、周也_大模型炒饭、会敲代码的鱼。
