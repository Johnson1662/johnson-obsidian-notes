## 11.2 并行策略详解

训练大语言模型必须把计算分布到许多 GPU 上。可以沿多个本质不同的维度并行，每种都有各自的取舍。本节用数学公式、示意图和实践指引详细介绍每种策略。

*Figure 11.2: 四种并行策略概览。生产系统通常会同时组合其中 2–3 种。*

## 11.2.1 数据并行（Data Parallelism, DP）与分布式数据并行（Distributed DataParallelism, DDP）

数据并行是最简单、也最常见的分布式训练形式 [209]。每块 GPU 持有模型的完整副本，处理不同的 mini-batch，并同步梯度。

原始 DP（PyTorch DataParallel）。 单进程方案：一块 “主” GPU 负责分发输入、汇集输出、广播梯度。受 GIL 以及到主 GPU 的 PCIe 带宽限制。

分布式数据并行（DDP，DistributedDataParallel）。 多进程方案：每块 GPU 各自运行一个进程。在反向计算继续进行的同时，通过 ring-AllReduce [321] 在后台同步梯度。

![](../images/91e5294615943c30b576af6bda475e41b441a8d6b49e956d577b3a044cb9ab57.jpg)

*Figure 11.3: DDP：每块 GPU 持有完整的模型副本并处理不同的 batch。梯度通过 ring AllReduce 取平均，与反向计算重叠。*

## DDP 的关键特性：

- 显存：每块 GPU 都要存完整的模型 + 优化器 + 梯度。70B BF16 模型约 ∼560 GB/GPU——如不做显存优化根本无法承受。

- 通信：每步对梯度张量做一次 AllReduce。大小 = 模型参数量 × 2 字节（BF16）。RingAllReduce 开销：每 GPU 传输 2 · <sup>N−1</sup> · M 字节。

- 扩展性：在 ∼64 块 GPU 以内接近线性。超过之后通信开始占主导。

- 梯度分桶：DDP 把参数按桶分组（默认 25 MB），只要某个桶的梯度就绪就启动 AllReduce——让通信与反向计算重叠。

```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_groupitaend="nccl" # NCCL 用于 GPU 间通信
model = model.to(local_rank)
model = DDP(model, device_ids=[local_rank],
    gradient_as_bucket_view=True, # 显存优化
    static_graph=True) # 开启通信优化
```

## DP vs DDP ——总是用 DDP

PyTorch 旧版的 DataParallel（DP）绝不应用于 LLM 训练：

- 单进程，受 Python GIL 限制

- 所有梯度都汇集到 GPU 0（瓶颈）

- 即便在单节点上也比 DDP 慢 $2 { - } 3 \times$

- 无法跨机扩展

DDP 是底线并行策略。对于 >7B 的 LLM，应优先使用 $\mathrm { F S D P / Z e R O _ { \circ } }$

## 11.2.2 张量并行（Tensor Parallelism, TP）

张量并行（Megatron-LM 风格 [327]）把单个权重矩阵切到多块 GPU 上。每块 GPU 计算部分结果，再通过 AllReduce 合并。

列并行（Column-Parallel）线性层。 权重矩阵 $W \in \mathbb { R } ^ { d \times h }$ 按列切到 T 块 GPU 上：

$$
W = [ W _ {0} \mid W _ {1} \mid \dots \mid W _ {T - 1} ], \quad W _ {i} \in \mathbb {R} ^ {d \times h / T}\tag{11.1}
$$

每块 GPU i 独立计算 $Y _ { i } = X W _ { i }$ （无需通信）。输出沿 hidden 维度被切开。

行并行（Row-Parallel）线性层。 权重矩阵按行切： $W = [ W _ { 0 } ; W _ { 1 } ; \ldots ; W _ { T - 1 } ] ,$ ，其中 $W _ { i } \in \mathbb { R } ^ { d / T \times h } \mathrm { \Lambda } _ { \mathrm { c } }$ C输入 X 也必须切开。每块 GPU 计算一个部分和，再通过 AllReduce 得到最终输出。

![](../images/4766a496b34f5e3f2374fe8629b6ad95b711f17b5b5ed4a76ec82486f2f0fd95.jpg)  
*Figure 11.4: 列并行线性层（TP=2）。权重按列切开；每块 GPU 独立计算 $X W _ { i \circ }$ MLP 将其与行并行层配对，从而避免多余的 AllReduce。*

TP 下的 Transformer Block。 在 Transformer 层中，Megatron-LM 按以下方式应用 TP：

1. MLP：第一层线性 $\left( h \to 4 h \right)$ 列并行，第二层线性（4h → h）行并行。行并行层之后做一次AllReduce。

2. Attention：Q、K、V 投影做列并行（按 head 切到多块 GPU）。输出投影做行并行。输出投影之后做一次 AllReduce。

3. 合计：每个 Transformer 层 2 次 AllReduce（attention 一次，MLP 一次）。

![](../images/80b81b04fce377cb3c7efad2731b564600661e8ad17330f3ee806d985feab16d.jpg)  
*Figure 11.5: 单个 Transformer block 中的张量并行通信模式。每层需要两次 AllReduce 操作（红色标注）——attention 之后一次，MLP 之后一次。*

Communication cost per layer: 2 AllReduce $\times ~ 2 \cdot ~ \frac { T - 1 } { T } ~ \cdot ~ b \cdot s \cdot d$ bytes For 70B (d=8192), b=4, s=2048, TP=8: $\textstyle = 2 \times 2 \times { \frac { 7 } { 8 } } \times 4 \times 2 0 4 8 \times 8 1 9 2 \times 2$ ≈ 448 MB per layer At 600 GB/s NVLink: 0.75 ms/layer 80 layers → 60 ms total TP overhead

## 为什么 TP 必须限制在节点内

每个 Transformer 层需要 2 次 AllReduce 操作（上文标注为 f 和 g）。对于 80 层的 70B 模型，每次前向就是 160 次 AllReduce（算上反向共 320 次）。在 NVLink 速率（600 GB/s）下，每次AllReduce 耗时 <0.5 ms。但在 InfiniBand（50 GB/s）上，同一操作要 ∼4 ms，总开销 160 × 4= 640 ms——比计算本身还长。

规则：TP 度 ≤ 节点内 GPU 数（通常 $\mathrm { T P } \le 8 )$ ）。跨节点扩展请用 DP/FSDP。

## TP 度的选取

- TP=1：不做张量并行。模型可放进单块 GPU（BF16 下通常 ≤ 13B）。

- TP=2：最小切分。适合在 2 块 GPU 上做 13–34B 推理。开销低（<5%）。

- TP=4：34–70B 推理的标准配置。开销 8–12%。

- TP=8：占满整节点。70B+ 训练的必备配置。开销 12–18%。

!!! note
    - TP>8: 跨节点 TP。极少使用——仅在 PP 不足以承载的 200B+ 模型上才会用。开销 30–50%。
    重要：attention head 数必须能被 TP 度整除。例如 LLaMA-70B（64 个 head），合法的 TP 取值为 1、2、4、8、16、32、64。

## 11.2.3 序列并行（Sequence Parallelism, SP）

序列并行（Sequence Parallelism, SP） [191] 解决的是张量并行单独无法消除的一个显存瓶颈：LayerNorm 和 Dropout 层中的激活值显存。

问题。 TP 把权重显存切到了多块 GPU 上。但 LayerNorm 和 Dropout 作用在完整的 hidden 维上，并在每块 GPU 上都重复存在。它们的激活值（反向传播需要）占用与 b×s×d 成正比的显存——每块 GPU 上一样多，TP 并不会把它降下来。

解法。 对那些不需要跨 GPU 通信的操作（LayerNorm、Dropout、残差连接），按序列维度切分。每块 GPU 对这些操作只处理 s/T 长的序列切片，仅在真正需要的地方（attention、线性层）再gather 出完整序列。

![](../images/3fb1e098cdb366f8e48d1630e990431a2b72f41e973ebd69cab763d2086383db.jpg)

*Figure 11.6: 序列并行通过沿序列维度切分，降低 LayerNorm/Dropout 的激活显存。通信（AllGather/ReduceScatter）取代了标准 TP 中的 AllReduce——总传输字节数不变，但显存得以节省。  *

!!! note
    SP 通信是“免费”的
    标准 TP 在每个子层后做 AllReduce，等价于 ReduceScatter + AllGather。SP 只是重排了这些原语：
    - 不带 SP 的 TP: AllReduce (= ReduceScatter + AllGather) → 所有 GPU 上数据相同 → 在完整张量上算 LayerNorm（浪费）。
    - 带 SP 的 TP: ReduceScatter → 每块 GPU 拿到 1/T 的序列 → 在部分张量上算 LayerNorm → 进入下一个 TP 层前再 AllGather。
    总通信量完全相同！SP 是零额外通信开销的纯显存优化，使用 TP 时应当始终开启。

## SP 的显存节省（70B 模型，TP=8，batch=4，seq=2048）：

$$
\text {激活值节省} = (T - 1) \times b \times s \times d \times n _ {\text {layers}} \times 2 \text {bytes} = 7 \times 4 \times 2 0 4 8 \times 8 1 9 2 \times 8 0 \times 2 \approx 5 9 \mathrm{GB/GPU} (1 1. 2)
$$

## 11.2.4 流水线并行（Pipeline Parallelism, PP）

流水线并行把模型按层纵向切分，把连续的层组指派给不同的设备（stage）。激活值在 stage 间向前流动，梯度向后流动。

气泡（Bubble）问题。 朴素流水线执行会产生 “气泡”——某个 stage 等待前一 stage 的输入或后一 stage 的梯度时的空闲时间：

气泡占比公式。 对于 P 个流水线 stage、每步 M 个 micro-batch：

$$

要让气泡开销 <10%，需要 $M \geq 1 0 \cdot ( P - 1 )$ 。 $\mathrm { P P = } 4$ 时：至少需要 30 个 micro-batch。

PP 中的通信。 与 TP（AllReduce）不同，PP 只需要在相邻 stage 之间做激活值的点对点（point-to-point）通信：

$$
\mathrm{每次传输的数据} = b _ {\mathrm{micro}} \times s \times d \times 2 \mathrm{bytes(BF16)}\tag{11.4}
$$

若 micro-batch=4、seq=2048、d=8192：每次传输 $4 \times 2 0 4 8 \times 8 1 9 2 \times 2 = 1 2 8 \mathrm { M B }$ 。InfiniBand 50 GB/s 时：每次 2.6 ms——相对每个 stage 的计算量来说很小。

负载均衡。 并非所有层的计算量都相等：

- Embedding 层：非常便宜（查表）。

- Transformer block：计算量均匀。

- 最末的 LM head：中等（词表投影是一次大型矩阵乘法）。

把更多 Transformer 层分配给中间 stage，第一/最后 stage 少放一些，以平衡计算。

## 11.2.5 完全分片数据并行（Fully Sharded Data Parallelism, FSDP / ZeRO-3）

FSDP [431]（PyTorch）和 ZeRO-3 [304]（DeepSpeed）解决了 DDP 固有的显存重复问题：不再让每块 GPU 都保存完整的参数、梯度和优化器状态，而是每块 GPU 只拥有 1/N 的切片，需要时即时重建完整张量。

![](../images/eb19b7554e799a95633cf3bf581ef9ea019d1f487806ddd00532cdbe0c3a8705.jpg)  
FSDP Forward Pass for Layer l:  
① AllGather θe from all GPUs (reconstruct full params) ② Compute forward on local microbatch ③ Discard non-owned shards (free memory immediately)

*Figure 11.8: FSDP 把所有模型状态切片到多块 GPU 上。每块 GPU 拥有 1/N 的参数、优化器状态和梯度。在每层计算前，通过 AllGather 按需重建完整参数。*

FSDP 每层的执行流程：

1. 前向：AllGather 参数 → 计算 → 丢弃非自有的分片。

2. 反向：再次 AllGather 参数 → 计算梯度 → ReduceScatter 梯度（每块 GPU 拿到自己的梯度分片）→ 丢弃非自有的参数分片。

3. 优化器更新：每块 GPU 仅用自己持有的梯度分片和优化器状态更新自己拥有的分片。

## FSDP 的通信量

!!! note
    FSDP 每步的通信量是 DDP 的 3×:
    - DDP: 1 次梯度 AllReduce = 环上合计 2M 字节 (其中 M = 模型字节数)。
    - FSDP: 2 次 AllGather (前向 + 反向) + 1 次 ReduceScatter = 3M 字节。
    这就是显存与通信的取舍。FSDP 值得使用的场景是: (a) 模型在 DDP 下无法装进 GPU 显存; 或 (b) 通信与计算重叠得很好 (现代框架可达到 70–90% 重叠)。

## 11.2.6 3D 并行：组合多种策略

大规模生产系统（70B+）会同时组合 TP、PP 和 DP/FSDP：

![](../images/d615b66e1f2efae8be9e9c8c2725e9204875cb80186913ef34693bfacd90e86d.jpg)

*Figure 11.9: 16 块 GPU 上的 3D 并行布局：TP=4（每个方框内，走 NVLink）、PP=2（橙色箭头，stage之间）、DP=2（红色箭头，梯度同步）。每个维度利用通信层级中不同的一层。*

!!! note
    生产配方：64 块 A100-80GB（8 节点）上的 70B

    节点内（NVLink 600GB/s）：生成阶段用 TP=8；训练阶段在节点内使用 FSDP。

    节点间（InfiniBand 400Gb/s）：跨节点 FSDP（8 路数据并行）。

    结果：每块 GPU 持有 ~70GB。Policy 权重在前向/反向时按层 gather。

    流水线并行：仅当模型超过 100B+ 且 TP+ZeRO 装不下时才用。会引入复杂度（气泡开销 10-20%）和调度困难。

    决策流程：

    1. 模型能装进 1 块 GPU 吗？→ 用 DDP。
    2. 用 FSDP 能装进 1 个节点吗？→ 用 FSDP（ZeRO-3）。
    3. 用 TP+FSDP 能装进 1 个节点吗？→ 节点内用 TP + 节点间用 FSDP。
    4. 仍然装不下？→ 跨节点再加 PP。这是最后的手段。

## 11.2.7 解耦 DiLoCo：跨数据中心训练

常规分布式训练假设高带宽互联——单个数据中心内的 100+ Gbps InfiniBand。这一要求使得用标准互联网链路跨地理分布式数据中心训练成为不可能。解耦 DiLoCo（Decoupled DiLoCo）[114]（Google DeepMind，2026 年 4 月）打破了这一假设，让大规模训练可以在普通带宽下跨区域进行。

## DiLoCo：核心思想

DiLoCo（带压缩的分布式本地 SGD，Distributed Local SGD with Compression）用周期性的外部更新取代连续梯度同步：

1. 每个 Worker i 在本地数据分片上独立训练 H 个内部步骤。

2. H 步之后，Worker 们通过计算一个外部更新（outer update）来同步：

$$
\Delta_ {\mathrm{outer}} = \frac {1}{N} \sum_ {i = 1} ^ {N} \left(\theta_ {i} ^ {(H)} - \theta_ {i} ^ {(0)}\right)
$$

其中 N 是 Worker 数量， $\theta _ { i } ^ { ( 0 ) }$ 是共享的起始检查点。

3. 外部更新通过一个全局优化器（如 Nesterov 动量）应用，所有 Worker 重置到新的共享 $\theta _ { \circ }$ 只有外部更新（每 H 步一个模型大小的张量）会穿越网络——而不是逐步骤的梯度。

解耦 DiLoCo 进一步解耦了外部同步：Worker 无需同时同步。相反，更新跨区域异步进行，由一个协调者在更新到达时应用。这能够容忍广域网的可变延迟。

## 解耦 DiLoCo：实证结果

一个 12B 参数模型在由标准互联网链路（2–5 Gbps）连接的 4 个美国地理区域上完成训练：

- 带宽降低：比同步分布式训练少用 236× 的带宽。

- 速度：比完全异步 SGD（受陈旧梯度困扰）快 20× 的墙钟时间。

- 模型质量：在标准语言建模基准上与单数据中心训练持平。

- 容错性：Worker 故障只会延迟外部更新，而不会拖垮整个训练。

## 为什么这很重要：主权 AI 与多云

## 解耦 DiLoCo 的意义远超效率本身：

- 主权 AI（Sovereign AI）：国家或组织可以从自己的数据中心贡献算力，而无需让敏感数据经过中央设施。

- 多云训练：同时利用 AWS、GCP 与 Azure 上的竞价实例，绕开故障。

- 数据中心韧性：一个数据中心宕机只会丢失该 Worker 在当前 步窗口内的贡献，而非整个训练。

- 异构硬件：不同 GPU 世代的 Worker 都可以参与，各自按自己的节奏运行。

关键洞见是：现代优化器对低频、带噪声的外部更新具有鲁棒性——内部训练步骤提供了足够的局部信号，外部同步只需要纠正分布漂移即可。

## 11.3 生成瓶颈：定量分析

Roofline 分析：为什么生成是显存带宽瓶颈

A100 参数：312 TFLOPS（BF16 tensor core），2 TB/s HBM 带宽。
Roofline 拐点：312T/2T = 156 FLOP/byte。低于 156 FLOP/byte 的操作受显存带宽约束。
自回归生成：每生成一个 token，需要读完所有权重（70B 模型为 140GB），并执行  $2 \times 70B = 140G$  FLOPs（batch=1 时）。
算术强度：140G FLOP/140GB = 1 FLOP/byte。比 roofline 低了  $156 \times!$ 
利用率：1/156 = 0.6% 的峰值 FLOPS。GPU 有 99.4% 的时间在等显存读。
Token 速率：2TB/s/140GB = 14.3 tokens/秒（单流，batch=1）。
生成 512 token：512/14.3 = 35.8 秒每条响应（batch=1，TP=1）。
Batch 化能改善: Batch=64、TP=4 → 只读一次权重, 并行生成 64 个 token。算术强度:  $64 \times 1 = 64$  FLOP/byte。好一些，但仍在 roofline 之下！

6. Prefix caching（共享前缀 prompt 下 1.5×）：不重新计算 system prompt 的 KV cache

诸如 DeepSpeed-Chat [410] 与 OpenRLHF [148] 这样的生产级 RLHF 系统采用解耦式架构，将生成、打分、训练拆成三个可独立扩展的集群。

![](../images/3dee4a5a3fc63312bbf9af1e8cd594e25ef6b17acafee0e2c8b27384aad480cb.jpg)

*Figure 11.10: 解耦式 RLHF 架构。每个集群针对自己的负载做优化。打分后的 rollout 先在经验缓冲（experience bufer）中累积，再被训练消费。*

!!! note
    为什么要解耦?

    生成受显存带宽约束（需要高速 HBM，浪费算力）。

    训练受算力约束（需要 tensor core，反向时浪费带宽）。

    同一硬件无法同时优化两者：若把所有事情放在一起，要么生成时浪费算力，要么训练时浪费带宽。解耦让每个集群用最优的硬件/配置。

    实际好处：

    • 生成和训练可以独立扩展
    • 生成集群无状态 → 容错极简
    • gen(step N + 1) 与 train(step N) 可重叠 → 30-40% 加速
    • 不同精度：生成用 INT8（带宽优先），训练用 BF16（精度优先）

## 其他技术：

- 梯度检查点（Gradient checkpointing） [49]：不存全部激活，反向时重算。节省约 60% 激活显存，代价是约 33% 的额外计算。可选择性：只对 attention 层（显存重）做 checkpoint，保留 FFN 激活（重算成本高）。

- 混合精度（Mixed precision） [255]：前向用 BF16（2 字节/参数），优化器状态用 FP32（m、v 各 4 字节）。master 权重用 FP32 累积。

- CPU ofloading（ZeRO-Infinity [305]）：把优化器状态放到 CPU RAM。显存省一半，但慢2–3×（PCIe 64GB/s 瓶颈）。

- 激活 ofloading：前向时把激活搬到 CPU，反向时再搬回来。仅在显存确实紧张时使用。

- FlashAttention [64, 65]：attention 显存从 O(n<sup>2</sup>) 降到 O(n)。快 2–4×，长序列时显存节省巨大。

## 11.6.1 FlashAttention 对 RLHF 的影响

!!! note
    为什么 FlashAttention 对 RLHF 很重要
    RLHF 涉及生成长序列（rollout）并对其训练。没有 FlashAttention 时：
    • 一条 4K token、32 个 head 的序列，仅 attention 矩阵就要 ~4 GB
    • 这严重限制了 PPO/GRPO 训练时的 batch 大小
    • 对 attention 激活做梯度检查点代价昂贵
    有了 FlashAttention:
    • attention 显存为 O(n)——由 Q, K, V, O 张量主导
    • 同等 GPU 显存下可承载更长的 rollout（8K-32K token）
    • 反向从 Q, K, V 重算 attention 分块（不存 n² 矩阵）
    • 这是长上下文 RLHF（如推理模型）得以成立的关键

## FlashAttention 与梯度检查点

FlashAttention 的反向在原地从 Q, K, V（已存）重算 attention 分块。这意味着 FlashAttention已经隐式实现了 O(n<sup>2</sup>) attention 矩阵的激活重算。无需再单独对 attention 层做 checkpoint这样做反而会多余地重算 Q,K,V。

## 11.7 大规模容错

## 硬件故障现实

单卡 MTBF：约 10,000 小时。512 卡集群 MTBF：10000/512 ≈ 20 小时。算上软件/网络故障，实际 4–8 小时。多日训练：会遇到 5–15 次故障。没有容错机制，一次故障就会让整次训练报废。

## 生产级容错栈：

1. 探测：NCCL 超时（60s）、GPU 心跳（10s）、NVML 健康监控、ECC 错误计数。

2. Checkpoint：每 50–100 步异步保存。非阻塞（后台线程）。保存内容：模型权重、优化器状态（Adam m/v）、调度器状态、RNG 状态、KL 系数、replay bufer。保留最近 3 个 checkpoint。70B 用时约 30s（并行写入 NVMe）。

3. 恢复：(a) 生成集群无状态，直接重启并加载最新权重。(b) 训练集群：加载 checkpoint，剔除故障节点重建 NCCL 进程组，重新分配 FSDP 分片，从最近 checkpoint 续训。

4. 弹性训练：Torch Elastic / Kubernetes 自动扩缩。几分钟内替换故障节点。训练以 N − 1 块GPU 暂时继续。

5. 预防：训练前做 GPU 健康预筛（跑 GEMM 压测）。热备机待命。双轨 InfiniBand 等冗余网络通路。

!!! note

## 通信-计算重叠

现代框架（FSDP、DeepSpeed）会积极地让通信与计算重叠：
前向传播：当第 i 层在计算时，AllGather 预取第  $i+1$  层的参数。第 i 层一结束，其参数立刻被丢弃（“free-after-forward”）。
反向传播：当第 i 层在算梯度时，ReduceScatter 发送第  $i+1$  层的梯度。调优得当时，这种重叠可隐藏 70–90% 的通信延迟。
调优旋钮：prefetch_factor（提前预取多少层）、reduce_bucket_size（梯度归约的粒度）、backward_prefetch（反向预取的“pre”还是“post”策略）。
## 11.10.4 网络拓扑设计

生产集群采用 fat-tree 或 rail-optimized（按轨优化）拓扑：

- Fat-tree：每一级都具备全二分带宽。任一节点都能以满速与任一其他节点通信。代价昂贵（需要大量交换机），但灵活性最高。

- Rail-optimized：每个节点的 GPU i 连接到同一台叶子交换机（“轨 i”）。轨内 AllReduce 便宜，跨轨流量昂贵。Meta 的 RSC 和 Google 的 TPU pod 都采用此拓扑。

- 3D torus / Dragonfly：用于 HPC 集群（Frontier、Aurora）。拓扑感知的作业放置至关重要。

## 作业放置很重要

在 512 卡集群上，随机分配节点会因网络拥塞导致 2–3× 减速。始终请求连续的节点块。生产调度器（Slurm、Kubernetes）应当强制本地性：一个训练作业的所有节点应处于同一叶子交换机下，或彼此距离不超过一跳。

## 11.11 训练吞吐与模型 FLOPs 利用率

## 11.11.1 衡量训练效率：MFU

模型 FLOPs 利用率（Model FLOPs Utilization, MFU） [55] 是衡量训练效率的标准指标：

$$
\mathrm{MFU} = \frac {\text {实际吞吐(tokens / 秒)} \times \text {每token的FLOPs}}{\text {硬件峰值FLOPS}}\tag{11.5}
$$

对于参数量为 P、序列长度为 s、batch 大小为 b 的 transformer：

$$
\mathrm{每} \mathrm{token} \mathrm{的} \mathrm{FLOPs} \approx 6 P + 1 2 \cdot n _ {\mathrm{layers}} \cdot d _ {\mathrm{model}} \cdot s\tag{11.6}
$$

系数 6 来自：2（乘加）× 3（前向 + 反向，反向约为前向的 2×）。第二项对应 attention 的 $O ( s ^ { 2 } )$ 代价。

## 为什么 MFU 会随规模下降

更大的模型需要更多并行，会引入：

1. 通信开销：FSDP 的 AllGather/ReduceScatter（64 GPU 时 ∼10–15%）

!!! note
    2. 流水线气泡：PP 在 micro-batch 的首尾引入空闲（PP=4 时 ~15-25%）
    3. 辅助模型占用显存：reference/RM 占用了本可用于更大 batch 的显存
    4. 负载不均：并非所有层计算量相等（embedding vs transformer block）
    经验法则：训练目标 MFU > 40%。低于 30% 时应使用 profiling 诊断。

## 11.11.2 算力最优的 batch 设计

有效 batch 大小与硬件利用率之间存在并非显而易见的相互作用：

$$
\text { 有效   } \mathrm{batch} = \mathrm {micro\_batch} \times \mathrm {grad\_accum} \times \mathrm{DP} \text {   度   }\tag{11.7}
$$

- 过小：GPU 利用率低（算术强度低），通信占主导。

- 过大：每 token 的学习收益递减（超过 critical batch size），算力被浪费。

- 最佳点：临界 batch size（critical batch size） $B _ { \mathrm { c r i t } }$ ，即梯度噪声等于梯度信号之处。对 LLM，B<sub>crit</sub> ∼ 1–4M token [250]。

对 RLHF 而言，batch 包含的是 rollout（不仅仅是 token）：

$$
\mathrm{RLHFbatch} = N _ {\mathrm{prompts}} \times K _ {\mathrm{generations}} \times L _ {\mathrm{平均响应长度}}\tag{11.8}
$$

生产常见取值：N = 128 条 prompt，K = 1–4 个生成，L = 256–512 token → 每步 32K–256K token。

## 11.15 RL 训练的优化器配置

RL 训练（PPO、GRPO、DPO）相比预训练或 SFT 对优化器有独特要求。Loss 地形非平稳（policy变化会改变生成的数据）、梯度更嘈杂（reward 信号方差大）、且更容易出现灾难性遗忘（CatastrophicForgetting）或 reward hacking。本节以 AdamW [238] 作为默认优化器，整理 RL 特有的优化器实践指南。

## 11.15.1 为什么 RL 需要不同的优化器设置

!!! note
    RL vs. SFT 优化——关键差异
    - 数据分布非平稳：SFT 数据集固定，而 RL 每轮迭代都会生成新的 rollout——数据分布随 policy 一起漂移。
    - 高梯度方差：reward 信号稀疏且嘈杂；梯度方差远高于在精心策划数据上的交叉熵。
    - 需要更小的更新：policy 必须贴近 reference 模型（KL 约束），所以学习率比 SFT 小 10–100×。
    - 不用 weight decay：正则化由 KL 惩罚提供，而不是 weight decay。再叠加 WD 可能与 KL 约束相互对抗。
    - 更短的 warmup: RL 从已收敛的 SFT checkpoint 起步——优化器状态只需极短的 warmup。

## 为什么 RL 用恒定（Constant）调度？

Cosine 与线性衰减调度都假设训练 horizon 固定、loss 单调下降。RL 训练两者都不具备：reward可能停滞、尖峰，或不可预测地震荡。短暂 warmup 之后保持恒定 LR，可让优化器在整个训练中始终保持响应能力。若必须衰减，请使用非常温和的线性调度，最小 LR 比例保持较高 $( \geq 0 . 5 ) _ { \mathfrak { c } }$

## 11.15.3 RL 用 Beta-2 = 0.95：更快的自适应

Adam 默认的 $\beta _ { 2 } = 0 . 9 9 9$ 给二阶矩留下了非常长的记忆（有效窗口 ∼1000 步）。在 RL 训练中，loss地形随 policy 演化迅速变化——1000 步前的梯度方差已无关紧要。使用 $\beta _ { 2 } = 0 . 9 5$ 把窗口缩短到∼20 步，让自适应学习率能够迅速响应变化中的梯度统计。

## beta2 = 0.95 反受其害的场景

对于非常小的 batch（例如在线 RL 中 batch=1）， $\beta _ { 2 } = 0 . 9 5$ 会让二阶矩估计噪声过大。这种情况下，使用 $\beta _ { 2 } = 0 . 9 9$ 作为折中，或通过梯度累积加大有效 batch。

## 11.15.4 RL 的混合精度：FP32 Master 权重至关重要

RL 训练对数值精度尤其敏感：

- 梯度更嘈杂——小幅更新必须在多步中精确累积

- 学习率极小 $( 1 0 ^ { - 6 } – 1 0 ^ { - 7 } )$ ），使得 $\Delta \theta \ll \theta$

- BF16 尾数（7 位 ≈ 0.8% 相对精度）无法表示相对于 $1 0 ^ { 0 }$ 量级权重的 $1 0 ^ { - 6 }$ 量级更新

RL 训练务必使用 FP32 master 权重。纯 BF16 训练（不留 FP32 副本）几乎必然会让 PPO/GRPO 在 100–500 步后出现 reward 崩塌。

## 11.15.5 梯度裁剪对 RL 至关重要

在 PPO 和 GRPO 中，reward 信号变异性可能极高，尤其训练早期。一个坏 batch 就能产生 norm> 100 的梯度，足以彻底破坏模型权重。 $\mathtt { m a x \_ g r a d \_ n o r m } { = } 1 \cdot 0$ 是标准设置。SFT 下裁剪不那么关键，但仍建议使用。

## RL 训练绝不要关闭梯度裁剪

SFT 的梯度 norm 通常稳定在 0.1–1.0；而 RL 的梯度是尖刺型的，原因有三：(1) reward 方差经policy gradient 传播；(2) 稀有的高 reward 轨迹会产生异常大的更新；(3) policy 漂移时 KL 惩罚项会产生大梯度。哪怕只有一步 ∥∇∥ > 50 的未裁剪更新，都可能让数百步训练前功尽弃。

## 11.15.8 MoE 在 RL 训练中的考虑

!!! note
    MoE 用于 RLHF
    混合专家（Mixture-of-Experts, MoE）模型 [89] 在 RLHF 中越来越常见：
    • 优势：相同算力下容量提升 3–4×。对 reward 模型尤其有利（更多容量去打分）。
    • 挑战：专家并行需要 all-to-all 通信（token 跨 GPU 路由），与流水线并行存在冲突。
    • GRPO + MoE：效果不错，因为生成成本由激活参数主导（而非总参数）。
    • MoE 用 LoRA：可以只对路由器 + 共享层加 LoRA，或对所有专家都加（昂贵）。

## RL 优化器口诀

做 RL 微调请记住：小 LR、不用 weight decay、恒定调度、FP32 master 权重、激进裁剪。把正则化交给 KL 惩罚——优化器只管沿 policy gradient 前进，且不要冲过头。

Miles：PyTorch 原生的 RL 后训练。 Miles [295] 是 PyTorch 官方为大规模 LLM RL 打造的技术栈，把 SGLang（用于高吞吐 rollout 生成）与 Megatron-LM（用于分布式训练更新）连接起来。它同时支持分离式执行（rollout 与训练使用各自的 GPU 池，最大化利用率）与同址执行（把两者放在同一批节点上，用于小规模实验）。Miles 代表了此前临时拼凑基础设施的标准化——正如十年前 PyTorch 本身标准化了深度学习训练一样。
